# IntelliJ plugin (`idea/`)

Route A: a modular Kotlin shell (frontend tool window + JCEF, backend sidecar, native platform RPC) around the same host the VS Code extension runs; session state, ACP, transcript and accounts live in the sidecar (the Rust binary `acpira`). Run `pnpm build` and `pnpm build:sidecar` first: the frontend module takes `dist/webview/*` as resources, and this machine's binary from `dist/sidecar/<os>-<arch>/` goes into every sandbox as `<plugin>/sidecar/bin/<os>-<arch>/acpira` (without it, and without `-PsidecarBin`, the tool window reports the missing binary). Then use `cd idea && ./gradlew test buildPlugin verifyPlugin` (`buildPluginVariants checksums` for per-platform zips) or `./gradlew runIde -PrunIdeProject=<dir> [-PautoOpen] [-PjcefDebug] [-PsidecarBin=/abs/rust/target/debug/acpira]`. Split-mode probes are `runIdeSplitBoth`, `runIdeSplitFrontend`, and `runIdeSplitBackend` with the same properties; their project argument is supplied through `argumentProviders` and opens on the backend. In monolith mode, `autoOpen` shows the tool window and `jcefDebug` exposes CDP on `localhost:9222`; `hostServer` substitutes another sidecar build. The IDE redirects `System.out` and sidecar stderr (`#acpira`, `sidecar:`) into each sandbox `log/idea.log`; read there instead of Gradle output. Layout (`com.github.hotic.acpira`):

- Gradle modules — root `plugin.xml` only declares metadata and `<content>`: `acpira.shared` loads required; frontend, backend, backend-terminal, browser-legacy, and browser-modular are optional content modules. `acpira.frontend.xml` depends on `intellij.platform.frontend` and shared, and owns the `browserProvider` extension point; it does not reference JCEF classes. `browser-legacy` and `browser-modular` compile the same `browser-runtime/` sources into separate module jars. Legacy depends on the `com.intellij.modules.jcef` plugin alias and is selected only on 261; modular depends on `intellij.platform.ui.jcef` and `intellij.libraries.jcef` and is selected on 262+. Both depend on frontend/shared, so webview resources stay in frontend. `acpira.backend.xml` depends on `intellij.platform.backend`, `intellij.platform.kernel.backend`, and shared; backend-terminal depends on backend and Terminal. Sidecar, settings, project files, and RPC implementation live in `backend/`; RPC contracts/DTOs and `Acpira` constants live in `shared/`.
- `web/BrowserProvider` + `ui/JcefProbe` — tool window and editor request an applicable provider through the frontend extension point. Providers use public `JBCefApp.isSupported()` and construct `BrowserView`; linkage failures, initialization failures, and unsupported runtimes produce distinct messages. On real 262 Client, a plugin-alias-only dependency produced `NoClassDefFoundError: com/intellij/ui/jcef/JBCefApp`; declaring the public JCEF content modules fixed loading. Do not restore internal `CefDelegate` / `JBCefNativeBundleProvider` bypasses or delayed retries: the observed failure was the module class path, not a cached JCEF support result. Separate optional adapters retain 261 compatibility, where the newer JCEF modules do not exist.
- `rpc/AcpiraBackendApi` + `connection/AcpiraConnection` — frontend views attach through a native RPC `Flow<ViewEvent>` to the backend project sidecar. `Host` events preserve source order with unlimited buffering; each view's unlimited post channel remains gated until the attach flow emits its first state, preventing page `ready` from overtaking backend attach. A missing backend produces a local `FAILED` state after 15 s while `durable` keeps retrying. Reconnection reuses the frontend's remembered session id; a later backend `READY` reloads an initialized page so it emits `ready` again. `fleet.rpc.core.Blob` carries attachment bytes. The frontend `https://acpira.local` handler validates URL segments, maps a blob request's `Referer` view token back to its project connection, and fetches bytes asynchronously, while backend `BlobStore` confines real paths to `sessionsDir`. Backend toast/external/editor requests travel on a second durable `uiRequests` RPC flow and execute through `FrontendUi` (`ProjectRemoteTopic` exists in 261 but its listener API is internal and fails Plugin Verifier)
- `sidecar/SidecarService` — one per project window (project-level service): picks the binary (`SidecarLocator`: `ACPIRA_SIDECAR_BIN` / Gradle `-PsidecarBin` names one for development, otherwise the packaged `sidecar/bin/<os>-<arch>/acpira[.exe]` for the backend's OS / CPU, its executable bit restored if lost; neither is a `SidecarSetupException` shown in the error panel — there is no Node fallback), spawns `SidecarProcess` (stdout envelopes, stderr → log), sends `hello` with `capabilities` = what `platform/IdePlatform` implements. `toast`, `openExternal`, `openInEditor`, `openResolvedFile`, and `openPlanDocument` cross `uiRequests` and execute in frontend; `searchFiles`, `writeSetting`, `revealInOS`, and optional `runInTerminal` remain in backend. Start, handshake, attach, outbox drain and ordinary sends share one single-thread executor and a generation so two views cannot spawn two processes during start-up, a page `ready` cannot overtake `attachView`, and a replaced process's callbacks cannot mutate the new one (`SidecarOutbox.flush` prefixes attach envelopes). Restarts with exponential backoff (up to 5 in a row; `helloOk` does not reset the counter — only a >60 s run or Retry does) and re-attaches every view on the session it was showing (`View.lastSessionId`, tracked from `init` / `session` host messages); `helloReject` ends in `FAILED` with the reason. The tool window swaps in an error panel with Retry on `FAILED`. IDE exit disposes the service → `shutdown` → the sidecar and its agent processes are gone (verified: no orphans)
- `settings/AcpiraSettings` — the application-level settings store (flat `acpira.*` keys as JSON): a `SimplePersistentStateComponent` whose `BaseState` holds the one JSON document (`var json by string("{}")`), persisted in `options/acpira.xml` (not roamed) — `SerializablePersistentStateComponent` over an immutable data class serialized to an empty `<State />`, `AcpiraSettingsStateTest` pins the XML round trip; `writeSetting` RPCs land here and every project's sidecar gets a `settingsChanged` event
- `platform/TerminalRunner` + `backend-terminal/IdeTerminalRunner` + `TerminalCommand` — backend declares the interface and asks the application container for its optional service; the `runInTerminal` capability exists only when `acpira.backend.terminal` loaded with the Terminal plugin. The implementation opens a Terminal tool window tab (`createShellWidget` + `sendCommandToExecute`) with one quoted line. A `null` environment value removes the variable, so POSIX gets `env -u ACP_BACKEND K=v cmd …`, PowerShell `$env:ACP_BACKEND=$null; $env:K='v'; & 'cmd' …`, and cmd.exe `set "ACP_BACKEND=" & set "K=v" & cmd …`. The dialect follows `TerminalProjectOptionsProvider.shellPath`; `TerminalCommandTest` covers quoting
- `platform/IdeFiles` + `FileRank` — `searchFiles` lists the project's content with `ProjectFileIndex.iterateContent` in a read action (excluded folders, ignored names, `node_modules` / `.git` skipped; 20 k cap, 15 s cache, shallow-first) and ranks with a port of `src/host/fileRank.ts`; `FileRankTest` mirrors `test/fileRank.test.ts` so the two scorers stay identical. Runs on a pooled thread, not the sidecar's reader thread
- `ui/AcpiraEditor` — editor tabs: `AcpiraSessionFile` (an in-memory `LightVirtualFile` of a private binary file type, so no other provider claims it) opened by `AcpiraEditors.open(project, sessionId?)` from the tool window's "Open in Editor" title action (fresh session, like the VS Code view title button) or the `openInEditor` RPC; `AcpiraEditorProvider` (`HIDE_DEFAULT_EDITOR`) builds an `AcpiraEditor` holding an `AcpiraBrowser` with host `editor` attached at once on the session, `AcpiraTabTitle` names the tab after the session (`AcpiraBrowser.onSession` → `FileEditorManagerEx.updateFileName`)
- `web/AcpiraScheme` — the frontend-only `https://acpira.local` resource handler, registered once on the running `CefApp`: `/index.html?view=<token>` is generated per JCEF bridge and theme; `/webview/*` comes from frontend module resources; `/blobs/<sessionId>/<blob>` is parsed and validated synchronously, then a CEF async handler requests `fleet.rpc.core.Blob` from backend `BlobStore`. Resource paths remain slash-separated and confined; backend resolves symlinks and requires a regular file under the real sessions root. `AcpiraSchemeTest` covers pure routing and web resources; `BlobStoreTest` covers traversal and symlink escape
- `web/AcpiraBrowser` — one frontend JCEF view: `JBCefJSQuery` posts through its per-view ordered `AcpiraConnection` channel; Base64 `MessageEvent` delivers backend host messages; navigation off origin and popups are refused; console errors are logged. Theme follows the IDE live through `LafManagerListener` / `EditorColorsListener`. `ui/AcpiraToolWindowFactory` shows JCEF or backend-unreachable state, and Retry calls backend RPC. `DevHooks.kt` implements `-Dacpira.dev.autoOpen`; `WindowFocusRelay` forwards activation through `AcpiraConnection`

Distribution: `./gradlew buildPlugin buildPluginVariants buildMarketplacePlugin checksums` (after `pnpm build` and `pnpm build:sidecar --all`, which CI runs on one runner per OS) builds the binary-free base ZIP (what `verifyPlugin` checks, not installable on its own), six smaller manual-download ZIPs, and `acpira-<version>-universal.zip` for Marketplace. The universal ZIP contains the six Rust sidecars in `sidecar/bin/<os>-<arch>/`; `SidecarLocator` selects the backend machine's OS and CPU. Releases up to 1.6.0 carried pinned Node.js runtimes under `node/` and the Node sidecar instead; no Node runtime or script is packaged or used any more. Optional backend-module OS dependencies do not constrain whole-plugin installation in split mode, so platform variants must not be published to Marketplace. The same universal version installs on heterogeneous frontend/backend machines. Manual variants retain version suffixes and backend OS/CPU dependencies. The root version comes from `package.json`; change notes come from the matching `CHANGELOG.md` section. POSIX binaries carry executable ZIP permissions. `scripts/verify-idea-packages.py` verifies all eight archives, module descriptors, binary equality, permissions, versions and checksums. `verifyPlugin` checks the binary-free ZIP, whose module jars match the universal package, against 261/262/263.

Release: `.github/workflows/release.yml` builds and verifies the IDEA archives after `pnpm build` with the six binaries of the `sidecar` job, attaches the universal and six manual ZIPs plus `SHA256SUMS` to GitHub Release, and uploads only the universal ZIP to JetBrains Marketplace using `JETBRAINS_MARKETPLACE_TOKEN`. The unsuffixed version is checked for duplicates before upload. Marketplace review remains asynchronous; a successful upload does not establish approval.

Split-mode facts on 2026.1: `runIdeSplitBoth` loads frontend/shared in JetBrains Client and backend/shared/backend-terminal on the host, with exactly one sidecar in the backend project (`IdeProductMode.isBackend`, real project cwd). `runIdeSplitFrontend` loads the UI but reaches no RPC provider and shows the 15 s backend-unreachable state; it must not start a local sidecar. `runIdeSplitBackend` is diagnostic only: Lux projects the tool window, but the frontend browser does not know the backend-registered `https://acpira.local` factory and fails with `ERR_UNKNOWN_URL_SCHEME`. JCEF and `AcpiraScheme` therefore stay frontend-only. Split run tasks pass `-PjcefDebug` only to the backend JVM, so JetBrains Client has no CDP endpoint; GUI probes use screenshots and native input instead. `-PautoOpen` does not expand the JetBrains Client tool window, which is opened through View → Tool Windows → Acpira. Backend `OpenFileDescriptor.navigate` does not project without the client's `ClientId`; file and plan notifications cross the wire as absolute backend paths. Frontend then calls `resolveFile(projectId, path)` over RPC; backend resolves the file and calls `rpcId()` within that requesting Client session, and frontend opens `id.virtualFile()` with `OpenFileDescriptor`. Calling `rpcId()` on the sidecar reader thread loses the Client session and can return `serializedValue=null`; resolving the backend path through frontend `LocalFileSystem` only appeared to work in the same-machine sandbox and fails across machines. Verified end to end in the BOTH sandbox: page load, prompt round-trip through the fake agent, README.md opening in the client editor, and sidecar kill → ~1 s backend restart → re-attach → new-session prompt (the dead session correctly stays read-only).

Facts verified in a 2026.1 sandbox before the shell was written:

- Build against IntelliJ Platform 2026.1 (`intellijIdea("2026.1.4")`, branch 261, JDK 21, `sinceBuild = 261`, no `untilBuild`); 2026.2 (262) is built with Java 25 but runs 261-compiled plugins. `IC` / `IU` helpers stopped at 2025.3, IDEA is one distribution. The platform ships Kotlin 2.3 metadata, so the Kotlin Gradle plugin must be on the 2.3 line (2.1 fails with "incompatible version of Kotlin"). IntelliJ Platform Gradle Plugin 2.18.1, Gradle 9.5.1, `useInstaller = true` (the SDK archive has no JCEF natives)
- JCEF: `<depends>com.intellij.modules.jcef</depends>` resolves on 2026.1.4 (a `pluginAlias` of the core plugin in `product-info.json`; `JBCefApp` sits in `lib/intellij.platform.ide.impl.jar`) and is required by 2026.2, where JCEF became a bundled plugin. Do not add `bundledPlugin("intellij.platform.ui.jcef")` to the Gradle build — it does not exist on 2026.1. 2026.1 runs JCEF out of process by default (`ide.browser.jcef.out-of-process.enabled`, a `cef_server` child); windowed browsers are created regardless of `setOffScreenRendering`
- Serving the webview: register the resource handler on the running app, `CefApp.getInstance().registerSchemeHandlerFactory("https", "acpira.local", factory)` after `JBCefApp.getInstance()` — no init-order race, and `https://acpira.local` is a secure context (`navigator.clipboard`, `type="module"` scripts, `fetch` all work; 512 KiB each way in ~50 ms, 200 messages stay ordered, round trip ~10 ms). A real custom scheme (`JBCefApp.addCefCustomSchemeHandlerFactory`, must run before JBCefApp starts — `AppLifecycleListener.appFrameCreated` is early enough) is **not viable** under out-of-process JCEF: `CefSchemeRegistrar.addCustomScheme` returns false, the scheme is non-standard, and module scripts die with "Cross origin requests are only supported for protocol schemes". Handlers must URL-decode, normalize and confine to the resources root with slash-separated segments (`..`, `%2e%2e`, `%2f` are refused with 403; never `Paths.get()`, which would turn `main.js` into `\\main.js` on Windows) and set the right MIME type
- Bridge: the served `index.html` gets the `JBCefJSQuery.inject("JSON.stringify(m)")` snippet spliced in as `window.__acpiraApi.postMessage` before any page script; Kotlin → page is `executeJavaScript("window.__acpiraReceive('<base64>')")` and the page `JSON.parse`s and dispatches a `MessageEvent`, so no JSON is ever pasted into a JS literal. Navigation off our origin is refused in `CefRequestHandlerAdapter.onBeforeBrowse` (the page stays; `ERR_ABORTED` in `onLoadError` is that refusal). `window.open` without a user gesture never reaches `onBeforePopup` (Chromium's popup blocker), so it proves nothing
- Processes: the sidecar and the CLIs it spawns run with `EnvironmentUtil.getEnvironmentMap()` / `PathEnvironmentVariableUtil.findInPath` (the IDE's login-shell environment), never `System.getenv` alone — a Dock / Toolbox launch has no shell PATH. `runIde` from a terminal inherits the shell PATH, so a sandbox cannot show the difference; the code path is still the one to use

Directory navigation in split mode: `resolveFile` returns `ResolvedPath` with the backend directory flag because Client remote VFS handles may report directories as files. The frontend uses its current project pane's native `SelectInTarget.selectIn(FileSelectInContext(...), true)` for directories. Direct `ProjectView.select` on the frontend follows an expansion-only path for remote roots; calling it on the backend selects the backend tree without selecting the Client tree. Verified on the macOS 262 Client with the Linux `/home/hotic/Work/Server` root selected and README.md still opening at line 1.
