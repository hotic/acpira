# Session store

Where it lives: `rust/crates/acpira-host/src/store/transcript_store.rs` (the store), `store/db.rs` (connections, catalogue), `store/db/body.rs` (rows), `store/db/migration.rs` (compatibility files), `store/pack.rs` (cold packing of file-backed records).

- The session catalogue and migrated bodies live in `sessions.db` (rows per record head / turn head / block, `store/db/body.rs`); `index.json` is only the file backend's cache and the catalogue's first import. A session migrates on its first save: body transaction, then the pre-migration archive (only when a whole legacy file was there), then the compatibility stub.
- A database created in a directory with no record files (live or trashed) is stubless, flagged in `user_version` beside the schema (`db.rs`): no `<id>.json`, no pre-migration archive. There the catalogue row is the session: listed while `trashed_at` is empty, trashed by setting it (the blob folder still moves to `trash/`), swept by it. A whole record file that turns up (an older engine's, a copy, a revert) is read as usual and removed once its first save is in the rows. The flag is decided once at creation; stores with stubs keep them, everything below about stubs applies to those only.
- An engine before the flag reads a stubless database as a newer schema and keeps to record files, so it never takes a body without a file for a deleted session; it sees an empty list there.
- Shells cannot read the catalogue: a session link in a store with `sessions.db` is handed to the engine instead of checked against a record file (`extension.ts`, desktop `links.rs`), so a link from elsewhere ends in the engine's missing-record toast.
- With no file to show what happened meanwhile, every removal of a stubless row is conditional on it still being trashed (`delete_trashed`), and a restore clears `trashed_at` before it moves the blob folder back; a reconcile writes a listed body's summary only while the row is still listed (`set_listed_summaries`).
- A catalogue reconcile never deletes a database body or changes where a body lives: a missing stub hides the session (`trashed_at`) until upkeep purges it weeks later, an unreadable one keeps its entry. Only a save, a revert, a copy from another machine or an explicit removal does.
- A save compares row hashes kept in memory (`SaveCache`), dropped when `PRAGMA data_version` shows another connection committed. A debounced save lets the session leave out subagents the store holds (`RecordSource::record_parts`); `flush` hands over everything.
- The stub trails the body (refreshed on a flush, on new blobs, on a foreign stamp, else after `STUB_REFRESH`), so the body is the record: a stub adds to it only what an older engine appended, and a whole record file newer than the body takes over from it. Every stub written here carries `sqliteStub`; an older engine drops the field when it rewrites the record, and a stub without it gives its list fields (title, pin, archive, category) to the body, since a list edit there keeps `updatedAt`.
- The pre-migration archive is the whole record the stub replaced: a whole file written back (revert, `ACPIRA_STORE=files`, a copy from another machine) removes it, and the next migration archives again, over whatever is still there.
- The trash sweep removes a body only once the trashed file is gone and no record is listed under the id (an undo in another engine may land mid-sweep).
- WAL or schema-open failure keeps the file backend, which refuses to write a session it could only load from its archive. Upkeep quarantines the database only when the check finds damage, never on a lock or I/O error. `ACPIRA_STORE=files` still reads the database and moves a body back to its file on save; `acpira store revert ID` does one at once, under the session's lease (refused while an engine has it open).
- `sync_index` waits for chained record writes, else a fresh session's first write is mid-rename and another window takes it for deleted.
