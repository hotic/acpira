# Agent quirks: Codex (codex-acp)

How codex-acp and the bundled codex behave on the ACP wire, with the version observed ("source" = read from the shipped package). Other CLIs and cross-agent notes: `agent-quirks.md`.

## Codex (codex-acp)

- codex-acp 1.13.0 (bundled codex 0.155.1, `CODEX_PATH` overrides): `loadSession` + list / resume / close / delete / fork; auth `api-key` and `chat-gpt` with no terminal methods, so sign-in goes through `authenticate`. Terminal fallback is `codex-acp cli login`; bare `codex-acp login` needs a separate `codex`.
- Controls: modes read-only / agent / agent-full-access (2.1.1 adds `workspace-write`), `model`, `reasoning_effort` (low … ultra), a `fast-mode` boolean (2.8.0 moves its category from `model_config` to `speed`), `collaboration_mode` (default / plan). Skills appear as `/$<name>` commands. Hidden models are not listed.
- A thread on a model no longer listed: the adapter lists it first but drops `reasoning_effort` and `fast-mode`, and an effort set fails invalid params until a listed model is picked (1.13.0 source).
- List / resume work only on the canonical cwd: the adapter canonicalizes (`/var` → `/private/var`) and string-compares per page, so `native_sessions.rs` retries with `realpath`.
- 2.1.1: a rollout is written only after the thread's first user message; once the process is replaced, resuming an unprompted thread fails `Internal error` with `data.details "no rollout found for thread id"`, meaning gone.
- 2.1.1 / codex 0.159.3: one writer per thread (`$CODEX_HOME/thread-writer-locks/`); resume while another process (another window, the Codex app's `app-server`) holds it fails `"thread <id> already has an active writer"`, classified locked. No PID, so no take-over.
- Compaction updates are gated on `clientCapabilities.session.compaction` (source).
- Tool calls open with `in_progress` (1.13.0), unlike Claude. 1.13.0 left a summoned child's `tool_call` `pending` forever with no permission request; `live_activity` stops naming an open tool once later output arrives.
- Image generation (1.13.0): a `kind: other` call titled `Image generation`, then a completed update with `Revised prompt:` text plus a full base64 `image` block, repeated in `rawOutput`.
- **Ultra** is a real `reasoning_effort` ("Maximum reasoning with automatic task delegation", GPT-6 Astra and others); delegated agents arrive as ordinary `session`-tier children, no workflow-specific wire (1.13.0). `:generation:` child ids after a restart stream normally.
- Session MCP servers (2.7.0 source): each goes to codex as `command` / `args` / `env` (or `url` / headers) only, so its tool calls end at codex's default tool timeout (60 s) and `ask_agent` answers within 50 s (`relay_client.rs`). A Codex config entry of the same name wins and the session's server is skipped, so a partial `mcp_servers.<name>` override cannot raise the timeout. The tool list is read once at thread start; `tools/list_changed` is ignored.
- As a lead (2.7.0, GPT-6 Astra): a wait that runs out answers "still working … do not poll", and Codex calls again on the same thread instead of ending its turn, once a minute for the whole round (`evals.md`, Fusion bench).
- Steering: answers an idle steer `startedNewTurn` whatever the opt-in; `_meta.codex.threadStatus` gives the idle edge (`protocol-gotchas.md` Queue).
- **Codex accounts**: the login is `$CODEX_HOME/auth.json`, refreshed in place with rotating refresh tokens, so never copied. A saved account is a private `CODEX_HOME` with its own `auth.json` and symlinks for everything else, so threads stay one store.
- Quota: `GET chatgpt.com/backend-api/wham/usage` with the access token and `ChatGPT-Account-Id` → `rate_limit.primary_window` / `secondary_window` (Pro has one weekly window). Exhaustion is AIR `quota_exhausted` (source). Unverified: cross-account resume through the shared store.
- **Goals**: 1.13.0 advertises `_meta.goal { controlMethod: '_session/goal', actions: set/pause/resume/clear }` and snapshots at `session_info_update._meta.goal`; 2.x moves both under `_meta.jetbrains.air` (`vendors/goal.rs` reads both). `/goal …` prompts equal the requests.
- Goal behaviour (1.13.0 and 2.2.2, live): an unmet goal continues after the turn with no `session/prompt`, bracketed by `threadStatus` active … idle; the host runs it as a detached turn. After two continuations without progress Codex sets `blocked` itself.
- Pause / clear never interrupt a running turn, only further continuations (a paused goal can still reach `complete`). `/goal resume` on a `complete` goal reactivates it. `usageLimited` / `budgetLimited` map to `limited`.
- An npm upgrade under a live process breaks it: codex starts `codex-code-mode-host` from its package path on each `exec`, the two share an unversioned IPC that rejects unknown fields, and the upgrade leaves the old codex running against the new host (2.1.1 → 2.7.0: every `exec` fails `failed to decode code-mode IPC frame: unknown field result_buffered_for_ns`, logged in `~/.codex/logs_2.sqlite`). Hence `AcpSession::adapter_updated` after an in-app update; an upgrade run by hand is not seen.
- Resume notices (2.8.0 / codex 0.170.0): `session/resume` attaches `startCodexTurnTracker` before `thread/resume` and omits `model`, so `configWarning`, `deprecationNotice` and a false model-mismatch warning (`recorded with model … resuming with …`, before `adopt_controls` sets the model back) flush as ACP `notice` updates around the response; `vendors/codex_notices.rs` drops them. `McpSessionStartup` also publishes skipped or failed MCP server startups after `session/new` / `resume` as `status: failed` `tool_call` updates (`toolCallId: mcp_startup.<server>.<uuid>`, `title: mcp__<server>__startup`); `codex_notices::mcp_startup_report` intercepts them so they log / toast instead of fabricating a turn.
- Open: codex-acp 2.x's "AIR tool call contract, exact diff patches" not run at turn level.

## SSH local run (exec-server)

Codex under local run in an `ssh://` folder (`remote/codex_exec.rs`, `remote.md`). Observed on codex 0.166.0 / codex-acp 2.6.0 and codex 0.170.0 / codex-acp 2.8.0 against a Linux host.

- Seam: `CODEX_EXEC_SERVER_URL=ws://…` in the adapter's environment makes the thread's only environment the remote one (`none`: no environment; unset: `local`); codex-acp passes no `environments`, and `$CODEX_HOME/environments.toml` only adds one beside `local`. `session/new` then takes a cwd that exists only on the host and loads the host's `AGENTS.md`. Shell, `apply_patch`, file reads and project config (`environmentConfig/read`) go through the server; `~/.codex` config and hooks stay this machine's.
- MCP (codex 0.170.0 / codex-acp 2.8.0): with `CODEX_EXEC_SERVER_URL` replacing the local environment, Codex rejects every client-provided stdio MCP server (`local stdio MCP server '<name>' requires a local environment`), while connecting directly from this machine to Streamable HTTP MCP entries passed in `session/new` / `resume` / `load`. `session_request` therefore bridges stdio entries (`acpira`, `acpira mcp-host` project shims, user stdio servers) onto a session-owned loopback Streamable HTTP bridge (`remote/mcp_http.rs`) whenever the adapter advertises `mcpCapabilities.http`.
- Server: `codex exec-server --listen ws://127.0.0.1:0` prints `ws://127.0.0.1:<port>`; `--ws-auth capability-token --ws-token-sha256 <hex>` wants `Authorization: Bearer` on the upgrade (401 otherwise). The client sends the URL's path untouched, which is where the tunnel's secret rides. The host gets this machine's exact version; mixed versions are unverified.
- Build: the `@openai/codex@<version>-<platform>-<arch>` package's `vendor/<triple>/`; the server needs only `bin/codex`, `codex-package.json`, `codex-path/` and `codex-resources/bwrap`.
- Stop: a cancelled turn sends the server no `process/terminate` (the CLI's exit does), so its command runs on, where a local one is killed. SIGTERM has the server end its commands and exit; SIGKILL leaves them running, each a session of its own. Hence one server per session, ended on stop through the helper's `exec` `graceMs` (`ExecTunnel::stop_commands`).
- Reconnect: the client retries about ten times a second, first with `resumeSessionId`. The same server resumes with its processes alive; a new one answers `unknown session id` (the open tool call fails) and the next connect starts clean.
- Sandbox: built by the server on the host. Where bubblewrap cannot set up (`kernel.apparmor_restrict_unprivileged_userns=1`, Ubuntu 24.04's default: `bwrap: loopback: Failed RTM_NEWADDR`) every command first exits `sandboxDenied` and waits for Guardian Review or an approval, as Codex run on that host does; `use_legacy_landlock` panics there. `agent-full-access` skips the sandbox.
- Limits: a summoned Codex child in a host folder is refused (`relay/round.rs`); the first start on a host waits for the upload with log lines only. Unverified: macOS hosts, a helper older than `graceMs` (it kills, leaving the commands).
- Probe: `scripts/probe/remote-codex-host.ts`.
