# Agent quirks: Claude (claude-agent-acp)

How claude-agent-acp and the Claude Code it bundles behave on the ACP wire, with the version observed ("source" = read from the shipped package). Other CLIs and cross-agent notes: `agent-quirks.md`; host handling rules: `protocol-gotchas.md`.

## Claude (claude-agent-acp)

- The adapter bundles the Claude Agent SDK and its native `claude` (`CLAUDE_CODE_EXECUTABLE` overrides). `authMethods` is empty unless the client advertises `clientCapabilities.auth.terminal: true`; then terminal methods run `--cli auth login …` in a host terminal, never `authenticate` (0.81.0).
- Controls (0.87.0): modes default / acceptEdits / plan / auto / bypassPermissions, `model`, `effort` low … max, a `fast` boolean. With the AIR `recommendedValue` capability it drops placeholder `default` rows. Effort is re-seeded per model.
- The model list is the bundled native binary's own: a new model appears only once the pinned SDK carries it (Sonnet 5.5 from SDK 0.3.284, Haiku 5.5 from 0.3.293, while 0.87.0 still pinned 0.3.287). Hidden families key by display name, so a new name shows by default.
- `usage_update` reports `used: 0`. The window is seeded at 200000 unless the model text matches `\b1m\b`, corrected only at turn end and per adapter process (0.81.0, issue #596); `vendors/claude_window.rs` replaces exactly 200000 for official models.
- Window sizing (2.1.224): `[1m]` or a catalog-native 1M model gives 1M, else 200k. `CLAUDE_CODE_MAX_CONTEXT_TOKENS` applies only to ids not starting `claude-`, so a gateway alias `claude-opus-5.5` stays 200k. `CLAUDE_AUTOCOMPACT_PCT_OVERRIDE` is a fraction of `min(window, AUTO_COMPACT_WINDOW)`.
- Thinking: recent models default the API's `thinking.display` to omitted, so thoughts arrive signature-only and vanish. `vendors/claude_thinking.rs` sends `_meta.claudeCode.options.thinking = { type: adaptive, display: summarized }` (0.81.0). Unverified through a custom `ANTHROPIC_BASE_URL`.
- Text after a tool call is not streamed (0.84.0, Opus 5.5 observed): every `agent_message_chunk` of the closing reply arrives in the same millisecond at the end of the turn, while a reply with no tool before it streams normally. The reply therefore lands in one frame as the turn settles.
- A whole-file `Read` carries `locations [{ line: 1 }]` with no offset, images included (2.1.224); `toolFiles` ignores line 1 and lineless files.
- Tool calls skip `in_progress`: `pending` → updates without status → `completed` (0.78.0, 0.83.0). The input streams as pending `rawInput` updates and the call runs once it is complete (progress beats carry only `_meta`), so the last pending input marks the start (`tool_call::time_tool`). Later updates resend only changed fields, so grown `rawInput` arrives without the title (`relay.rs` remembers rows by id).
- Restoring a never-prompted session: Claude Code writes no transcript until the first turn, so `session/resume` fails `-32002 resourceNotFound` (0.87.0), treated as gone; the Ultra rebuild of such a session is a fresh `session/new` (`UltracodeState::unprompted`). Resume answers with the adapter's defaults whatever the session ran (0.83.0).
- Compaction: with `clientCapabilities.session.compaction` (≥ 0.81.0) the adapter sends standard `compaction_update`; without it, a `think` tool call "Compact conversation" (0.81.0 source; not seen live). "Autocompact is thrashing" is Claude Code's own circuit breaker, not a host fault.
- Cancel with pending steers: up to 0.85.x a stop leaves unpicked steers queued, Claude Code starts on them at once, and `session/prompt` answers `cancelled` only at the 30 s force floor. From 0.86.0 cancel drops them silently; the host re-queues them (`protocol-gotchas.md` Queue).
- **Plan mode under the SDK** (Claude Code 2.1.284, source): plan mode no longer auto-allows tools when non-interactive, so every non-read-only call arrives as `session/request_permission`. `acpira.planAutoApprove` answers `allow_once` (never `allow_always`, which writes a lasting rule) in `session/gates.rs`. Not checked on a live turn.
- Plans: 0.84.0 streams ExitPlanMode with no input, then refines with `rawInput: { plan, planFilePath }` but drops `kind` / `title`. 0.93.0 answers Revise (`reject`) by ending the turn `cancelled` with nothing else. TodoWrite is written while planning.
- **Bypass-immune safety asks** (0.93.0 / SDK 0.3.268+, source and live): delete-class Bash rulings (e.g. `cd /tmp && rm -f …`) still invoke `canUseTool` under `bypassPermissions` with `suppressAlwaysAllowRule: true` (`Yes` / `No` only); `gates.rs` answers `allow_once` in a full-access mode.
- **Goals** (0.83.0+): only `set` / `clear` under `_meta.jetbrains.air.goal`, to AIR clients only. `_session/goal` while idle runs a turn the host never asked for, so every Claude goal action goes as a `/goal …` prompt (`Vendor::goal_clear_starts_turn`); the echo (`Goal set: …`) is dropped.
- The goal is a Stop hook; once met the CLI emits `active_goal: null`, but 0.87.0 drops it while the setting `/goal` command is pending (always on a first-check pass). The host treats an `end_turn` with an active goal as met (`goal::met_by_turn_end`).
- Background subagents hold the parent turn open: `session/prompt` waits until every `run_in_background` child leaves `liveBackgroundTasks` (0.81.0 source). Intentional; a follow-up prompt only queues, and a running child is never marked disconnected by the prompt returning.
- Autonomous cycles: background Bash never holds a turn, so its completion wakes the model after `end_turn` and the follow-up streams with no start mark. Its end is the result's `usage_update`, the only one with `cost`; `_meta["_claude/origin"]` rides on it only when the result names an origin, and a scheduled-wakeup cycle had none (0.84.0), so it ran until a stop. `vendors/claude_autonomous.rs` runs it as a detached turn.
- A `session/prompt` sent mid-cycle is folded into it by the CLI. Up to 0.94.x the adapter books that cycle's result as autonomous and absorbs its idle, so the prompt never returns (seen on 0.84.0). From 0.95.0 the folded prompt owns the cycle and settles normally (`scripts/probe/steering-host.ts --autonomous`, passed on 0.99.1). `_session/steering` answers `promptRequired` during a cycle in every version.
- `ScheduleWakeup` is a timer inside the CLI: no AIR `asyncTasks` and no `task_started` for it (0.84.0 source), so a pending wakeup is invisible on the wire and an idle release would kill it. The engine reads it off the tool's row, the delay from its result text ("(in 1860s)"), and treats it as background work until the cycle it starts (`vendors/claude_wakeup.rs`).
- Without the notices capability, a stopped task's `**Task stopped by user:**` text arrived after `end_turn` and opened an autonomous cycle nothing closed (0.93.0); advertising `notices` avoids it.
- Native subagents: with AIR `nativeSubagentSessions` the child streams under its own session id after `subagent_spawned` (0.78+). Gated by `_meta.jetbrains.air` because the SDK strips the draft `clientCapabilities.subagents`; other agents ignore both keys.
- 0.93.0 swallows every `Agent` / `Task` tool call, so `subagent_spawned` is the only placement mark; the engine adds a stand-in delegation row.
- `SendMessage` to a finished child announces `<taskId>:generation:<n>` but the stream keeps the first run's `parentToolUseId`, which the adapter drops as late (0.83.0, unchanged 0.89.1). The run is only in `subagents/agent-<taskId>.jsonl`; `Vendor::resumed_child_logs` reads it by time window.
- **Claude accounts**: the OAuth login lives in the secure store named by `CLAUDE_SECURESTORAGE_CONFIG_DIR`: keychain item `Claude Code-credentials-<sha256(dir)[..8]>` (unsuffixed when unset; 2.1.300 suffixes from `CLAUDE_CONFIG_DIR` alone), elsewhere `<dir>/.credentials.json`. A saved account is a private namespace only; `~/.claude` stays shared.
- The local login (default keychain item + `~/.claude.json` `oauthAccount`) is listed automatically; a terminal `claude auth login` outside Acpira lands there. Acpira never refreshes tokens (the refresh token rotates); never copy or restore rotating tokens over another login.
- Public plan names differ from OAuth identifiers: `/api/oauth/profile` still returns `organization_type: claude_max` + `rate_limit_tier: default_claude_max_20x` for Ultra. Neither that tier nor the public name proves the account has no five-hour limit; use the usage response's windows.
- Quota: `GET api.anthropic.com/api/oauth/usage` with `anthropic-beta: oauth-2025-04-20` → `five_hour` / `seven_day` `{ utilization, resets_at }`. Rate-limits hard per token (429 while `/api/oauth/profile` answers), so reads are spaced and paused after 429 (`host-architecture.md`). Open: whether the pause alone lets it recover.
- Refresh-token expiry (2.1.300 source): past `refreshTokenExpiresAt` the refresh gets `invalid_grant` and the CLI blanks the stored tokens (compare-and-swap under `.oauth_refresh.lock`); only a new login restores it. The account stays listed and its quota reads 401 → `expired`.
- `auth status` is not read-only: native subcommands start a refresh when the access token is near expiry and `process.exit` right after printing. The adapter runs it on `initialize` and every prompt.
- macOS `log show`: Bun-built Claude binaries share one Mach-O UUID, so `processImagePath` can name another install. A temp HOME does not isolate the keychain; auth fixtures need an explicit secure-store namespace.
- Over SSH the login keychain is locked per security session: secret reads exit 36 while attributes still read, and Claude asks for `/login`. `security unlock-keychain` in that session fixes it; signing in again would rotate tokens against the desktop copy, so Acpira offers unlock (`accounts/keychain.rs`).
- Retry errors: the AIR retry warning says only "Retrying Claude, attempt N of M." and the raw `api_retry` frame adds status, error kind and `retry_delay_ms` but no body (0.84.0). The body (`529 {"type":"error",…,"request_id":…}`, or `Connection error.` plus the socket error) is only in the CLI's session log `<config>/projects/<encoded cwd>/<sessionId>.jsonl`, a `system` / `api_error` line per attempt (`retryAttempt`, `timestamp`); `vendors/claude_retry.rs` reads it after each frame. Authentication retries are left to `claude_auth.rs`.
- Silent 401s: a stale `ANTHROPIC_API_KEY` makes `auth status` report logged in, and the adapter suppresses auth warnings inside `api_retry`, so the turn retries for over a minute (0.84.0 / 2.1.284). The host ends a root turn on the second 401 `authentication_failed` retry and blocks start only on an explicit missing credential (`vendors/claude_auth.rs`).
- Exhaustion arrives as `billing_error`, `account_on_hold` or the synthetic `You've hit your…` messages (source).

## Orchestration levels (Claude ultracode)

- Claude Code 2.1.224 had `ultracode` as an effort level; 2.1.284 made it a session boolean ("xhigh + dynamic workflow orchestration" at any effort). Acpira presents it as an **Ultra** effort after Max (`vendors/claude_ultracode.rs`, `session/ultracode.rs`, `refine_controls`); the select shows `ultra` even when the agent answers `xhigh`.
- The keyword `ultracode` in a human-originated prompt also turns it on per turn (the adapter stamps `origin: human`). No adapter version publishes a config option for it. Since 2.1.284 an `effortLevel` apply without an `ultracode` key turns it off, so a settings-file `ultracode: true` does not survive the adapter's effort applies.
- It is set per session through `_meta.claudeCode.options.settings` (0.87.0). That object replaces the settings the adapter derives from `CLAUDE_MODEL_CONFIG`, so those keys are merged back in. A changed `settings` makes resume tear down and recreate the query.
- That rebuild cancels turns and kills background work (workflow tasks, subagents, summons), so a switch is deferred to just before the next prompt while anything runs. `ultra` never goes on the wire: wire effort is `xhigh` (or the highest offered). Verified on the fake agent only.
- Dynamic workflows are off for SDK hosts, so the sidecar starts the adapter with `CLAUDE_CODE_WORKFLOWS=1` unless set; `enableWorkflows: false` in settings still wins, and Ultra is not offered then.
- A running ultracode turn uses the `Workflow` tool: one `async_task_spawned { taskType: workflow }` (0.83.0, live). The adapter does not map per-agent `task_progress.workflow_progress`, but forwards raw SDK messages as `_claude/sdkMessage` when `_meta.claudeCode.emitRawSDKMessages` names a filter; `vendors/claude_workflow.rs` asks for `task_progress`.
- Every progress frame lists every agent (a queued one without `agentId`); the run ends `stopped` then `completed` at once, so `stopped` is only provisional. Agent `result` previews are cut near 400 chars, so a schema-bound JSON result never parses.
- Each workflow agent's process is in a private, version-dependent sidechain log: `<config>/projects/<encoded cwd>/<sessionId>/subagents/workflows/<runId>/agent-<agentId>.jsonl` (2.1.284). Fall back to scanning `projects/*/<sessionId>/` since the cwd encoding may differ; skip unknown lines (`session/workflow_logs.rs`, `vendors/claude_workflow_log.rs`).
