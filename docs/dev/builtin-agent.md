# The built-in agent

Acpira's own agent (`acpira`), for models that have no official harness of their own: DeepSeek, Kimi, GLM, Qwen, MiniMax, OpenRouter and other OpenAI-compatible or Anthropic Messages endpoints, plus local servers. It is Rust inside the engine (`rust/crates/acpira-agent`), served over ACP by `acpira agent --home <root>`, so it ships without Node or any TypeScript. The engine launches it like every other agent: same spawn, warm pool, process group and stderr log. `AgentRegistry::with_self_agent` registers it first, so it leads the agent order until a saved order says otherwise. Feature set and modes follow OpenCode; the loop layering follows Pi.

## Layout

- `<root>/providers.json`: model sources as the settings page writes them (contract in `acpira-shared/src/providers.rs`, mirrored by `packages/shared/providers.ts`). Keys live in `<root>/secrets.json` as `acpira.provider.<source id>`, never in the providers file. The host side is `acpira-host/src/providers.rs` (`ProviderStore`).
- `<root>/agent/sessions/<id>.jsonl`: the session log, with `<root>/agent/sessions/<id>/` beside it for `outputs/` (spilled tool output) and `plan.md`. Both are deleted together with the Acpira session that drove the agent session, once its undo window has closed (`acpira_agent::acp::session_paths`, see session deletion in `protocol-gotchas.md`).
- `<root>/catalog/models.json`: the daily catalogue refresh the host writes. The agent takes the newer of it and the snapshot compiled into `acpira-shared` (`assets/model-catalog.json`, regenerated by `pnpm catalog:update`).
- Crate modules: `acp.rs` (the ACP surface), `turn.rs` (one turn), `tools/` (read, write, edit, bash, job, grep, glob, list, todo, exit_plan, question, webfetch, websearch (`web.rs`, `html.rs`, see Web tools below), plus `names.rs` for name correction; `read` reads PNG, JPEG, GIF and WebP files as images and a PDF as its text page by page (Fewer steps below) and takes up to 12 windows in `path` and `paths` (whole files or `file:N-M` ranges) under one 50 KB budget split evenly, and asks permission for each file; a bare `path` is dropped when `paths` holds ranges of the same file, because `gemini-4-argon` fills the required field with the file and puts the lines it wants in `paths` (2026-10-23: 29 of 43 reads in one session, each re-reading the file's first 50 KB); `edit` takes one `old_string` / `new_string` pair or an `edits` list whose items may name their own files, applied in order, all or none; `read`, `write`, `edit` and `bash` also take the to-do list (`todos`) and `edit` / `write` a command to run after the change (`then_run`), see Fewer steps below; `bash` with `background` starts a job in its own process group and answers after 1.5 s (with `interactive`, in a pseudo terminal that `job` with `input` types into, Fewer steps below), `job` returns its new output since the last check, waits up to 120 s or kills it, and `jobs.rs` keeps 512 KB per job, at most 8 running, all killed when the agent shuts down: on stdin EOF or SIGTERM / Ctrl-C `run_until` cancels every turn and stops every job before it exits, since the jobs' process groups are not the agent's and the engine's signals never reach them; a SIGKILL of the agent, which the engine sends only after the 5 s grace, still leaves them running), `permission.rs`, `modes.rs`, `prompt/` (layered system prompt), `budget.rs` (tool output budget), `compact.rs` (pruning and summary compaction, below), `chunk.rs` (chunk compaction, below, with `tools/history.rs`), `skills.rs` (the shared skills as slash commands, plus `tools/skill.rs`), `mcp/` (the MCP client, with `tools/mcp.rs`, see MCP servers below), `store.rs` (session log), `catalog.rs`, `llm/` (OpenAI Chat, OpenAI Responses and Anthropic Messages clients, `family.rs` per-family request differences, `fast.rs` the fast tier, `discover.rs`), `mock.rs` (the scripted model server, feature `mock`).

## ACP surface

- `initialize` advertises `loadSession`, `sessionCapabilities.list` and `resume`, image plus embedded-context prompts, `mcpCapabilities.http` (not `sse`) and, at the top level, `_meta.steering.supported` (steering, below) and `_meta.goal` (goals, below).
- Modes are `agent`, `plan` and `raw`. Agent and Plan offer the same tools (`modes::TOOLS`, `exit_plan` included; outside Plan mode it answers with an error), so a switch between them never changes the request prefix; Raw mode (below) offers none, so entering or leaving it does once. Config options are the model select (every usable model, value `<source id>/<model id>`, the source's display name as description), an effort select when the current model has levels (default: the family's preferred level, `medium` for Claude and `high` for the rest, else the strongest, see the harness comparison below; a model added by id with none takes the catalogue's, as discovery would have filled them, unless its thinking is off. Without a level and with thinking on `auto` no thinking switch is sent at all, which on Claude means no thinking). The composer's left side holds only the Agent / Plan chip; the right side is the model's, and with no usable model it holds an Add model shortcut to the settings page. The approval level is not a session control (2026-10-12; it was a `_permission_mode` config option before, which put a second chip beside the mode): it is the agent's setting, `approval` at the top of `providers.json` (`ask` (edits and commands ask, the default when absent or unknown), `auto-edit` (edits run, commands ask) or `full` (everything runs); `APPROVAL_LEVELS` in `acpira-shared`), set from the Permissions section on the agent's settings page (`ProviderAction::Approval`) and read at the start of every turn (`Config::approval`), so a change applies to every session from its next turn. A session's `state` records no longer carry it; an older record's `approval` is ignored. `set_config_option` with `approval` is refused like any unknown option, and the host's replay of remembered prefs only sets options the session offers, so a remembered `approval` is skipped. Edits to the agent's own configuration always ask, even under `full`: `providers.json`, `secrets.json`, the prompt override folders and `.agents/hooks.json`, also through a symlinked file or folder (`Guard` compares the path as written and with its symlinks resolved; a target that does not exist yet resolves through its nearest existing ancestor).
- When `providers.json` (or the catalogue) changes, every open session whose config options moved gets a `config_option_update` within a second (`Server::watch_controls`, a stat poll), so a model saved in settings shows up in the running session's picker, not only in new ones.
- The session holds exactly what the picker shows (`acp::reconcile`, run on resume, on every `set_config_option`, in `push_controls` and at the start of a turn): a session opened before any model existed (opened with no usable source, the source saved in settings while it stays open) takes the default model and that model's default effort, and an effort the current model no longer offers, or a missing one where it now offers levels, becomes its default. Before this (fixed 2026-10-13) the picker fell back to the default model while the session held none: the host's replay of a remembered effort and the first effort click were refused with `Unknown effort`, and a first prompt went out without any level, until one model switch filled both in. A model that is no longer configured is not replaced: the picker shows the default, but the turn still refuses with "no longer configured". Verify with `tests/review_regressions.rs` (`a_session_opened_before_its_model_existed_holds_the_shown_effort`).
- Permission rules follow OpenCode's semantics: layers of (permission, pattern, decision) rules (defaults, approval level, what the user allowed in the session, then the mode), last match wins. The mode layer drops its own `ask` rules under `full` (`Mode::rules` takes the approval level), so full access runs Plan mode's commands and non-read-only MCP tools without a card; what a mode denies (any edit but the plan file) holds whatever the level is, and an "always allow" answer never widens a mode rule. Reading the session's `outputs/` never asks. An allow rule narrower than `*` (what an "always allow" answer adds, such as `echo review *`) never matches a command line with shell structure (`;`, `&`, `|`, `<`, `>`, a backtick, `$(` or a line break; quoting is not parsed), so such a command asks and is offered no always-allow answer.
- Session titles (2026-10-13): `fastModel` at the top of `providers.json` (a `<source id>/<model id>` pick, set from the Quick tasks section on the agent's settings page, `ProviderAction::FastModel`; the host refuses a pick that is not usable) names each session from its first prompt. `title.rs` sends the prompt's text blocks (attachments and images left out, at most 1000 characters) to that model in one call beside the turn, outside its cancel, with thinking off and at most 512 output tokens; the answer's first line, stripped of a `Title:` label, quotes, markdown marks and trailing punctuation and cut to 60 characters, goes out as `session_info_update { title }` and is logged as a `title` event. Only the first prompt triggers it (a session with a user message in its history never asks again, so a resumed or renamed session keeps its title); without a usable fast model, with a prompt that has no text, or when the call fails, nothing is sent and the host keeps the title it made from the prompt. This is what Claude (claude-agent-acp's `session-titles.js`, Claude Code's `generate_session_title`) and Codex (codex-acp's `TitleGenerator`, a side thread on `gpt-5.6-luna`) do for their own sessions. Verify with `tests/sessions.rs` (`the_fast_model_names_a_session_once_from_its_first_prompt`, `without_a_usable_fast_model_the_session_keeps_its_prompt_title`); not yet run against a real provider.
- Fast (2026-10-13): a model with a fast tier gets a third config option, `fast` (category `model_config`), which the composer shows as the Fast toggle in the effort header. It is a `boolean` when the client's `initialize` advertises `clientCapabilities.session.configOptions.boolean` (the engine does), else a `standard` / `fast` select; `set_config_option` takes a real boolean or either select value, and refuses `fast` for a model without the tier. Which models have it is `llm/fast.rs`: on Anthropic Messages Claude Opus 5, 5.5 and 4.8 (ids matched as prefixes, dots read as dashes); on the OpenAI formats GPT-6, GPT-5 (not the nanos), GPT-4.1, GPT-4o, o3 and o4-mini, a gateway prefix such as `openai/` ignored. `fast` on a model in `providers.json` (the model editor's Fast mode: Automatic / Offered / Not offered) overrides that list. On the wire a fast call is `speed: "fast"` plus the `fast-mode-2026-02-01` beta (added to any `anthropic-beta` list the source sends) on Anthropic Messages, and `service_tier: "priority"` on Chat and Responses (OpenAI renamed priority processing to Fast mode on 2026-07-30 and also takes `"fast"`; `"priority"` is the spelling older models and the gateways accept). The switch is session state (`state` records carry `fast`, restored on resume), kept through a model without the tier and applied again on the next one that has it; a turn reads it once at its start like the effort. A fast call's `request` record carries `fast`, with `fast.served` when the provider named the tier it served (Anthropic `usage.speed`, OpenAI `service_tier`, which is `"default"` when a rate limit downgraded the call), and its `cost` is twice the list price unless the provider reported a standard tier (twice is what Claude Opus 5 / 5.5 and gpt-5.6-sol list; OpenAI says other models may be up to 2.5 times). Turning it on or off is a `view` change (`changed: ["fast"]`), since Anthropic documents that a speed change invalidates the prompt cache. Sources: Anthropic's fast-mode reference and OpenAI's Fast mode guide, read 2026-10-13. Verify with `tests/fast.rs` and the `fast` tests in `llm/`; not yet run against a real provider.
- Sidekick (2026-10-21, `acp.rs` `sidekick_of`, `turn.rs` `sidekick_note`, `mcp/` `Hub::relist`): a client whose `initialize` declares `clientCapabilities._meta["acpira/sidekick"]: true` (the engine does) gets one more config option, `sidekick`, a select of the custom category `_sidekick`: `none` first, then every usable model as the model select lists it. While the pick's model has levels a second select follows, `sidekick_effort` (custom category `_sidekick_effort`, so no client takes it for the lead's effort): that model's levels, the one picked while the model offers it and the model's default otherwise; a sidekick pick keeps the level when the new model offers it, and the lead is never told of it. The engine runs the pick as the executor its `ask_agent` lists first to the root session (`transcript-pipeline.md`, Sidekick); this agent only keeps the pick and tells the model about changes to it. The `state` record carries `sidekick` and `sidekick_effort` (restored on load and resume; a pick whose model is no longer configured is kept but shows, and counts, as none). The tool table stays as it was first sent, since a changed tool definition invalidates the whole prompt cache (Anthropic): a pick before the first message marks the engine's `acpira` server to list its tools again before that message, so its `ask_agent` names the sidekick from the first request; a later pick, change or removal is told with the next message in a `<sidekick>` block in front (like `<mode>`), only outside Raw mode and while `acpira_ask_agent` is offered. A pick where acpira offered no `ask_agent` at all (no persona when the session started) lists acpira's tools once more instead; the other case where the table changes mid-session is a roster edit on the settings page, which acpira announces with `tools/list_changed` (`host-architecture.md`, Cross-harness subagents) and which costs that one prompt-cache rebuild. A reopened session's servers list their tools with the sidekick the engine holds for it, so it needs no note. Verified with `tests/sidekick.rs` (offered only to such a client, refused for an unknown model, the second listing before the first message, the note once per change with the table unchanged, the extra listing without `ask_agent`, the pick across a restart, the effort select following the sidekick's model and coming back with the session)
- The host labels the model options by source (`model_sources.rs`, the `acpira` arm), so two sources offering a model with the same name stay two rows in the picker.
- Slash commands and skills (2026-10-13): `session/new`, `load` and `resume` send `available_commands_update` inside the request (as Devin does; straight to the client, never recorded, since a replay would only repeat a stale list): `/compact` and `/goal` (goals, below), then every skill of `~/.agents/skills/*/SKILL.md` and the project's `.agents/skills/*/SKILL.md` (`skills::scan`: the project's wins on a name, dot-names and folders without a SKILL.md are skipped; the name is the frontmatter's `name` without whitespace, else the folder; `description` and `argument-hint` → `input.hint`). The list is read when the session opens, so a skill added later shows up on the next open, like Grok and Kimi. A `/name` anywhere in a prompt's text, at the start or after whitespace and ending at whitespace, punctuation or the end (the boundary the composer's pill uses, `skills::mentioned`), puts `<skill name path>` with the SKILL.md body (frontmatter off, `$ARGUMENTS` = the rest of that line) behind the user message, each skill once; only the prompt's `text` blocks are scanned, never an attachment, and the replayed `user_message_chunk` stays the text as typed. A session with any skills also offers the `skill` tool, appended behind the fixed set so the other specs keep their place: its description lists the skills with their descriptions and `skill { name }` returns the body plus the folder the skill's files are relative to (OpenCode's progressive loading); `read` permission on the SKILL.md, allowed by default. Without skills the tool set is exactly what it was. Verify with `tests/skills.rs` and the unit tests in `skills.rs`.
- Compaction (2026-10-13, `compact.rs`), the two kinds OpenCode has. Pruning (`compact::prune`, after a turn when `turn::prune_due` says so, 2026-10-15: automatic compaction on, the summary strategy picked, and the last call at 70% of the compaction threshold or more; a prune makes the next call miss the provider's cache from the first cleared result, measured below, which far from the threshold costs more than the smaller requests save, while near it the prune puts a compaction off; chunk compaction folds the finished turns' output itself, and with automatic compaction off only an overflow touches the history; `tests/compaction.rs` `old_tool_output_is_pruned_only_*`): walking back from the end past the last two user turns, completed tool results are kept until they hold 40k tokens (`PRUNE_PROTECT`, bytes / 4), every older one becomes `[Old tool result content cleared]`, and only when that frees 20k (`PRUNE_MINIMUM`), so the prefix (and the provider's cache) is left alone otherwise; error results and `skill` results are never cleared, and a result cleared earlier ends the walk. Summary compaction replaces everything but a tail with a summary written by the settings page's fast model when one is set (`fastModel`, read at the moment of the compaction; the excerpt is cut to that model's window), else by the session's own model, which also takes over in the same compaction when the fast model's call fails, including a reply cut off at the output limit (the `compaction` event then has `fallback { model, error }`; 2026-10-14, `tests/compaction.rs` `the_fast_model_writes_the_summary_*` and `a_summary_cut_off_*`, not yet run against a real model). A writer whose window would leave out the start of the transcript is passed over when a later one holds it whole (the event's `skipped`). Since 2026-10-16 the summary follows Claude Code instead of OpenCode's short anchored template, which wrote at most 4096 tokens with thinking off: each writer thinks as it would in a session (the session's model with the session's thinking and effort, the fast model with its own thinking setting and the level a new session on it would start with, `acp::default_effort`; the event records `effort`), with up to 32k output tokens for reasoning and summary (`SUMMARY_OUTPUT`, at most the model's limit and a quarter of its window; `max_tokens` goes out only when the limit is known), and no tools. The prompt is Claude Code 2.1.299's compaction prompt, its default `control` arm read from the binary's strings: an `<analysis>` pass, then nine sections in `<summary>` (Primary Request and Intent, Key Technical Concepts, Files and Code Sections with code, Errors and fixes, Problem Solving, All user messages, Pending Tasks, Current Work, Optional Next Step with verbatim quotes), reworded for a transcript of another assistant's work, with a note of what is carried beside the summary and a length cap of an eighth of the compaction threshold (1500 to 12000 tokens, given in words, `summary_words`); the `<summary>` block is kept and the analysis dropped (`summary_text`; an untagged reply is taken whole; the outer tags are preferably the ones standing on a line of their own and the summary ends at the last `</summary>`, so a tag quoted inside, such as an HTML `<details><summary>` snippet, no longer cuts off the sections after it). In the transcript the newest tool text (call arguments and results) stays whole within 200 KB, a third of the writer's room at most (`TOOL_TEXT_BUDGET`, Gemini CLI's 50k-token budget for function responses); older tool text is cut as below. Beside the summary the summary item carries, verbatim and independent of the writer (`compact::Carry`): the user's own words of every summarized message (`chunk::user_words`, the agent's notes left out, 4000 characters of each one's start and end), the newest within min(20k, threshold / 16) tokens with a count of the ones left out (Codex keeps 20k tokens of user messages after its compaction); the last to-do list (`todo` result) unless the tail writes a later one; up to five files that successful `read` / `write` / `edit` calls touched, newest first, re-read from disk at the compaction, 5k tokens each within min(25k, threshold / 10), a long one cut at a line with where `read` resumes, never one the tail touches, a binary one or one whose call failed (a read refused on its permission card stays out; Claude Code restores five files of 5k tokens); and the running request as before. A later compaction carries the earlier messages on and keeps the earlier to-do list and files where nothing newer replaces them. All of it is logged in the `compaction` event and kept in `SessionState::carry` / `Loaded::carry`, so a reopen rebuilds the same item. The item ends with Claude Code's resume instruction (continue without asking, do not acknowledge or recap the summary), and says the kept tail may already hold what the summary calls pending. How the others compare, read 2026-10-16: Claude Code forks the session itself (same model, thinking and effort, the whole native history, so the summary call reads the cache) and attaches the plan, invoked skills (25k tokens) and background tasks besides the files; Codex sends the native history to the same model with a short prompt and keeps the newest 20k tokens of real user messages plus the summary; Gemini CLI compresses at half the window, keeps the last 30% verbatim, asks for a `<scratchpad>` then a `<state_snapshot>`, and runs a second pass that critically evaluates the snapshot. The tail is the last two turns within a quarter of the usable window (2k to 8k tokens), the oldest split at a message boundary when it does not fit whole (never in front of a tool result), and when the last two turns are the whole conversation everything is summarized. A later compaction puts the previous summary (`<previous-summary>`) in front of the transcript and asks for one summary of both, the earlier record of what the user asked for copied over unchanged (Claude Code's `short_v2` wording), rather than starting over. It runs (1) on `/compact` (nothing of the command enters the history; with nothing to compact the agent answers "Nothing to compact yet."), (2) inside a turn when a call's `input + output` reaches the threshold, once that step's tool results are in, so the next call is the small one — the threshold is the host's `acpira.compactAtTokens` / `autoCompact`, which the host sends as `_meta["acpira/compaction"] { auto, atTokens }` on every `session/prompt` (`AcpSession::prompt_params`; other agents ignore it), capped at the window less the room for the model's output (`min(output, 32k)`), with the window and output limit read again before and after every model call (`turn::refresh_limits`, 2026-10-14), so a window edited in the settings mid-turn sets the next call's threshold instead of waiting for the next turn (the rest of the setup stays frozen for the turn); between turns the once-a-second `providers.json` check (`Server::push_controls`) sends the last `used` against the new window as a `usage_update`, so the meter follows the edit at once (`tests/compaction.rs`, `a_window_edited_*`); `auto: false` switches this trigger off — and (3) when the provider refuses a request as too long: the history is compacted once and the same step goes out again, a second refusal is the turn's error. A refusal counts as an overflow when its message says so (`compact::is_overflow`, HTTP 400 / 413 / 422 or an in-stream error; `OVERFLOW_WORDS` holds what the gateway answered on 2026-10-13: OpenAI "Your input exceeds the context window of this model", sometimes as HTTP 400 with OpenAI's JSON inside `error.message` and sometimes inside a 200 stream with `code: context_length_exceeded`; DeepSeek and GLM "The prompt is too long: N, model maximum context length: M"; MiniMax "context window exceeds limit"; Gemini "The input token count exceeds the maximum number of tokens allowed (N)"), or when the request itself was refused (HTTP 400 / 413 / 422, or an in-stream error typed `invalid_request_error` / `context_length_exceeded`, which the parsers now return as `LlmError::Rejected` and the turn never retries) while the agent's own estimate of it is at least 80% of the window (`compact::is_refusal`): the gateway's Claude routes refuse an oversized request on every format with only "There is an issue with this request, please try a different model." inside a 200 stream, and before `Rejected` existed that message was retried four times as a service error. After an overflow the running turn is kept whole when it fits half the window (OpenCode replays the last user message), so a pasted file in the new prompt survives; otherwise, and on a threshold compaction whose tail starts after the running turn's prompt, the prompt's text (images left out, at most 32 KB) follows the summary verbatim inside `<request>` and is logged as the `compaction` event's `request`, so the task is not left to a paraphrase. In the transcript the summary is written from, a tool result keeps 2000 characters and says how much more the assistant saw, and a user message keeps 8000 characters of its start and of its end (`USER_EDGE_CHARS`). The client sees `compaction_update` in_progress then completed / failed and a `usage_update` with the estimated size afterwards, which the real count on the next call replaces; the host's own turn-boundary `/compact` (`protocol-gotchas.md`) still works as a fallback since the agent advertises the command. The view from then on is a user message holding `<conversation-summary>` in front of the kept tail; the mode note is announced again on the next prompt, since the one the model saw was summarized away. Verify with `tests/compaction.rs` (threshold with the tail kept, `/compact` and a reopen, overflow and retry, auto off), the unit tests in `compact.rs` (prune plan, tail selection, the prompt, the policy) and `scripts/probe/builtin-compaction.ts [--model <source>/<model>] [--at TOKENS]` (the sidecar path with a copy of the real `providers.json` in a temp root: pong, a 40 KB read that crosses the threshold inside the turn, a recall question, `/compact`, a project skill mid-sentence, the `skill` tool; spends real calls). Both summaries read the excerpt's cut tool result as the tool having returned less ("truncated at line 30, the code is not yet visible"), hence the explicit note on a cut result in `serialize` (not re-run since). `--scenario prune` (`claude-haiku-5.5`, 2026-10-13): five 49 KB reads in one turn, two small turns, then a `prune` event cleared the two oldest results (25.7k tokens by the bytes / 4 estimate) and the next call's real input fell from 127k to 78.7k, so Claude's tokenizer counted the cleared text at about twice the estimate; that call read only the system prompt and tools from cache (5788) and the one after it 78721, i.e. the cache breaks once per prune; the model, shown `[Old tool result content cleared]`, read `a1.txt` again and answered from it. `--scenario overflow` (`deepseek-v4-flash`, 2026-10-13): a 904k-token turn of attachments, then a turn that took the request to 1,071,067 tokens; DeepSeek answered HTTP 400 "The prompt is too long: 1071067, model maximum context length: 1048576", the agent compacted with the running turn kept whole (`tail` 1) and the retry (171k) answered the code word at the end of the new attachment. - Chunk compaction (2026-10-14, `chunk.rs`), the `chunk` strategy of the Bkm016/opencode fork (MIT, `packages/opencode/src/session/chunk.ts` and the loop in `session/prompt.ts`, read 2026-10-14), picked on the settings page (Agents → Acpira → Context → Compaction; `compaction: "chunk"` in providers.json, `ProviderAction::Compaction`, the default `summary` written as no entry) and read when a compaction runs. It calls no model. Every finished turn becomes a chunk: a range of the session log's `item` events (`from..to`, ordinals; `Store` counts them, a reopened store starts from `Loaded::logged`) that the model sees as its user messages (mode / MCP notes and skill bodies left out; one over 2000 tokens as its start and end with a `history_list` offset) and an assistant message with the final reply and the files written; a turn that did not end on a reply without tool calls is `interrupted` and also keeps its last three tool outcomes and a one-line log of the earlier steps. The view is the summary item (if a summary ran before), then `chunk::render`: the checkpoint's rules and index in front of the first chunk's input, newest chunks whole up to `Budget::target` (OpenCode's 20k, a fifth of a smaller usable window), older ones as excerpts up to `hard` (24k), the rest archived as one line of their request each (240 tokens for the first, 80 for the others, 1500 in all), then the items after the last chunk. Estimates count a CJK character as a token (`chunk::tokens`). Triggers are the summary's: `/compact` seals every finished turn; the threshold and an overflow seal the turns before the running one and, when the estimate still takes 70% of the threshold (after an overflow: always), fold the running turn's earlier steps into a `partial` chunk whose summary is a work-state index built from the tool calls (changed files with their last diffs, errors marked resolved when the same file or command later succeeded, reads, searches, commands with exit codes and last lines), cut at a step boundary so the verbatim rest fits half the threshold, the latest step always verbatim; on a threshold compaction both shares are scaled by the provider's count of the call that crossed it over the estimate of the same request (`chunk::in_estimate_units`, held within 0.5 to 3 times), since the estimate is the chunks' own and a tokenizer may count far more: on 2026-10-23 `gemini-4-argon` counted 403k for a request of source reads estimated at about 280k, and the fold aimed at 200k kept 286k; when the turn ends the next seal widens it to the whole turn under the same id. Nothing to fold, or a log that does not match the history, falls back to the summary (on `/compact`, nothing to fold says "Nothing to compact yet."); after an overflow a second refusal is summarized. A summary takes the shown chunks in and clears them from the view. The `compaction` event has `strategy: "chunk"`, the `chunks` it added or changed (with their rendered texts, so a reopen renders without the folded items), `tail` and `budget`. `history_grep { pattern, chunk_id?, case_sensitive?, head_limit? }` (fixed string, 20 hits with two lines around each) and `history_list { chunk_id, offset?, limit? }` (80 lines) read a chunk's items back from the log (`store::history`, prune never applies there) as numbered lines `USER` / `ASSISTANT` / `ASSISTANT_TOOL` / `TOOL_OUTPUT` / `TOOL_ERROR`, reasoning never shown; they are offered behind `question` while chunk compaction is picked (`modes::TOOLS_CHUNKED*`), under the `history` permission, allowed by default. Left out from OpenCode's: the pre-send drop of the oldest visible chunks at 80% of the window (the selection is made when sealing), `source=task` evidence, and per-message references for long text in the running turn. Verify with `tests/chunk.rs` (`/compact` without a model call and the tools reading the folded read, a reopen rendering the same checkpoint, a threshold folding a turn into a work-state index and the partial chunk widened afterwards, an overflow chunked then summarized, the tool set) and the unit tests in `chunk.rs`. Not yet run against a real model.
- Steering (2026-10-14, `steer.rs`): `_session/steering`, the extension claude-agent-acp and codex-acp implement, takes a message into the running turn, so the queue's Steer button and the composer's mid-turn send (`acpira.steerQueued`) work on this agent too. - Rewind (2026-10-22, `store.rs` `Store::rewind`, `acp.rs` `Server::rewind`): a history edit goes back to just before the edited message, like Cursor, instead of rebuilding the history or continuing with a superseded note. Goal tool calls show no tool row (the goal rows stand for them, and an `other` row would make the workspace gate treat the turn as touching anything). - SSH hosts (2026-10-24, `remote.rs`): a session request with `_meta["acpira/remote"]` names a host. - Failed model calls are retried in the turn (`turn.rs`, `MAX_ATTEMPTS` 4): network errors, broken or stalled streams, an `error` event inside a 200 stream and HTTP 408 / 409 / 425 / 429 / 5xx; a rejected key, another 4xx or an in-stream error naming the request or the context is not. The wait is `Retry-After` (at most 60 s) or 1, 2, 4 s. A stream without an event for 300 s counts as stalled (`ACPIRA_AGENT_STREAM_IDLE_SECS` overrides it; Codex's stream idle default). Before a retry the failed attempt's tool rows are marked failed and its partial text is dropped from what the model gets (the streamed chunks stay on screen); a `session_info_update` carrying an AIR `sessionFailure` warning ("Retrying <source>, attempt N of 4") puts the attempt on the working label, cleared when the stream resumes. Each attempt is its own `request` record, `attempt` from 2 on. An Anthropic stream that breaks while a tool call is streaming after another one finished is not a failure: the reply keeps the finished calls (blocks stream in order, so a started block means the ones before it are complete), the unfinished call's row is marked failed, the turn runs what it has, and the `request` record carries `cut` with the provider's message (`Assembler::salvage`). A reply that ends with no text and no tool call, at most reasoning, is retried the same way unless its stop is the output limit or a refusal (`turn::empty_reply`); the attempt's `request` record keeps its usage and stop beside the error, and once the attempts run out the turn fails with "the model ended its reply without any text or tool call" instead of ending as if answered. ## Web tools

Added 2026-10-14, after a session in which the model told the user it had no way to open a link, then reached it with `curl` once pushed. Modelled on OpenCode's `webfetch` / `websearch` (read in `packages/opencode/src/tool/` at 4d900b2f); every other harness Acpira drives ships its own.

- `webfetch { url, format?, timeout? }` GETs the URL from the agent process (browser user agent, `Accept` preferring markdown; a Cloudflare `cf-mitigated: challenge` 403 is retried once with an `acpira/<version>` agent, as OpenCode does). Bodies over 5 MB are refused; the timeout defaults to 30 s, at most 120. HTML becomes markdown through `html.rs`, a single-pass converter written for this (no HTML crate): scripts, styles, `nav`, `footer`, `aside`, forms and `hidden` content are dropped, `<main>` (else the `<article>`s) is taken alone when it holds at least half the text, links and images are made absolute. The answer starts with `URL:` (the final one after redirects), `Title:` and `Description:` (the description meta tags, which is where X and other script-built pages keep their only server-side text), and a page with under 200 characters of text gets a note that it is probably built by scripts. `format: text` drops the markdown marks, `html` returns the page as served. Text, JSON, XML and the like come back unchanged; anything else is saved as `outputs/<call id>.<ext>` and only its path and size go to the model. The model's copy goes through the usual output budget.
- `websearch { query, count? }` calls a hosted search service with one MCP `tools/call` over HTTP (no `initialize`, as OpenCode does): Parallel's free `https://search.parallel.ai/mcp` (`web_search`, the session id as `session_id`, `PARALLEL_API_KEY` as a bearer token when set) or Exa's `https://mcp.exa.ai/mcp` (`web_search_exa`, `EXA_API_KEY` in the URL when set). Exa goes first when `EXA_API_KEY` is set, else Parallel; `ACPIRA_WEBSEARCH_PROVIDER=exa|parallel` overrides, and the other one is tried when the first fails. Exa's keyless endpoint reports a rate limit as a successful result with `_meta["ai.exa/rateLimited"]`, which counts as a failure (it was rate-limited on the first try of 2026-10-14 and answered later the same day). Parallel's JSON results are rendered as markdown, at most 2500 characters of excerpts each. The description carries the current year, as OpenCode's does.
- Jina (2026-10-14): the agent's settings page has a Web search section with a Default / Jina select; picking Jina shows a key row below it. `ProviderAction::WebSearch { backend, key? }` writes `webSearch: "jina"` at the top of `providers.json` (absent means default) and the key to `secrets.json` as `acpira.web.jina` (an empty key deletes it, an absent one keeps it; the default backend takes no key); the view carries `webSearch` and `webKeys`, never the key. With Jina picked and a key stored, `websearch` calls `GET https://s.jina.ai/?q=…&num=…` first (`Authorization: Bearer`, `Accept: application/json`, `X-Respond-With: no-content`, 10 s), then the free chain; a failed Jina call is named in the result (`Jina: … failed`), and a 401 / 403 says the key was refused. Without a key `s.jina.ai` answers 401, so Jina is never used keyless. The agent re-reads both files on change, so the next call picks the setting up. Verified by the contract test in `test/providersContract.test.ts` and the config test; the Jina call itself has not run with a real key.
- DeepSeek (2026-10-18): a third backend, `deepseek`, on the same select. Its row below the picker is "Search through": DeepSeek's own API (then a key row, stored as `acpira.web.deepseek`) or any model source with a key, written as `webSearchVia` in `providers.json` (`ProviderAction::WebSearch { via }`: absent keeps it, empty clears it, an unknown id is refused, deleting the source clears it). A source is called at `<its API root>/v1/tools/search` with its own key (`tools_search_url`: `https://host/v1` and `https://host` both map there, a full endpoint keeps its root); the Asgard gateway serves that path with DeepSeek's request and answer shape and merges DeepSeek with Jina behind it. A named source that is gone or has no key turns DeepSeek off rather than sending queries to DeepSeek's API. The call is `POST { query, count }` with a bearer key, 10 s; results are `results: [{ title, url, date (RFC 3339), summary, snippet }]`, rendered like Jina's with the summary cut to 800 characters. DeepSeek declines some queries (political ones among them, measured 2026-10-18) with HTTP 200 and an empty list, so an empty answer is a failure and the next backend is asked. Order: the default backend uses no key; a keyed pick goes first, the other keyed backend follows when it is set up (Jina's stored key, or DeepSeek through its source or key), then the free ones. Verified by the host test in `providers.rs`, the config test, `deepseek_results` / `tools_search_url` in `web.rs`, the contract test, and `search_deepseek` run once by hand against api.deepseek.com and the gateway (2026-10-18); not yet inside a real turn.
- Both are `fetch` calls on the wire (as claude-agent-acp sends WebFetch and WebSearch), so the webview renders their markdown; `rawInput.url` is the fetch row's target. They are read-only and run side by side with other reads.
- Permissions: `web` (public URLs and every search) is allowed in the defaults. A URL whose host is `localhost`, a single label, a `.local` / `.internal` / `.lan` / `.home` / `.corp` / `.intranet` / `.home.arpa` name, a numeric form or a loopback, private, link-local, shared (100.64/10) or unspecified address is `web-local` instead, which asks (allowed under `full`); "always allow" covers that origin for the session. Such a fetch goes without the user's proxy. Redirects are followed by hand, at most five, and each hop is checked: a public call that redirects to a private address, or whose host resolves to one, is refused with a message rather than followed. The resolution check is a lookup before the request, so a name that changes its answer between the two (DNS rebinding) is not caught.
- The base prompt (version 4) has one line under Tools: open a link with webfetch, search with websearch, and try before saying a page cannot be reached.
- Verify with the tests in `tools/web.rs` (URL joining, private addresses, arguments, search answers, and a local server for redirects, pages, JSON, a saved PNG, a 404 and a refused private address) and `tools/html.rs`. Fetched by hand through the functions on 2026-10-14 (acpira 1.10.1 on macOS, behind the user's proxy): the X post from that session (title and description carry the post's text, the body its author, time and view count), the ACP site (served markdown for the `Accept` header), a Rust std page (51 KB, spilled), a Chinese blog index and a GitHub repository (redirected from `sst/opencode`); `websearch` answered through both Parallel and Exa. Not yet run in a turn against a real model.

## Plan mode

Plan mode allows writing only the session's `plan.md`, whatever the approval level, and asks before a command or a non-read-only MCP tool up to `full`, which runs them without a card (2026-10-16, `Mode::rules` takes the level). A `full` command can still touch the disk through the shell — the write rule is on the `edit` permission, not on `bash` — so the reminder names the commands that change nothing and forbids one that writes, deletes or installs; the level widens the card, not what the model is told to attempt. The model writes the plan there with `write` / `edit`; `exit_plan` takes no arguments (a `plan` argument is still accepted from models that pass one) and sends the plan through `session/request_permission` with `_meta["acpira/planApproval"]` and a `switch_mode` tool call carrying `rawInput.plan` and `planFilePath`, so the host's existing plan card takes it unchanged. The tool call is titled `Exit plan mode` from its first update, which the webview localizes. Approving switches to Agent mode inside the same turn and the model carries the plan out with Agent mode's tools. Refusing ends the turn and the plan stays in place for revision. The mode change reaches the model as a reminder in the next user message, never as a system prompt change.

The Plan reminder (`modes.rs`, 2026-10-14) follows Cursor's plan mode, as the `cursor-plan` skill records it. It asks one or two questions with the `question` tool first when the request is unclear, and otherwise states assumptions in the plan. The plan opens with a `# Title`, which the card shows as its title. Sections come in a fixed order, as many as the task needs: scope, current problems with file and line evidence, target design, changes by file, verification, stages, out of scope. Structure goes into mermaid blocks under a short syntax rule list, and the plan card renders them with the chat's Markdown. Unless the plan is a single step, its steps go on the to-do list with `todo` before `exit_plan`, all pending and in order. The to-do bar shows that order while the user reviews the plan, and the approval's tool result tells the model to work through the list item by item. The steps stay in the model's `todo` call, not in the plan file; there is no frontmatter `todos` block for the engine to parse. Not yet checked against a real model.

## Raw mode

Raw mode (2026-10-18, `modes::RAW`, the composer's Raw / 原始模式 chip with the `Unplug` glyph) talks to the endpoint with nothing of the agent's own around the conversation. `turn::setup` sends no tools (no built-in ones, no skills, no MCP servers), and its system prompt is only `rawSystemPrompt` from `providers.json` (the settings page's Raw mode section, `ProviderAction::RawSystemPrompt`, read at the start of every turn; a blank or missing prompt sends no `system` block on Anthropic Messages, no system message on Chat and no `instructions` on Responses). The base prompt, family variant, prompt overrides, AGENTS.md and environment block stay out. So do the variant's default sampling and thinking: the model's own settings, effort and Fast still apply. Entering Raw mode puts no `<mode>` note in front of the prompt. Agent mode right after it gets none either, since its system prompt arrives with it; Plan mode after it gets its usual note. The MCP note waits for the first turn of a mode that offers MCP tools, and `/skill` mentions stay as typed. The request records the prompt as variant `raw`, with the digest of the settings text. What still reaches the model: attachments in the shape every mode gives them, and a steered message's `<steer>` note, which is how the history recognizes it. Raw mode never compacts on its own: no automatic summary, no pruning, and an overflow is the turn's error. Only `/compact` writes a summary, never chunks, because chunks point at history tools Raw mode lacks. `session/set_mode` to `raw` is refused (-32602) once the history holds a tool call or a tool result. Anthropic refuses a request whose messages hold `tool_use` / `tool_result` without `tools`, a constraint recalled from the API, not re-verified against it. The host then drops the pick and shows the error. Raw → Agent / Plan is always allowed. Verify with `tests/raw.rs`; not yet run against a real provider.

## Questions

The `question` tool (`tools/question.rs`, 2026-10-14) puts one to four questions on the host's question card. Each question has a short `header`, up to eight `options` with `label` and `description`, and `multiple` for a multi-select. Without options it takes a free-text answer. The turn runs it itself, like `exit_plan`. It sends `elicitation/create` with `mode: "form"` and the tool call's `toolCallId`, which is Kimi's dialect: one property `qN` per question. A choice question carries `oneOf`, or `items.anyOf` when it is a multi-select, plus `_meta["acpira/allowOther"]`, which `questions.rs` reads like Devin's `cognition.ai/allowOther`, so the user can type an answer of their own. The call's rawInput gives the card the model's own labels and descriptions. An `accept` goes back to the model as `Q:` / `A:` lines, with `(no answer)` for a gap. A `decline`, or an `accept` with nothing in it, is a skip: the model goes on with its own judgement. A `cancel` ends the turn like a rejected action. Either way the row shows no output card, since the question card holds the answers. The tool needs no permission and comes after `websearch` in the tool list, so the earlier specs kept their place. A client that does not declare `clientCapabilities.elicitation.form` still gets the tool, which keeps the prefix the same for every client. There the call fails with a note telling the model to ask in plain text. The base prompt (version 5) and the Plan reminder point the model to the tool. Verified with `tests/question.rs` (answers, skip, close, no form support) and the engine scenario `builtin_agent::the_question_tool_*` against the real binary, golden `builtin-question`. Not yet checked against a real model.

## Fewer steps

Added 2026-10-18. A step costs about 9 s of model time on GPT-6.1 Sol and Gemini 4 Argon against a median of 2 ms for a read, so the tools take more work per call instead of running faster. Counted on the 2026-10-15 Argon eval logs (181 steps) and 48 local session logs (1018 steps), scripts in the git-ignored `output/step-analysis-2026-10-18/`: 14% of the eval's steps only moved the to-do list on and 14% ran a command right after an edit, and in the local logs GPT-6.1 Sol and Gemini 3.8 Flash made one call per reply in 96 to 99% of their steps, mostly a single read or search.

- `todos` on `read`, `write`, `edit` and `bash` (`tools::TODO_RIDERS`, `todo::rider_property`; `turn.rs` calls these riders): the whole list, set while the round is prepared, before any of its calls runs. The turn shows it as a `todo` row of its own, a `tool_call` titled `todo` with `rawOutput.todos` as the todo tool's row carries, so the host's to-do bar takes it unchanged, above the call's row: the row the stream opened for the reply's last call is retitled `todo` (`tool_call_update` with title, kind and rawInput; the host recomputes the verb on every packet, `normalize.rs` `a_streamed_row_retitled_todo_becomes_the_to_do_row`) and the call gets a new row below it. On an earlier call of a reply the streamed rows stay put, since a new row would land below the calls after it, and the list's row follows the round's rows (`tests/riders.rs` `a_list_on_a_call_before_another_*`), and puts `To-do list updated (N pending, N in progress, N completed).` in front of the call's result. A list that does not parse is named there instead and the call still runs. An empty list, `null` or `""` is no update (models fill optional arrays with empty ones), so only the todo tool clears the list. Any built-in tool's `todos` is taken, never an MCP tool's, whose arguments are its server's. The todo tool's description no longer says "completed as soon as it is done" and points at the parameter instead. Compaction carries the last list from the calls' arguments, the todo tool's or a rider's, so a pruned todo result no longer hides it.
- `then_run` on `edit` and `write`, SoL-Pi's Action Fusion: a command run once the change is made, prepared like a `bash` call (default timeout, the session folder). It gets a command row of its own, opened after the edit's row completed, under the rules a `bash` call would have: under `ask` and `auto-edit` it has its own card and its own "always allow" pattern. The call's one result is the change's, then `$ <command>` and the output, with `[exit code N]` last when non-zero; the call itself is not an error then. It is not run, with a line saying why, when the change failed, was not allowed, or left every file as it was; on another tool it is refused with a note. A rejected command ends the turn after the round like a rejected call, the change stays made and the result says so. A turn cancelled while the command runs records the change as made and the command as cancelled (`SessionState::landed`, read by `settle`), not the whole call as cancelled. The chunk index counts the command like a `bash` call. The plan (P1 `p1-edit-tools`) kept it off until an eval; the paired eval below found it used and helpful on GPT, Gemini and DeepSeek, and it is on for every family, since there is no per-family switch.
- `edit` across files: each `edits` item may carry its own `path` (default: the call's `path`). There is one change per file, in the order the files first come up, a file's edits in order, all or none: at prepare time, and again at run time, where a file that changed meanwhile gets its edits again and one that no longer takes them fails the call before anything is written. Files are matched by their canonical path, so `a.txt` and `nested/../a.txt` (or a symlink to it) share one change instead of the later write dropping the earlier edits. A write that fails partway puts back the files already written, newest first; any that cannot be restored are named in the error and keep their diff on the card. One card shows a diff per file; every file goes through the edit rules and the config guard, and a refusal names the file denied. The result reads `Edited 2 files: a.rs (2 changes), b.rs.`
- `read` ranges and an even budget: `path` and `paths` take `file:N-M` and `file:N`, also `file:N:` copied from a grep hit, unless a file of that very name exists; `offset` / `limit` on the call win over a range in `path`. A range of the same file is another window, while a bare repeat of the first file is still dropped. The windows of one call split the 50 KB budget evenly from the smallest up, a window under its share being read whole; before, the first took what it needed and the rest what was left, and 17 of 63 multi-file reads in the local logs ran out. A window that reaches the end of its file no longer offers a next offset. Each window is a location of its own with the line it starts at (`line`, left out for line 1, which the host takes as a whole-file read), so the row shows `a.rs:120` and opens the file there; before, a range written into the path showed no line at all.
- `read` on an image (2026-10-24, after a session in which the model told the user it could not look at any local picture: `read` answered "binary file" and `show_image` only shows the user): a PNG, JPEG, GIF or WebP file, known by its signature rather than its extension, comes back as the picture, the way Claude Code's and OpenCode's `read` do. The tool card always shows it when it is at most 5 MB encoded (`tools::mcp::MAX_IMAGE_BYTES`); the model gets it as the tool result's image, on the same path an MCP tool's images take (`Action::Read { images }` is the turn model's `takes_images`, `turn::images_of`), when the model takes images, the picture is at most 5 MB encoded and 8000 pixels on a side (Anthropic refuses more, and a refused image would stay in the history and fail every later request), and the call's images stay within 16 MB together. The text result names the file, format, size in pixels (read from the header: PNG IHDR, GIF screen, JPEG SOFn, WebP VP8 / VP8L / VP8X) and KB, and either says the image is attached or why it is not shown, so a text-only model is told it missed one. An AVIF, BMP, HEIC, ICO or TIFF file is refused with a hint to convert it to PNG or JPEG first. An animated GIF (2026-10-25) goes, when the model takes images, as a PNG sheet of its frames (`frames.rs`, the same sheet the engine sends for an attached GIF, see `transcript-pipeline.md`), on the card as well, and the text adds the frame count, duration, grid and sample times; with a text-only model the card keeps the GIF itself (`an_animated_gif_is_read_as_a_sheet_of_its_frames`). Verify with `tools/read.rs` (`image_headers_give_their_size`, `an_image_file_is_read_as_its_picture`) and `tests/turn.rs` (`reading_an_image_file_shows_the_model_the_picture_when_it_takes_images`); header parsing checked on 2026-10-24 against real files written by `sips`, ffmpeg and Pillow (baseline / progressive / EXIF JPEG, GIF, lossy / lossless / alpha WebP). Not yet run against a real model.
- `read` on a PDF (2026-10-24, `tools/pdf.rs`): the file is known by `%PDF-` in its first KB and read as text page by page with pdf-extract 0.12 (a workspace dependency added for this, with lopdf under it; lopdf's own extraction turned CJK pages into mojibake), each page under a `--- page N ---` line. For a PDF, offset / limit, a range in the path (`doc.pdf:3-5`) and the `pages` argument (`3-5`, `3`, `10-`, Claude Code's name; it sets the window of `path` when offset / limit are absent) count pages, and the header reads `(PDF, 14 pages)` or `(PDF, pages 3-5 of 14; continue with offset 6)`. Only the pages asked for are parsed, and parsing stops once their text passes the 50 KB budget. A page whose text is mostly control characters, U+FFFD or private-use code points (fonts without a usable encoding) or that has none says so in its place; a window where no page has text answers with how to render pages to PNG (pdftoppm, mutool, magick, sips) and read them, not with an empty read. Text is cleaned of control characters, runs of spaces inside a line and runs of blank lines. Encrypted files are opened with the empty password (most only restrict copying); a parser panic is reported as an unreadable file: caught in process where panics unwind (tests, debug builds), while shipped builds, which abort on a panic (2026-10-26), parse in a child process of the same binary (`acpira pdf-pages FIRST LIMIT MAX_BYTES`, the PDF on stdin, the answer as JSON on stdout, ended after 120 s), checked by `acpira-host/tests/pdf_child.rs`. Reads now run on a blocking thread, since a large PDF parses for seconds. `webfetch` points saved images and PDFs at `read` instead of a command. Checked on 2026-10-24 against real files: a 14-page Chinese NotebookLM export read whole in 44 KB (0.5 s in a debug build), an 8-page one with U+0001 word separators read cleanly, a 13-page file without a text layer and an 18-page one whose first pages use fonts without encodings got their notes. Verify with `tools/pdf.rs` (a PDF built with lopdf in the test) and `tools/read.rs` (`a_pdf_is_read_as_its_pages`). Not yet run against a real model.
- Interactive commands (2026-10-24, `tools/jobs.rs`): `bash` with `interactive: true` (also `tty`) starts a background job in a pseudo terminal (portable-pty, the crate the engine's terminals use; 160x48, `TERM=xterm-256color`, `NO_COLOR=1`, `LANG` set when missing, `GIT_TERMINAL_PROMPT=0`; PowerShell without `-NonInteractive`), so prompts, REPLs and installers that ask behave as for a person. `job` with `input` (also `chars`, Codex's `write_stdin` argument) types into it, `\n` sent as a carriage return (Enter for line readers and key readers alike), then waits until the job has been quiet for 400 ms, has ended, or `wait` seconds (default 3) passed, and answers with what it printed since the last check. A job started without `interactive` refuses input, and an ended one says the input was not typed. Output is stripped of terminal control sequences as it arrives (state carried across chunks) and redrawn lines read as their last state at report time (carriage returns and backspaces). Typing needs no permission card, as for Codex's `write_stdin`: approving the command approved talking to it. The row is titled `Type into job N: <input>` with escapes visible. Plain background jobs keep their null stdin and pipes. Driven by hand on 2026-10-24 through the job table: Python 3.14 and Node 22 REPLs answered `42 done` and `[ 2, 4, 6 ]` with clean prompts. Verify with `tools/jobs.rs` (`an_interactive_job_runs_*`, `terminal_output_reads_*`) and `tests/turn.rs` (`an_interactive_command_asks_once_*`). Not yet run on Windows (ConPTY) or against a real model.
- `grep` `context` (also `-C`, Claude Code's name for it, and `context_lines`; at most 50): each file's matches come under its path as `line: text`, the lines around them as `line- text`, windows that touch merged and the others parted by `--`. ## MCP servers

Added 2026-10-14 (`src/mcp/`, `tools/mcp.rs`); before, `mcpServers` was dropped, so neither the engine's own `acpira mcp` nor the user's shared servers reached the model, which then ran MCP servers by hand through `bash`.

- Sources: whatever `session/new`, `load` and `resume` carry in `mcpServers`, which is what the engine sends every agent: its `acpira mcp` (`show_image`, `show_widget`, `workspace_hooks`, `ask_agent` with the relay) and the shared servers of `~/.agents/mcp.json` and the project's `.mcp.json` (`host-architecture.md`, shared config). The agent reads no MCP file itself. Stdio entries (no `type`, or `stdio`; `env` as `[{ name, value }]`) and `type: "http"` (streamable HTTP, `headers` the same shape) are taken; `sse` is skipped with a note, and since `initialize` does not advertise it the engine does not send one either.
- Lifetime: every server starts connecting when the session opens (or is revived from its file by `load` / `resume`; a session still open in the process keeps its servers). A turn waits for the ones still starting, each bounded by 30 s (`START_TIMEOUT`, Claude Code's `MCP_TIMEOUT` default), so `session/new` returns at once and the tool set is complete from the first request. Stdio children run in the session cwd, stay in the agent's process group (the engine's group kill or Job object ends them with the agent), are killed when the agent closes (`Server::close`), and their stderr goes to the agent's log as `[mcp <name>] …`. An HTTP server on this machine or a private network is reached without the user's proxy, as `webfetch` does; `Mcp-Session-Id` and the negotiated `MCP-Protocol-Version` go on every request, a 404 on a request that carried a session id starts a new session and repeats the request once, and closing sends the session's `DELETE` in the background.
- The client says `clientInfo.name: "acpira"`, offers `roots` (answering `roots/list` with the session cwd and `ping`), and no sampling or elicitation. `acpira mcp` lets an `ask_agent` call of this client wait 25 min like Claude Code's; the agent's own bound on a call is 30 min (`CALL_TIMEOUT`), and cancelling the turn stops waiting without telling the server (the engine's server does not handle `notifications/cancelled` either).
- Tools: a server's `tools/list` (every page) becomes `<server>_<tool>` with characters outside `[A-Za-z0-9_-]` turned into `_` (OpenCode's naming; the engine recognizes `acpira_show_image` and `acpira_ask_agent` by it), behind the built-in tools and the `skill` tool, in the order the servers were given, so the prefix stays the same between calls. A name over 64 characters, or one taken by a built-in tool or an earlier server, is left out with a log line. The input schema goes as the server wrote it, with `$schema` removed and `type: object` / `properties` filled in when missing; the server validates the arguments. A `notifications/tools/list_changed` makes the next turn list that server again, and the changed tool set is a `view` change: the view holds the tool names and `toolsDigest` (name, description and parameters of every tool, in order), so a relisting that keeps the names and rewrites a definition, as acpira's `ask_agent` after a roster edit, is recorded as `tools` too (2026-10-22, `tests/sidekick.rs`). Name correction also finds an MCP tool written another harness's way (`blockbench.screenshot`, `mcp__blockbench__screenshot`) or in another case.
- The model is told, in the first user message of the session (an `<mcp>` block in front, like the mode note, never the system prompt), the servers' `instructions` under `## <server>` and every configured server that is unavailable (failed to start, or skipped) with the reason, so it can tell the user instead of improvising. The block is sent again only when its text changes; a session reopened in a new process hears it once more.
- The tool card: titled with the model's name for the tool (`<server>_<tool>`, kind `other`), and from its first `tool_call` on, its updates and its permission card carry `_meta["acpira/mcp"] { server, tool, title }` (the configured server name, the tool's own name, its `title` or `annotations.title`), which the engine shows as "Call <Server>" with the title as the target (`transcript-pipeline.md`, MCP tool rows).
- Permissions: `mcp-read` (a tool its server marks `readOnlyHint`) is allowed by default and such calls run side by side with other reads; `mcp` (any other tool) asks unless the approval level is `full`, with "Always allow <tool> in this session" on the card; the engine's own tools (one rule per name in `acpira-shared/src/host_tools.rs` `ALL`, the server marks only `ask_agent` read-only) are allowed by default, so `show_image` needs no card. Plan mode asks for every `mcp` tool except the engine's, unless the approval level is `full`. Since 2026-10-26 the rule names each tool instead of `acpira/*`: a tool a plugin adds to the same server asks like any other MCP tool, in Plan mode too (`permission.rs` `engine_rules`, `host_mcp.rs` `every_tool_served_is_on_the_engine_s_list`).
- Results: text blocks are joined and go through the output budget; an embedded text resource becomes `<resource uri=…>`, a link `[name](uri)`, audio and binary resources are named; `structuredContent` stands in when there is no text; `isError` marks the row failed. Images go on the tool card always, and to the model when it takes images (`input` has `image`), at most 8 per result and 5 MB each (Anthropic's limit), otherwise the model is told how many it did not get. In the history a tool result carries them (`images`, logged in the session file as `{ image, mime }`); Anthropic gets them inside the `tool_result`, Chat and Responses as a user message after the round's last result (`[An image returned by the tool call <id>]` then the images), since their tool outputs take text. Pruning clears a result's images with its text; compaction counts an image as 1000 tokens. A server's `notifications/progress` during a call replaces the card's content with its latest line until the result arrives.
- Verified with `tests/mcp.rs` (a streamable HTTP server on a local port: tool naming and order, the instructions note, a read-only call without a card, its image after the result on Chat, a card with always-allow, another harness's tool name, a text-only model, an unreachable server and a skipped `sse` entry), the unit tests in `mcp/` (entries, naming, results, a forgotten HTTP session and progress from an event stream, error answers) and `tools/mcp.rs`, the Anthropic and Responses body tests, and the engine scenario `builtin_agent::the_engines_own_mcp_server_reaches_the_model_and_show_image_shows_the_picture` (the real `acpira mcp` over stdio: its tools offered, the receipt back, a show-image row with the picture). `pnpm probe acpira --mcp --cmd "<repo>/rust/target/debug/acpira agent --home <tmp>"` showed the marker server getting `initialize`, `notifications/initialized` and `tools/list` (acpira 1.10.2, 2026-10-14).

## Session log

`store.rs` appends one JSON event per line, each with `t` in epoch milliseconds. Nothing is rewritten; what the model gets is a view projected from `item` events.

| Event | Holds |
|---|---|
| `session` | First line: id, cwd, format version (`FORMAT` 1) |
| `item` | One conversation entry as the model sees it; a tool result an MCP server returned images with carries them as `images` |
| `update` | A `session/update` as sent, for replay; streamed text and terminal output merged per block |
| `state` | Mode, model, effort and the Fast switch at the start and after each change (one held before the file exists is written when it is opened, also into a resumed session's file) |
| `prompt` | The system prompt whenever it was composed: variant, version, digest, text |
| `request` | One per model call: model, source, format, prompt variant / version / digest, `policies` (`outputBudget`, `compaction { auto, threshold }`), usage (input, output, cacheRead, cacheWrite, reasoning), `cost` at list prices, `ms`, `attempt` on a retry, then `stop` or `error`. A call cut off by a cancel is recorded with stop `Cancelled`. A provider that reports 0 prompt tokens gets an estimate from the request's size (about four bytes a token, a thousand per image), marked `usage.inputEstimated` |
| `view` | `changed` (any of `model`, `prompt`, `tools`, `fast`), `from`, `to`: the request prefix changed between two calls |
| `title` | The fast model's naming call: `model`, `ms`, usage and `cost` like a `request`, then `title` or `error`. It is not a `request`: it shares nothing with the conversation's prefix |
| `compaction` | A summary compaction (with `strategy: "chunk"` a chunk compaction instead: `reason`, `ms`, `chunks` added or changed, `tail`, `budget`; the view becomes the earlier summary, the rendered chunks and the tail): `reason` (`manual` / `threshold` / `overflow`), `model` (the one that wrote it), `effort` (the level it thought at), `fallback` (the fast model that failed first, with its error), `skipped` (a writer passed over because its window would cut the transcript), `ms`, usage and `cost` like a `title`, then `summary`, `tail` (how many of the latest items were kept behind it) and what the item carries beside the summary: `messages` (the user's own words, oldest first) with `omitted` (how many earlier ones the budget left out), `todo`, `files` (`{ path, text }` as restored) and `request` (the running turn's prompt carried verbatim, when the summary took it in); or `error`. `store::load` projects it: the view becomes the summary item plus the last `tail` items, later `item` events follow |
| `prune` | The tool results a prune cleared: `calls` (their ids) and the `tokens` freed; `store::load` clears them again |
| `goal` | The session's goal (`goal::Goal`: objective, status, budget, tokens and time used, the idle-turn count) after a change, `null` once cleared; the counters are written once per turn. The last one is the goal; a rewind keeps it |

- The file is created on the first event that needs it; the `session` and `prompt` prelude waits until then, so an unused session leaves nothing behind.
- `session/load` replays the recorded updates, then serves the session. `session/resume` serves it without a replay; the engine uses resume when reopening (checked by the reopen scenario below, host log `session/resume ok`).
- `session/list` pages 50 sessions per call with a cwd filter and a numeric `nextCursor`. A session's title is its `title` event's when it has one, else the first line of its first message; a listing parses the file only up to the first message and then only lines that start as a `title` event.
- A session that is neither open nor on disk answers `-32002`.
- A line cut short by a crash is skipped on read.

## Requests, prompt caching and cost

- The base prompt (`prompt/builtin/base.md`, version 6: version 5 plus the lines on `todos`, `then_run`, edits across files, read ranges and grep context; version 5 pointed at the question tool, version 4 added the web tools line, version 3 several changes to one file in a single `edit` call) is original text: working habits, tool use, honesty (a command is reported only after a tool ran it, even when its output is predictable), care with irreversible actions and the user's uncommitted changes, and answer style.
- The system prompt is composed once per session from the base, a family variant, the user's and the project's same-name files under `.agents/acpira/prompts/`, AGENTS.md and the environment. It is composed again only when a model switch selects another variant.
- Between two ordinary calls the request prefix stays byte for byte: earlier messages, tools and model do not change. Anything that does change it is a `view` event in the log. The engine scenarios assert exactly this pairing.
- Tool output above 2000 lines or 50 KB (OpenCode's limits) is saved under `outputs/`; the model gets a preview, what was cut, and the path. Command output keeps head and tail. The tool card shows the whole output.
- `catalog::complete` fills a model's missing context and output limits from the catalogue (marked estimated) and supplies its prices. `Cost::estimate` bills cache reads and writes at their own prices when the catalogue has them, else at the plain input price. The figure is an estimate at list prices, not the bill.

## Model discovery

`llm/discover.rs` serves the settings page through the host (`providerProbe` → `providerProbed`, kinds `models`, `check`, `test`, `local`), on the host's blocking pool with its proxy-aware HTTP agent.

- Metadata comes in three tiers. First the fields the endpoint reports. Then the catalogue, matched by `model_key` (gateway prefixes such as `deepseek/` stripped, case and separators normalized). Then defaults: a 128000-token context and text-only input. Every value not reported by the endpoint is named in `estimated`; the model editor names it in a note until saved, and the turn loop never sends an estimated value as a limit. Effort levels likewise come from the catalogue only; a model the endpoint flags as reasoning that the catalogue has no levels for (one newer than the catalogue) gets `DEFAULT_EFFORTS` (`low` / `medium` / `high`, marked estimated) wherever a level reaches the wire: always on Responses and Anthropic Messages, on Chat only for a family whose switch takes a level (`complete_for`). Without levels such a model's thinking stays `auto` and no request turns it on: `gemini-4-argon` on the asgard Responses gateway answered 31 requests with 0 reasoning tokens until levels were lit by hand (2026-10-14). The model dialog says so under the levels row when none is lit.
- Listing shapes handled: OpenAI-style id-only lists, OpenRouter's full metadata (`context_length`, `top_provider.max_completion_tokens`, `architecture.input_modalities`, `supported_parameters`), Anthropic's paged list (`?limit=1000&after_id=`, `x-api-key` plus `anthropic-version`, and a bearer token too when the host is not api.anthropic.com), Gemini's native `models/` names with `inputTokenLimit` / `outputTokenLimit`, LM Studio's `/api/v0/models` (read first; the loaded window wins over the maximum) and Ollama's `/api/show`. The asgard gateway's OpenAI-style list (recorded 2026-10-14) adds camelCase limits (`contextLength`, `maxOutputTokens`), `limit.context` / `limit.output`, a `capabilities` object (`context_length`, `max_output_tokens`, `supports_reasoning`) and the booleans `reasoning` / `supportsReasoning` / `supportsThinking`; all are read, but no effort levels are listed (`settings.extendParams: ["thinkingLevel"]` names the parameter only). Embedding models are dropped. Unverified: apart from the asgard entry, these shapes in `tests/discover.rs` are written from each server's public documentation, not recorded off a wire.
- Ollama's context from `/api/show` is the model's trained window, not the `num_ctx` the server actually serves, so it is always marked estimated.
- `check` lists the models (free); `test` makes one real call with `max_tokens` 16 and thinking off; `local` probes Ollama and LM Studio on their default ports with short timeouts and no proxy.
- No vendor presets: the settings page adds every source as a custom endpoint (name, API format, base URL or full endpoint, key), with the request URL it produces shown under the URL field. A URL ending in `/chat/completions`, `/responses` or `/messages` is used as typed (`fullUrl`) without asking; a text button on that line flips between appending the format's path and using the URL as typed, and a saved source keeps its choice. All sources share one card that opens with the search row, as on every agent's model list; each source is a group in it under a rule (source mark, name with a key-status dot and the model count, the URL under it, an edit pencil) over compact model rows and a last "Add model" row; Add model opens a dialog list that fetches the endpoint when it opens, adds on click and takes a typed id, and a newly saved source opens it at once. The source form (added or edited) is a dialog too, and Remove lives there. There is no source switch; a source switched off earlier shows a grey dot and a Turn on button. Ollama and LM Studio still come from the `local` probe, saved with `preset` `ollama` / `lmstudio` (no key field). The family comes from the model id, then the base URL (`family.rs`, `vendor_api_roots_select_their_family`); a vendor `preset` in an older `providers.json` still counts as a hint.

## Tests

- `cd rust && cargo test -p acpira-agent`: the agent against the scripted model server over an in-process ACP client. Covers streaming, both wire formats, tools and permission cards, name correction, the output budget, Plan mode, questions, the session log round trip, discovery, compaction (`tests/compaction.rs`, chunks in `tests/chunk.rs`), skills (`tests/skills.rs`), MCP servers (`tests/mcp.rs`), goals (`tests/goal.rs`) and steering (`tests/steer.rs`; `mock::Reply::Held` holds a reply and `support::Answer::Wait` a card until the test lets them go).
- `cargo test -p acpira-host --test engine builtin_agent`: the engine drives the real `acpira agent` binary against the scripted server in eight scenarios: an edit behind a permission card, a Plan approval that builds in the same turn, a question answered on the question card, a cancel before the first chunk, a reopen that resumes, the engine's own `acpira mcp` called through MCP, a message steered into a command round, and a goal set from the dock that the engine continues until the model marks it complete. Every scenario checks the prefix rule against the session log. The edit, plan, question, cancel and steer transcripts are golden output in `test/fixtures/engine-builtin.json` (Unix only, temp paths written as `/acpira`, `/repo` and `SESSION`), rendered by `test/builtinAgent.test.ts`; `ACPIRA_UPDATE_FIXTURES=1` records an intended change.
- The agent reads the user-level `~/.agents/AGENTS.md` of whoever runs the tests into its system prompt. No assertion depends on it.

## Windows

The bash tool runs `powershell.exe -NoProfile -NonInteractive -Command` there, never the `bash.exe` on PATH (on the test machine that is WSL's launcher in `System32`). Windows PowerShell 5.1 writes piped output in the OEM code page (936 on a Chinese system), which came out as mojibake; every command is now prefixed with a switch of `[Console]::OutputEncoding` (and `$OutputEncoding`) to UTF-8, which native commands started from it follow because they share its hidden console. Tool results show paths with forward slashes, since joining a model's `src/util` with a file name gave `src/util\b.rs`. Cancelling kills the command's whole tree through `taskkill /T /F`.

Verified 2026-10-10 on Windows 11 (PowerShell 5.1.26100.8115, code page 936), with the agent crate's test binaries cross-built for `x86_64-pc-windows-gnu` and run over SSH: all unit tests (including the Windows-only Chinese output and cancel tests in `tools/bash.rs`) and every integration suite against the scripted server passed. The engine scenarios in `builtin_agent.rs` were not run on Windows.

## Real providers

Verified 2026-10-11 (acpira 1.9.1) through an OpenAI-compatible gateway, one `openai-chat` source with `scripts/probe/agent-host.ts acpira --home DIR` (DIR holds `providers.json` and `secrets.json`; a `--home` root is kept after the run). `--shell --attach` and `--write --plan` run separately, since the click-through approver stands down under `--write` / `--plan` until the scenario has answered its own card.

- `minimax-m3`, `gpt-6-luna` and `glm-5.3-flash` pass every check: pong, text attachment, a `bash` row with its plain-text output, an edit behind a permission card, a plan card titled `Approval needed: Exit plan mode` linked to its plan document and rejected without a write. Streaming text and reasoning, tool calls, usage and cost records all come through.
- Honesty: right after a "reply with only that word" turn, asked to run `echo acpira-shell-ok`, `glm-5.3-flash` answered without running it 2 times in 15 under the version 1 base prompt and 0 in 15 under version 2 (a command with unpredictable output: 10 of 10 ran under both).
- Caches: `gpt-6-luna` and `glm-5.3` report cache reads on a repeated prefix; `glm-5.3-flash` only once the prefix passes roughly 2.5k tokens (none at 2.3k, 2176 at 3.1k). Entering Plan mode kept `gpt-6-luna`'s cache (1792 read on the first Plan call; 0 before the tool set was shared between modes).
- This gateway streams `minimax-m3` usage with every prompt count at 0 (its non-streamed answers carry real counts), so those calls are logged with `inputEstimated`.
- Anthropic Messages: `claude-sonnet-5.5` on the gateway's `/v1/messages` passes the same checks, picks the `claude` variant, and reads the cache from the second call on (about 4100 of 4200 input tokens). Signed thinking blocks replay correctly within a tool loop (a captured request replayed with and without them both succeeded).
- The same endpoint ends a Claude stream with an SSE `error` event (`response stream interrupted`, `api_error`) right after a `tool_use` block that streams no `input_json_delta`, i.e. a call with empty input (2026-10-11, `claude-sonnet-5.5` and `claude-sonnet-5-5` alike, both answered by the same upstream). It cut every reply opening with an argument-free `list` call, alone or next to another call, so a plain retry failed the same way 4 times running; `disable_parallel_tool_use` changed nothing. Replays of such a request with `list.path` required (the model then passes `"."`) or without `list` succeeded 2 of 2 each. Hence `list` requires `path`, and a cut after a finished call keeps that call (above). The other harnesses never hit it: none of their Claude calls had empty input. The earlier Plan-mode failures (a `write` then `exit_plan` with only an optional `plan` parameter, and a `list` call after thinking) fit the same cause.

- OpenAI Responses (`openai-responses`, 2026-10-11, the same gateway): `gpt-6.1-sol` streams reasoning items with `encrypted_content` when the request has `store: false` and `include: ["reasoning.encrypted_content"]`; replaying a turn's own output items (reasoning, message, function calls, without `id` and `status`) is accepted, and cache reads start at the second call (with `prompt_cache_key` set to the session id; not tried without it). The response echoes `parallel_tool_calls` and each tool's `strict` back, so they are sent explicitly (`true` and `false`). `swe-2` (Devin's model) answers Responses with encrypted reasoning too and reports cache reads there, while its Chat answers carry `signature_delta` and tool ids like `read:0#…`. `gemini-3.8-flash` works on both formats, with `reasoning_content` on Chat and reasoning items without `encrypted_content` on Responses; no thought signature is exposed, so nothing of its reasoning can go back.
- DeepSeek's own API (`https://api.deepseek.com`, `deepseek-flash` = V4.1 Flash, 2026-10-11): thinking is on by default; usage carries real `prompt_cache_hit_tokens`. The docs say a tool-calling turn needs every earlier `reasoning_content` back or it answers 400, but requests without any came back 200 in every case tried, so the `deepseek` family's current-turn echo is safe either way.
- Thinking off on the same gateway's `opencode-go` routes (2026-10-14, `glm-5.3-flash` and `deepseek-v4.1-flash`, raw requests): both think by default, and neither `thinking: { type: "disabled" }` (what the family table sends on Chat), the Responses request without `reasoning` (what `Thinking::Off` sends there), `enable_thinking`, `chat_template_kwargs` nor `reasoning.enabled: false` turns it off. Only `reasoning_effort: "none"` on Chat or `reasoning: { effort: "none" }` on Responses does: DeepSeek then answers with no reasoning at all, while GLM moves its reasoning into the answer text (a summary request came back as 12 to 16 KB of English analysis before `## Objective`, 14 of 14 times). With thinking left on, a summary at the 4096-token cap came back empty or cut off in 13 of 14 GLM calls and 7 of 14 DeepSeek calls, and `compact::summarize` takes a cut-off text as a summary (it ignores the stop reason). Replaying seven real compactions of two sessions, graded blind by `claude-opus-5.5`: DeepSeek with effort none finished in 7 to 13 s and scored 6.9 of 10, with thinking 7.8 in 11 to 35 s; GLM with thinking 8.8 on the runs it completed but 1 on the others, in 24 to 91 s; the sessions' own `gemini-4-argon` / `gpt-6.1-sol` summaries 6.3. Since 2026-10-16 the summary call thinks and has 32k output tokens, and a reply cut off at the limit falls back to the next writer instead of being taken (`compact.rs`); the replay above was not repeated on the new prompt.
