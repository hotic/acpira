# Agent quirks: Antigravity

How `agy acp` behaves on the ACP wire, with the version observed ("source" / "binary" = read from the shipped binary). Other CLIs and cross-agent notes: `agent-quirks.md`.

## Antigravity

- Runs `agy acp` (agy 1.5.9). The older `agy_acp_server` package (Registry `antigravity-acp`) offers Claude / GPT only to allowlisted `clientInfo.name`s.
- Login: keychain item `gemini` / `antigravity`, or a file in the gemini dir under SSH; saved accounts: `accounts/antigravity.rs`. 1.5.16's `agy acp` (macOS) reads the keychain despite `SSH_CONNECTION` (`-p` does not); only `AGY_CLI_FORCE_FILE_TOKEN_STORAGE` keeps it on the file.
- A prompt comes back as `user_message_chunk` before the reply.
- Failed turns are `end_turn` with the failure as its own chunk, `\n⚠ <text>\n`; `vendors/antigravity.rs` cuts it into the turn error. A `session/cancel` mid-stream (1.5.12) leaves the same shape, `⚠ The stream was interrupted. …`, a note for its model: dropped on a cancelled turn (`cancel_note`). Gemini models share one quota bucket, Claude has its own.
- Restore: `session/resume` does not replay. An unknown id answers `-32603 Failed to read session <id>; …` while `session/load` succeeds empty, so that message counts as gone (`errors.rs`).
- MCP calls: `name` `mcp_<server>_<tool>`, title `Run <name>`, kind `other`; the server ends at the first `_` (`tool_kind.rs`). A later session request of one process whose entry differs (its env included) registers `<server>_<8 hex>` beside the first (1.5.13), skipped by both name readers; the hub's grant is one per session, thread and depth so Acpira's entries stay the same (`RelayHub::env`). `agy` injects `toolSummary` into every MCP tool schema, asks `request_permission` on every MCP call (read-only too), omits `toolUseId` in `tools/call` `_meta` and result `content` on `tool_call_update`.
- MCP tool budget (1.5.16): the tools of every registered server share one declaration budget (some 50 KB of schema text). Over it the smallest schemas are declared first and the rest are cut: not declared, and unreachable over ACP (no `call_mcp_tool` there; `_meta` `antigravity/alwaysLoad` does not exempt a tool). A second registration of a server counts again, so a large project server plus a duplicate cut Acpira's remote tools down to the smallest few. A large project server alone still cuts Acpira's biggest tools (`ask_agent`, `show_widget`).
- Session instructions and hooks (1.5.9): `session/new`, `load` and `resume` accept `_meta.antigravity.systemPrompt` (`{ append }` or replacement string). `_meta.agy.disabledTools` does not disable built-in tools, whereas `<cwd>/.agents/hooks.json` `PreToolUse` exit 2 blocks them cleanly.
- Background commands: a `run_command` still `in_progress` at `end_turn` runs on; its exit wakes the model for a whole agent run with no prompt running, and nothing on the wire says the run is over. 1.5.12 streams the exit (`tool_call_update`) and the run live. 1.5.9 sent neither: only `session/list` `updatedAt` moved, and `session/load` on the live process replayed both. A load restarts the stream, so replays read while a run streams show its text twice. `session/late_reply.rs` keeps the row as a background task and shows the run as one detached turn, ended when the stream and the time stand still, reading replays only for a process that has streamed nothing; nothing watches after a restore.
- Steering (from 1.5.0, verified on 1.5.12): no `_session/steering`; a `session/prompt` sent mid-turn is the steer. The running prompt answers `end_turn` at once with its own usage, the new one owns the rest of the turn until it answers; the steer is never echoed. A prompt sent while a permission or question card waits is refused (`antigravity::steer_bounced`), so steers hold until the card is answered. A stopped steer stays in agy's conversation: it is never queued again.
- `/compact` (1.5.13): nothing on the wire but a `usage_update` with the pre-compaction size and an empty `end_turn`; agy's transcript logs the checkpoint. `antigravity::compacted_silently` makes that a finished compaction with stale usage. Auto-compaction waits out an owed late reply (`after_prompt`).
- `/goal` (1.5.17 binary and wire): `available_commands_update` advertises `goal`, backed by a Stop hook (`goal_stop_hook.go`) that forces continuation until the model emits `<!-- GOAL_COMPLETE -->` or `<!-- GOAL_CANCELLED -->`, with neither `_meta.jetbrains.air.goal` / `_session/goal` nor `session_info_update` snapshots. While `goal::actions` is absent, `AcpSession::synthesizes_goal` tracks `set` / `clear` host-side from `/goal` prompts and markers (`vendors/antigravity.rs`), clearing via a hidden prompt or prompt-steer (`GOAL_CANCEL_PROMPT`); native extension metadata takes over automatically once `agy acp` advertises it. Unverified live against a real `/goal` turn.
- Sandbox (1.5.9, macOS): `auto` never asks and runs commands in agy's own sandbox whatever `enableTerminalSandbox` says, with the `.git` of a folder that is a repository at session start read-only (`git pull` / `commit` fail); its monitors refuse a `BypassSandbox` retry without a permission request. `default` and `accept-edits` ask per command and run it unsandboxed, so full access rides on `accept-edits`.
- Questions (1.5.12): `ask_question` goes over `elicitation/create` (`q<n>` + `q<n>_other` companion with no `_meta`, option-less questions as `q<n>_other` only, boilerplate `The agent has … question(s).` message). Unverified: MCP load failures, a prompt sent or `session/cancel` while a late reply is being written, the Windows install directory.
- Background auto-update (1.5.14 binary): both `agy acp` and `agy -p` spawn a detached `--bg-updater` that runs `agy --version`, flashing a console window on Windows. `AGY_CLI_DISABLE_AUTO_UPDATE=true` (exact lowercase `true`) skips it (unverified live on Windows).
- Subagents and `/swarm` (1.5.16 binary and live session): no ACP subagent lifecycle updates; child tool calls stream on the root session id under `toolCallId` `<child_uuid>:<inner_call_id>` (including after `end_turn`, so `late_live` skips them). Root `swarm { action: "add" }` and `invoke_subagent` open `Session` nodes in place (`subagent_tree/antigravity.rs`), and `session/antigravity_subagents.rs` polls `<gemini_dir>/antigravity-cli/brain/<session_id>/.system_generated/{subagents/*.json,swarm/{members,plan}.json,swarm/board.jsonl}` for names, task summaries, briefs, board posts and `SUBAGENT_STATE_KILLED` / `killed` completion. Non-swarm children (`invoke_subagent`, `image-generator`, `self`) stay `SUBAGENT_STATE_ALIVE` after finishing a turn so the parent can still `send_message` them; their completion is read from `<brain>/<child_uuid>/.system_generated/logs/transcript.jsonl` ending on a tool-less `DONE` `PLANNER_RESPONSE` with an empty `messages/undelivered/` inbox, and a later wake-up opens a fresh node gated by the prior `idle_step`. Child permission and elicitation requests carry the same `<child_uuid>:` prefix and route to the child node. Unverified live against a fresh `agy acp` turn (unit-tested against recorded wire shapes and disk files).
- Own tools (1.5.16 transcripts): `update_steps`, the swarm board (`read_board`, `post_message`, `swarm_wait`), `swarm status` / `title`, `send_message`, `ask_question`, `manage_subagents` and `manage_task` (background tasks, `TaskId` `<conversation>/task-<n>`) are bare `Run <name>` rows of kind `other`; `agy_tool` (`normalize/tool_kind.rs`) names them. `update_steps` sends the whole list every call (`steps: [{ title, status: pending | in_progress | done }]`) and answers a bare `OK`, so it is the one to-do tool whose input becomes the list. Left generic: `update_focus` (never seen called) and `schedule` (`verb.wakeup` would drive Claude's wakeup tracking).
- Orchestrators (1.5.16 binary prompts and one live turn): `model` options `gemini-pro-orchestrator-neon` / `gemini-pro-orchestrator` (Carbon) / `-argon`, named `Orchestrator (<lead>)`; the Antigravity app's Opus-led one is not offered over ACP. A planning model (plan mode on) and a faster execution model take turns in the one conversation: the planner's `exit_plan_mode` (`rawInput.plan`, the whole plan) hands over, the executor's `enter_plan_mode` (`rawInput.reason`) hands back when stuck, at a periodic review or when a user message arrives (the CLI asks it with a hidden `[plan review due]` step), and the planner then hands over again or ends. Both are plain `tool_call`s, title `Run <tool>`, kind `other`, no permission request, no mode or model update. Nothing else on the wire tells the executor's thoughts, calls and text from the planner's; its text ends the turn as the reply. Each step in `brain/<session_id>/.system_generated/logs/transcript.jsonl` names its `model`: the orchestrator id for the planner, `gemini-flash-worker-agy` for the executor (the binary's `orchestrator-model-roles` lists executors `gemini-4-hydrogen` / `claude-sonnet-5-5`). The relay rounds: `subagent_tree/orchestrator.rs`. Not yet seen live: `enter_plan_mode`, a periodic review, a steer mid-execution.
