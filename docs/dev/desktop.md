# Desktop app

`apps/desktop/` is the standalone desktop app: the webview bundle (`dist/webview`) and the Rust engine outside any IDE, in a Tauri 2 shell (tauri 2.12; WKWebView on macOS arm64, the platform packaged and checked first; WebView2 on Windows and WebKitGTK on Linux, see their sections), with the session column on the left over every project as its baseline. It is a shell like the VS Code extension and the IntelliJ plugin; all engine behaviour stays in `rust/`. Plans live outside the repository (`~/.agents/plans/acpira-desktop-client_7d50b6df.plan.md` for the app, `acpira-desktop-tauri_a0f11ebc.plan.md` for the move to Tauri); this file records what is built and verified. Until 2026-10-25 the shell was Electron 45 (never released; removed that day): entries dated before then were checked in it, and its numbers below are the baseline the Tauri shell was measured against. The WebKit gate (bench, protocol probes, what WKWebView changed in the page) is `docs/tauri-webkit-gate.md` (local).

## Layout and commands

- Two parts. `rust/crates/acpira-desktop` (a `rust/` workspace member with no Tauri dependency, so `cargo test --workspace` and clippy cover it) holds everything that needs no window: the sidecar client (`client.rs`: outbox until `helloOk`, every view re-attached on reconnect, a replaced connection's late output dropped by generation, preview leases asked again; `wire.rs` relays host messages verbatim as `RawValue`), the engine endpoint and launch (`engine.rs`, the same key as `packages/engine-client/engine.ts`), the locator, `confine`, the editors, the login environment, the shell's settings store, the shared settings poll, window state, the IDE settings seed, the terminal script, the context API, platform requests (`platform.rs` `handle_request` over a `Platform` trait), the menu tree in the app's language (`menu.rs`), preview addresses and browser history (`browser.rs`), the page HTML and routes (`page.rs`), and the single-instance lock (`single_instance.rs`). `apps/desktop/` is a Cargo workspace of its own (Tauri needs webkit2gtk on Linux, which the `rust/` gates must not) and not a pnpm package; it holds only the window side: `src/app.rs` (the main process), `chat_window.rs`, `browser.rs`, `menu.rs`, `mac.rs`, `win.rs` and `linux.rs` (the system calls Tauri lacks, behind `os.rs`), `serve.rs`, `commands.rs`, `smoke.rs` and `init.js`.
- In `apps/desktop/`: `cargo build` (add `--features smoke` for the smoke hook), `cargo clippy --features smoke --all-targets -- -D warnings`, `cargo fmt --check`; `node scripts/smoke.mjs` and `node scripts/package.mjs` are below, `node scripts/icon.mjs` renders `icons/icon.svg` into `icons/icon.icns` and a 32 px `icon.png` (`rsvg-convert`, `iconutil`). The PNG is only Tauri's default window icon, which tauri-codegen embeds in the shell as raw RGBA (the former 1024 px one was 4 MiB of the binary) and macOS never shows; the Dock, Finder, About and a dev run's Dock icon all read the icns. The page needs the root `pnpm build` (`dist/webview`, `dist/picker.js`; a checkout's binary finds them two levels above `apps/desktop`) and an engine: `ACPIRA_SIDECAR_BIN`, else `dist/sidecar/<os>-<arch>/acpira` from `pnpm build:sidecar`, else `rust/target/debug/acpira`.
- Development / smoke switches: `ACPIRA_HOME` (data root; use a temp one, a real `~/.acpira` gets `categories.json` `projects` seeded), `ACPIRA_DESKTOP_USER_DATA` (the app's own settings, window state, browser history, and the log as `logs/desktop.log`; otherwise `~/Library/Application Support/com.hotic.acpira.desktop` and `~/Library/Logs/com.hotic.acpira.desktop`), `ACPIRA_DESKTOP_PICK` (folders, path-delimiter separated, that answer the folder dialog in turn without showing it), `ACPIRA_DESKTOP_BACKGROUND=1` (an accessory app: no Dock icon, never activated, windows ordered behind every other window, WebKit rendering while covered through `_setWindowOcclusionDetectionEnabled: NO` and App Nap off, no notification or failure dialog; so a smoke never interrupts whoever uses the Mac), `ACPIRA_ENGINE=stdio` (an attached engine instead of the persistent one).
- A first launch copies `settings.json`, `windows.json` and `browser-history.json` from the Electron app's profile (`~/Library/Application Support/Acpira`) when it has none of its own.

## How it fits together

- Main process (`src/app.rs`): single-instance lock (`flock` on `<profile>/instance.lock`; a second launch hands its arguments over `instance.sock` and exits), one `SidecarClient` to the persistent engine (`acpira serve`, socket key with `shell: 'desktop'` so no IDE window shares it), any number of `ChatWindow`s. Quitting only disconnects; macOS keeps the app and its connection when the last window closes. Platform requests run on the main thread and answer through a oneshot.
- Hello: `env.projects: true` and no `cwd` (the engine's project-shell rule, `docs/dev/host-architecture.md` "Project shells"), `hostLanguage` from `NSLocale preferredLanguages`, `blobBase: acpira-app://localhost/blobs`, the settings snapshot, the capabilities in `platform.rs` `CAPABILITIES`.
- Each window is an engine view with host `editor`. Page traffic goes `init.js` → `acpira_post` → `client.send`, host messages come back through the page's channel, verbatim. `viewFocus`, `pickFolder` and the tool panel's `panel*` messages stay in the shell, as `viewFocus` does in `apps/vscode/src/bridge.ts`.
- `acpira-app://localhost/` (an asynchronous custom scheme: a standard, secure origin, `isSecureContext` true, no back entry): a window starts on `/blank` so WebKit's 60 fps cap (`PreferPageRenderingUpdatesNear60FPSEnabled`, private, turned off through `WKPreferences _setEnabled:forFeature:` and checked before each call) applies before the real page loads; `/index.html` is generated (`page.rs`: the VS Code page's CSP with `acpira-app:` as the source, `window.__acpira = { host, font, sessionLinkBase: 'acpira://session/', shell: 'desktop' }`, the body scheme class from the system appearance), `/desktop.css` the `--vscode-*` variables, `/webview/*` and `/blobs/*` files through `confine` (decoded, realpath inside the root, so `..`, `%2e%2e` and symlinks out are refused), read off the main thread, every response `cache-control: no-store` so a reload takes a new bundle. A `/webview/*` name with no file of its own is served from its `<name>.zst` sibling, decompressed, with the original name's type (`Route::Packed`): the packaged app stores `assets/` that way (below); blobs never fall back.
- Transport (`src/init.js`, injected into the top frame of `acpira-app:` pages only): up, one `invoke('acpira_post', <raw JSON array>)` at a time carrying everything posted meanwhile, so the shell sees messages in posting order (separate invokes may overtake each other); down, a Tauri `Channel` whose messages carry an index the page reorders by. `window.__acpiraApi` has `postMessage`, `getState` / `setState` (sessionStorage), `readClipboard` (the terminal's paste: WebKit's `readText` shows a paste bubble; `packages/ui/vscodeApi.ts` `readClipboardText`) and `pathForFile`. Theme changes call `window.__acpiraTheme(dark)`, which toggles the body class.
- Drag and drop: Tauri's own handler is off (`disable_drag_drop_handler`): it answered every drag itself (wry returns `true`), so the DOM saw no Finder drop and no internal drag either (the session list's reordering). WKWebView gives a dropped file's name and bytes but not its path; the paths of a Finder drag are read from the system drag pasteboard (`Apple CFPasteboard drag`, file URLs, `acpira_drag_paths`) when the drag enters the page, and `pathForFile` matches them by name at the drop (the column's folder drop).
- Settings (`acpira-desktop/src/settings.rs`): `<profile>/settings.json` holds only the settings that follow the window (session list side and scope, editor selection), flat keys without `acpira.`, tmp + rename; a first launch writes `sessionListPosition: left` and `sessionScope: all`; a file that does not parse is moved to `settings.json.broken`. `writeSetting` writes there and the change goes back as `settingsChanged`. Every other setting is shared with the IDE shells in `<ACPIRA_HOME>/settings.json` (2026-10-23, see the shared settings entry in `host-architecture.md`): the engine writes it, the shell reads it for the menu language, the browser window's look, the page font and "open files with" (`shared_settings.rs`, polled once a second by mtime, size and inode).
- Login shell environment (`login_env.rs`): `$SHELL -i -l -c` printing `env -0` between marks, 10 s timeout (process group killed), `PWD` / `OLDPWD` / `SHLVL` / `_` / `TERM_SESSION_ID` / `ELECTRON_*` dropped; merged into the engine's command environment. It runs on a thread of its own before `client.start()`, while the first window loads.
- Platform actions (`CAPABILITIES` in `platform.rs`): `writeSetting`, `openExternal`, `revealInOS`, `openResolvedFile` and `openPlanDocument` (through "Open files with", below; a plan sent only as markdown is written to a temp file first), `openInEditor` (the session in a new window; the session menu says "Open in new window"), `openBrowser` and `runInTerminal` (below), `toast` (into the page, below), `notify` (quiet while a window shows the session; chime to the last focused page; a `UNUserNotificationCenter` notification whose click brings the session up, which needs the app bundle). `searchFiles` is not declared: the engine walks the session's project.

## The page's desktop layout (2026-10-23)

`window.__acpira.shell === 'desktop'` makes `App` pass `desktop` to `Shell` (`packages/ui/desktop.ts` `DesktopContext`, read by `SessionList` and `Header`). Styles in `packages/ui/styles/desktop.css`: tokens unlayered, so they beat the density's `--hdr`; rules in `@layer components`; anything that collides with a call-site utility is switched at that call site.

- Frame. The column lies on a darker window canvas (`--canvas`, `--bg-0` mixed 78% with black; 55% read as a hole beside the page) with no fill or rule of its own. Below `--session-dock-min` the column becomes a page over the whole window, on the canvas as well (Narrow window, below); as the first drawer it had no fill, and its list was drawn straight over the conversation (until 2026-10-23). The chat is a sheet (`data-sheet`) inset `--sheet-inset` 8 px from the window's top, right and bottom edges, `--r-lg` corners. The window's title row (`chat/DesktopFrame.tsx` `TitleRow`: back, forward, then the column's toggle, as Codex orders them) is pinned at the window's top-left, absolute over the column or the sheet's header, so it never moves when the column folds or a page changes; the column leaves an empty strip under it (`TitleSpace`). It and the sheet's header (title plus the project's name, no rule) share one 44 px line (`--hdr` pinned) and are the window's drag regions (`data-drag-region`). Before 2026-10-23 the toggle lived in the column and a second one appeared in the header once it folded, which read as the button jumping.
- Traffic lights. macOS: `TitleBarStyle::Overlay` with a hidden title and `traffic_light_position(17, 32)` (`apps/desktop/src/app.rs`; Tauri measures 9 pt lower than Electron's `trafficLightPosition { x: 17, y: 23 }`, which put them at the same place). The window has no title bar of its own: a press on a `data-drag-region` starts `start_dragging` from `init.js` (controls excepted), and a double click does what `AppleActionOnDoubleClick` says. Measured on macOS 27 with an AppKit window: the buttons are 14 × 14 pt, 23 pt apart (9 pt gaps), so the lights span x 17–77. Their centre line is y 30, which is the title row's (8 + 44 / 2). The first light's centre is x 24, which is the column's row icons at the default (airy) density. `--lights-w: 84px` leaves about 15 px to the first button's icon. With no column beside the sheet (hidden, or a narrow window), the header starts after the title row (`--title-w`, `--sheet-lead`).
- Column. The title row's toggle folds the column away and brings it back (in a narrow window it opens the list page, `data-session-toggle`). It is kept in webview state `desktopColumnHidden`, which only the docked column reads: a narrow window's list page and ⌘K open whatever it says (until 2026-10-23 a column folded in a wide window left the drawer zero wide and inert once the window narrowed, and ⌘K unfolded the absent column instead of opening the drawer). The VS Code drawer's scrim is `bg-scrim/45`: the theme clears Tailwind's own palette, so the `bg-black/20` it had generated no CSS and dimmed nothing; the desktop page dims the sheet instead. Its width eases only while it moves (`data-moving` on the column itself: React writes a child's attributes before its parent's, so a flag only on the root landed after the width had changed and the opening jumped). The content keeps its open width (`--column-w`) and is clipped instead of re-wrapped. New session (⌘N) and search (⌘K) are rows on top. Categories are hidden. Each project lists its latest 5 sessions (the active one always among them), and the rest sit behind one row that names how many, their agents and the most urgent state. Project rows have no count and no "current" badge; their hover shows the pen (new session there) and "…" (reveal, copy path, remove from list), and right-click opens the same menu. A gear at the foot holds settings, appearance and help, built like a row's lead so it stands under the row icons; its glyph is a size up (`--foot-icon` 18 px) and its hover fill square (36 px), since at the rows' 14 px it looked lost. Back / forward walk the sessions this window showed (`useSessionHistory`).
- Projects. The "Projects" label's folder+ and ⌘O open the system folder dialog: `WebviewMsg pickFolder`, answered by `HostMsg pickedFolder`, both handled by `ChatWindow` and never sent to the engine. A folder dragged from Finder onto the column also joins (`pathForFile`). A new folder is appended (`addProject`), flashes and scrolls into view, and its start page opens. With no project at all (init without `active`, or `noSession`) the sheet shows the open-folder state.
- Start page: an empty session with nothing queued (`chat/StartPage.tsx`). There is no greeting. The composer stays where a conversation keeps it, two lines tall. Above it sits a segmented agent picker (rounded-lg frame, rounded-md segments, the picked one spelling its name). The project is a dropdown on the sheet header after the title (`ProjectPick`: search, `~` paths, the current one ticked, "Open another folder… ⌘O"); importing an agent's own sessions is an icon on the column's Projects label beside add-folder and the filter. Until 2026-10-23 both sat in a bar under the composer, whose small second dropdown under the composer's own read as clutter. Picking an agent or project starts the empty session over there (`newSession { agent, cwd }`; the engine drops the empty one it leaves), and the typed text moves with it (`moveDraft`). The first message folds the picker away while the field eases to one line.
- Settings (`SettingsShell` with `desktop`): the same frame. The rail lies on the canvas under the same pinned title row, without the column's toggle; its back returns to the chat and forward stays disabled, and the rail has no "back to chat" row. The page is a sheet. In the desktop frame the rail's widths come from `desktop.css`, so the narrow icon rail stays as wide as the title row over it. The session list position (Appearance) and scope (General) are not offered: the shell always passes `left` and `all`, so a value written before cannot strand the column. General offers "Open files with" in the scope's place. "Share selections" stays: its copy names any tool, and the browser panel's page context goes out through it. The language's `auto` reads "Follow system" (`settings.language.system`): the hello's `hostLanguage` is the system's first preferred language.
- The gear menu opens with no collision padding: the gear sits nearer the window's edge than the shell's `--pad`, which had pushed the menu off its button.
- Page and column motion (2026-10-23). Chat and settings replace each other in `App`; the canvas, sheet and title row are the same on both, and what sits in the column or rail and on the sheet fades in as it mounts (`desktop.css`, `acp-fade-in` 220 ms). The settings rail takes the chat column's stored width (`sessionPaneW`), so the sheet's edge stays put. The header's new-session and settings buttons, there while the column is folded, stay mounted and ease their width and opacity with the column (`data-column-act`; a fixed-width button as the grid item held the 0fr track open, so a clip box sits between). The list fades under the top action rows once it scrolled (`list-fade` with `useScrollFade`), as it does at its foot.
- Popovers line up with what opened them: the project row's "…" menu is `sm` wide, so it can end at its button (at `md` the collision padding shifted it right of it); the session column's own menus (the view menu, a project's or a section's "…", a group label's menu, their submenus) open to the right of their trigger over the chat (`side="inline-end" align="start"`, Cursor's placement, 2026-10-23), so a column dragged narrow never squeezes or flips them; the IDE lists keep `bottom` / `end` with submenus opening `inline-start`.
- With the column folded: opening settings opens its rail from nothing (`data-opening`, `acp-rail-open` 320 ms), and coming back mounts the column open at the rail's place and folds it once painted (`Shell` `fromSettings`), so the sheet's edge never jumps. The folded flag is webview state `desktopColumnHidden` (`COLUMN_HIDDEN_KEY` in `packages/ui/desktop.ts`).
- The gear menu carries the theme, the language and the layout (below) as quick switches (submenus, the current value named on the row and ticked inside), writing the same settings as the settings page; a pick leaves both menus open, since a language change re-renders the page in place (`docs/dev/webview.md`); their `auto` reads "Follow system" on desktop (`settings.theme.system`, `settings.language.system`): the system appearance and preferred language.
- A project's "more" row adds ten sessions per click, one fold per page so only the added page opens; once all are out it reads "show less" and folds them all away.
- Narrow window (2026-10-23; picked in the local LAB `lab/portrait.preview.html` as `nav=page&bar=toggle&head=center&frame=inset`, which stays for the PWA, phone and Swift versions). Below `--session-dock-min` (760 px) `Shell` sets `data-narrow` on the root, and `data-drawer-open` while the list is open. The list is a page over the whole window (`absolute inset-0`). Closed, it stays laid out at `translateX(-100%)`, hidden and inert, so it can slide. Opening slides it in over 320 ms on `--start-ease` while the sheet moves a quarter right and dims under `data-sheet-dim` (the scrim at 45%, inside the sheet, which isolates its stacking and is inert meanwhile); closing takes 220 ms on `--ease-close`. It moves only while the user opens or closes it (`data-drawer-moving`, 450 ms from the last move, narrow only), so a window crossing the tier lands without moving. Until that flag was limited to narrow windows, a widen within 450 ms of a close slid the docked column in from the left, and the smoke's next right-click landed off the page. The toggle, Esc wherever the focus is, a picked session and the tier close it; the focus goes back to the toggle when it was inside. The title row keeps the lights and the toggle only (a narrower `--title-w`), with back / forward on ⌘[ / ⌘]. The header centres the title over a second line (agent mark and name, then the project, or `ProjectPick` on the start page), and its account and settings buttons move to the head of the "…" menu (an account submenu, settings ⌘,). The sheet keeps its 8 px inset; whether that edge stays on a phone is still open. In the LAB with the production Shell (Chrome, both themes), at +92 ms into an opening the page was at x −140, the sheet at 70 and the dim at 0.67, ending at 0 / 104. At +71 ms into a close the page was at −162. Widened and narrowed again with the page open, the window landed without moving.
- Shortcuts: ⌘N new session, ⌘K search, ⌘O open folder, ⌘, settings, ⌘[ / ⌘] back / forward through the sessions this window showed (Ctrl elsewhere). On the settings page the title row's back / forward and the same keys walk the pages visited since the settings opened (2026-10-26, `usePageTrail` in `SettingsShell`): a rail click, an orchestration persona or group opened from its list, and the breadcrumb heading back up to the list (`PageCrumb`) each add a step, a deleted persona's page gives way to the list without one, and back past the first page returns to the chat. The drill-in used to carry a back button of its own beside the persona's name, which competed with the window's arrows. In the IDE shells, which have no title row, the breadcrumb is the way up and the rail's Back to chat the way out. The page binds them, and the menu bar carries the first four too (below), so on macOS they reach the page through the menu.
- Checked in the LAB (`lab/desktop.preview.html?set=prod` and `?set=prod-empty`): the production Shell in a window frame with the lights drawn to macOS 27's measure, alignment measured from the DOM, both theme modes. In the Electron window (2026-10-23, macOS 27, temp `ACPIRA_HOME`, so the engine answered `noSession`): the open-folder state shows. A `screencapture -l <window>` of the real window, whose id comes from `CGWindowListCopyWindowInfo`, measured the native lights' centre line at y 30.0 pt, the same as the title row's icons. The root `pnpm package` (`pnpm package:desktop` for the app alone) builds those inputs once and runs it after the VSIX; `pnpm install:local` copies the app into `/Applications`, quitting a running copy first.

Plain `acpira` would be the shell's own `Acpira` on a case-insensitive volume: the first package silently replaced the engine with the shell (2026-10-25).
- Signing: `APPLE_SIGNING_IDENTITY` names a Developer ID Application identity in the keychain, ad hoc without it (runs on the machine that built it only). The Tauri CLI notarizes and staples when `APPLE_API_KEY` / `APPLE_API_ISSUER` / `APPLE_API_KEY_PATH` or `APPLE_ID` / `APPLE_PASSWORD` / `APPLE_TEAM_ID` are set. The hardened runtime needs no entitlement (`Entitlements.plist` is empty): WKWebView's JIT runs in WebKit's own content process.

## Smoke

`cd apps/desktop && node scripts/smoke.mjs [--app <Acpira.app | Acpira.exe>] [--engine <bin>] [--pack-tool <acpira-update-pack>] [--keep] [--shots DIR]` runs the real app on a temp `ACPIRA_HOME`, profile and HOME, in the background (`ACPIRA_DESKTOP_BACKGROUND`). Its only agent is `test/fake-agent.ts`, bundled into the temp folder so that only this run's processes match its path, and its settings are written beforehand (English copy, the built-in agents disabled). WKWebView has no DevTools protocol and Tauri's WebDriver does not run on macOS, so a build with the `smoke` feature listens on `ACPIRA_DESKTOP_HOOK` (one JSON command per line: `eval`, `windows`, `resize`, `close`, `menuBar`, `menu`, `link`, `screenshot`, `quit`); presses are pointer and mouse events dispatched in the page at the element's centre (the point must land on the element, so a press on something still sliding in fails), typing goes through the native value setter and `input` events. Checks:

- the page runs on `acpira-app://localhost`, a secure context, with no back entry; a fresh home shows the open-folder state and writes no session record;
- the empty state's button and the column's "Add project" (answered by `ACPIRA_DESKTOP_PICK`) each add a project and open a session there, and one prompt in each gets the fake agent's reply; `@notes` lists only the shown session's project file, in both projects;
- a second launch with `acpira://session/<first>` hands the link to the running app and brings the first session back; a link to an unknown session shows the not-here toast;
- the drag pasteboard's paths reach `pathForFile` (the pasteboard is written only while no mouse button is down, so a drag of whoever uses the Mac is left alone);
- the tool panel starts closed with its toggle clear of the header; it opens on the project's tree, a folder opens, a file shows in the viewer, "+" offers Files, Terminal and Browser, a browser tab shows a loopback page through the preview proxy with the tab named after it and the page in `browser-history.json`; a terminal tab takes the focus, a line typed through xterm's `input` event runs in the project folder, the tab takes the shell's name, and closing the tab ends the shell;
- a language change re-renders in place (the column and the selected row stay the same nodes), and the installed menu bar's titles follow it (File … Help, then 文件 编辑 视图 窗口 帮助, then English again);
- View › Layout through the menu handler lays out explorer, stage, chat and column from left to right and back;
- a real 480 × 760 resize shows the list as a page as wide as the window, a pick closes it, and widened the column docks again;
- "Remove from list" on a project's right-click menu takes it off the column while its session's record stays;
- File › New Window opens a second window, which shows and closes;
- quit saves the one window's place; a relaunch within the engine's grace restores it on its session and reaches the same engine process; after the last quit the engine ends within its idle grace and no process runs the run's fake-agent copy;
- with `--app <Acpira.app>` (or, on Windows, `--app <Acpira.exe>` with a pack tool; "Updates" below) the run updates the app: it runs a `ditto` copy of the bundle under the temp folder, re-signs a second copy (ad hoc) with `Contents/Resources/smoke-update.txt` as the next patch version, packs both with `acpira-update-pack` (debug build, zstd level 3, a throwaway key) and serves them on the loopback (`ACPIRA_DESKTOP_UPDATE_URL`, `ACPIRA_DESKTOP_UPDATE_KEY`). Before the last quit it posts `updateCheck` with `download`, waits for `ready` through the hook's `update` op (the delta, not the full package), presses the toast's Restart, and checks that the bundle was replaced and a new process from it restores the window on the same session; both engines end within their grace.

Without `--app` it builds the debug app and engine first (no update step: a bare binary has no bundle to replace); with `--app` the packaged app runs on its bundled engine unless `--engine` is given. A run takes about 60 s after the builds, most of it the engine's 30 s grace. A failure keeps the temp folder with `failure.png` and the app log.

## Updates

The app updates itself without Sparkle or `tauri-plugin-updater` (`rust/crates/acpira-desktop/src/update/`, window-free and unit-tested; the shell side in `apps/desktop/src/app.rs`). VS Code and IntelliJ keep their marketplaces' updates.

- Release side (`docs/releasing.md` "Desktop app"): `acpira-update-pack` turns the signed, notarized `Acpira.app` into `Acpira-<v>-darwin-aarch64.app.tar.zst` (zstd tar of the bundle, level 19), one `Acpira-<from>-to-<v>-darwin-aarch64.delta` per earlier full package, `desktop-update.json` and its detached Ed25519 signature `desktop-update.json.sig` (hex). Each delta is applied back onto its base and compared with the new bundle before it is listed; a delta larger than 60% of the full package is dropped. Given an exe (`--app Acpira.exe`, platform `windows-x86_64` by default) it packs a one-file tree, `Acpira.exe` whatever the input is called, mode 0o644 as Windows reports every file, into `Acpira-<v>-windows-x86_64.exe.tar.zst` and its deltas. Each platform is packed on its own runner with `--unsigned`; `acpira-update-pack merge --out DIR part.json…` joins the parts (same schema and version, no platform twice, the first notes, one system minimum) and signs the result (2026-10-26).
- The manifest (`manifest.rs`, schema 1): `version`, `notes`, `minimumSystemVersion` (macOS's; Windows reports no system version, so it never applies there), and per platform (`darwin-aarch64`, `windows-x86_64`) the full asset, the tree's file list (path, size, SHA-256, mode, symlink target) and the deltas by from-version, each asset as URL, size and SHA-256. The signature covers the manifest bytes, so every digest and every delta's base list is signed. Keys are in `update::PUBLIC_KEYS` (several allowed for a rotation); a build with none never checks (`manual: unconfigured`), nor does a macOS build without `TEAM_ID`. Windows does not use `TEAM_ID`.
- A delta (`delta.rs`) is an uncompressed tar: `index.json` first (the base's file list and one op per new file), then `data/<n>`. Ops: `keep` (same digest: `clonefile`, so APFS shares the blocks), `patch` (a zstd frame decoded with the installed file as its reference prefix, long-distance matching up to window log 31), `add`, `link`; files absent from the index are left out. The installed bundle must match the base list byte for byte, otherwise the full package is taken; the result is checked against the manifest's file list either way (`verify_tree`), `_CodeSignature` and the stapled ticket included, so the client never signs anything.
- Downloads (`fetch.rs`, `ureq`): https only, to `github.com`, `objects.githubusercontent.com` and `release-assets.githubusercontent.com` (where release assets redirect since 2026), every redirect hop checked; resumed with `Range`, hashed while streaming, renamed into place only on a matching digest. The proxy is the engine's (`acpira_shared::proxy`: the `proxy` setting, `ACPIRA_PROXY`, auto on port 7890).
- Staging (`stage.rs`): the bundle is assembled next to the install on the same volume (the cache dir when it shares the volume, else a hidden sibling), then `codesign --verify --deep --strict -R` with the identifier and Developer ID team, and `spctl -a -t exec` for the notarization. On Windows the volume test compares `GetVolumePathNameW` (a folder another volume is mounted on counts as that volume), the tree is `<staging>/Acpira/Acpira.exe`, a sibling staging folder gets the hidden attribute, and a build that is not exactly one `Acpira.exe` fails the cycle before any download. The exe is not Authenticode-signed yet, so the signed manifest and the per-file digests are its whole check; a `WinVerifyTrust` check would sit beside `verify_signature` (`stage.rs` names the place). Restart to Update (the toast's button, the app menu's item under About, the About page) swaps it in with `renamex_np(RENAME_SWAP)`, quits as usual and a helper starts the new bundle once the old pid is gone (`open`; a smoke build executes it directly so the temp HOME survives). A staged update left at quit is applied then and starts with the next launch. Running turns survive: the engine socket's key is the engine binary's path, size and mtime, so the new app starts a new engine and the old one finishes its turns and ends after its grace.
- Windows install (2026-10-26, `swap.rs`): the install is the running exe itself (`swap::install_of`; the user may have saved it as `Acpira (1).exe`, which keeps its name, and a delta reads the installed file under that name). A running exe cannot be overwritten or deleted but can be renamed: at Restart (or quit) it moves to `<name>.old` (hidden), the staged exe is renamed into its place, and when that second rename fails the first is undone. Restart then starts the new exe directly with `ACPIRA_DESKTOP_WAIT_PID=<old pid>` (no helper process, so no console; `process::detach`); its `main` waits up to a minute for that pid (`OpenProcess` + `WaitForSingleObject`) before claiming the single instance, and clears the variable. The `.old` file is held by the old process and by the engine it started from the same exe, so the updater deletes it at every start and every check, best effort. The old engine keeps running its turns: the new exe's size and mtime give it a new pipe key.
- No in-place update (`ManualReason`; the About page links to the release instead): not in a bundle (`cargo run`), App Translocation (run from the dmg or Downloads without moving), a read-only volume, a folder the user cannot write, a signature without the release team (ad hoc / development builds), no key / team in the build, or a macOS below the manifest's minimum. On Windows: a development build (an exe still named `acpira-desktop-tauri.exe`, cargo's name; `package-windows.mjs` copies it out as `Acpira.exe`, so any other name counts as packaged), an exe under `%TEMP%` (Explorer runs an exe opened inside a zip from `%TEMP%\Temp1_<zip>\`, 7-Zip similarly; reported as `translocated`, whose copy still names the Applications folder), or a folder where a probe file cannot be created (Program Files without elevation; the folder's read-only attribute means nothing on Windows). The smoke build leaves the temp check out, since its copy lives under the temp folder.
- Scheduling and UI: a check a minute after launch and every six hours (none in a smoke build); it downloads when "Download updates automatically" is on (shell setting `updateAuto`, default on). Page messages `updateCheck` (`download`), `updateInstall`, `updateAuto`; the shell broadcasts `updateState` (`UpdateState` in `packages/shared/protocol.ts`) and posts a toast with a Restart action on reaching Ready (a system notification with no window). The UI is the desktop-only About page at the settings rail's foot (`packages/ui/settings/AboutPage.tsx`, LAB `lab/desk-update.preview.html`): version and status, the one next step, the switch, then help / release notes / source.
- Measured 2026-10-25: engine 1.10.7 → 1.10.8 as a zstd patch 3551 KB, bsdiff 3326 KB, its full zstd 6.86 MB (bsdiff only 7–19% smaller, so zstd, which needs no extra dependency); the local app's full package 13.4 MB / 180 files, a rebuilt-engine delta 0.33 MB. The smoke's re-signed copy: full 17.6 MB, delta 88 KB.
- Verified 2026-10-25: unit tests in `cargo test -p acpira-desktop` (manifest signatures, deltas rebuilding the bundle exactly, a modified install falling back to the full package, resumed and refused downloads, staging, the state machine against a loopback release); `scripts/smoke.mjs --app` on `package.mjs --smoke` (delta, swap, restart on the same session). Not yet: a Developer ID / notarized build (`spctl`, the team requirement), the CI job, App Translocation and read-only volumes on a real dmg, a download through a proxy.
