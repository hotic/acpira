# Protocol gotchas

Cross-agent ACP behaviour the host depends on. Agent-specific facts are in `agent-quirks.md`; the verified / source / unverified matrix is `docs/acp-agents-compat.md`.

Hard-won facts about the ACP implementations we drive; check here before assuming the spec:

- Historical message editing uses a fresh `session/new` plus retained transcript context because standard ACP has no turn-addressed rewind. Never truncate only the UI while keeping the old peer context, and never replay historical tool actions as prompts. `AcpSession.editTurn` stages attachments and exact model/config/mode selections before replacing the local continuation; failed edited-turn retries rebuild that context. Workspace files are not rolled back. Oversized full-history editing automatically continues in the same native session with only the edited prompt and selected attachments; the full transcript remains intact. The editor keeps a single send action. `intent: 'continue'` on `EditTurnRequest` requests that path explicitly. Verify Grok / Devin / Kimi capability boundaries with `scripts/probe-edit-turn.ts` (a one-off probe, since removed). The editor reuses the composer's picker but its controls are a local snapshot (no `set_config_option` until send), so a model switch there would keep the previous model's dependent controls. `SessionManager.learnShape` records, per agent and model option id, the non-model controls a ready session's agent truth carries (`shared/modelShapes.ts`, structure changes only, persisted as `modelShapes` in `sessions/prefs.json` and merged per model across windows, carried on `SessionView.modelShapes`); `openTurnControls` / `editTurnConfig` (`shared/turnSettings.ts`) take the model's learned shape first, then the live controls for the live model, then a same-family sibling's shape, and keep the snapshot only for a model never seen live. The learned shape outranks the live view because the view can pair a model with another model's parameters (`previewControls` while starting, the optimistic overlay while a composer model switch is in flight) — trusting it showed Luna with SWE-2's Medium / High / Max and no Fast. `refreshIndex` (webview ready, window focus) also merges shapes other windows wrote and `republish`es that agent's live sessions, since a push without a newer `rev` is dropped by the webview. `applyEditSettings` is strict about the model and mode, while a dependent value the chosen model no longer offers yields to the agent's own value (an offered value the agent refuses still fails the edit). Devin 3000.11.3, from stored session controls: GPT-6 Luna / Claude Opus 5.5 carry `speed` [standard|fast] and `thought_level` low–max, SWE-2 has no `speed` control and `thought_level` [medium|high|max]; Luna Fast → SWE-2 in the editor used to fail with "Selection unavailable: speed" (`tests/engine/acp_session.rs` "dependent controls", fake `FAKE_SPEED`).
- Cross-agent oversized-edit verification on 2026-09-15: `scripts/probe-edit-turn.ts grok --oversized --model=asgard` (a one-off probe, since removed) and the equivalent `kimi --oversized --model=asgard/kimi-k3` both kept the native session, complete displayed history, retained context marker, and kept/new text attachments while changing reasoning to low. The probe adds approximately 1.09 MB of synthetic UI-only history after `/compact` to exercise the host byte limit; it is not a native model-window load test. Kimi 0.41.0 explicitly reported compaction completed. Grok 1.0.18 returned `end_turn` with no status/text and unchanged context usage in this small session, recorded as `rpc-completed-without-status`, not proof that compaction reduced the context. Adapter regressions in `tests/engine/acp_session.rs` additionally cover Grok synthetic plan/yolo modes and Kimi background completion; `tests/engine/agent_process.rs` and `tests/engine/compaction.rs` cover their queue and usage differences.
- Resending an unchanged historical message after only identical empty failed attempts is a retry: `sessionEdit.unchangedFailedRetry` keeps the native session and sends only that message. Text and attachments must be unchanged and every discarded agent turn must be an empty error, but the retry may carry changed model/config/mode selections, applied natively through `applyEditSettings` on the live session rather than by rebuilding. This preserves native compaction; reserializing a multi-megabyte UI transcript for a plain retry exceeded Devin's model window. Genuine edited turns still rebuild their context.
- Model identity must preserve the ACP option ID and source/group identity, independently of the display name. Kimi's `kimi-code/k3` and `asgard/kimi-k3` both advertise `K3`; merging them by name routes selection to the first provider. Grok advertises custom config aliases such as `asgard` without source metadata, so `host/acp/modelSources.ts` reads custom endpoint declarations and `shared/modelSources.ts` annotates the options. Keep ACP select groups through normalization. New agent integrations must verify official/custom same-name selection, independent hiding, restoration, and config updates; unknown sources stay unclassified, and ambiguous duplicate parameter tuples remain separate by their original option IDs. Devin's genuine effort/Fast/1M variants still group normally.
- Plan approval: Grok 1.0.18 sends `_x.ai/exit_plan_mode` with `planContent`, answered with `{ outcome: 'approved' | 'rejected' }` by `grokPlan.ts`. An unhandled method is misleadingly reported as a client disconnect. Devin and Kimi use `session/request_permission`; Devin marks plan writes/exits with `cognition.ai/isPlanFileEdit` / `cognition.ai/isExitPlan`, while Kimi puts the plan body in permission content. Codex sends the review as `kind: 'switch_mode'` with `rawInput.plan` (`plan-review:*` toolCallId, `implement_plan` / `revise_plan` options) and Claude's ExitPlanMode permission carries `exit-plan-default` (allow_once) / `exit-plan-*-auto` (allow_always) / `reject` (reject_once) — both land as `plan_document` linked to the card by `planId`, and the chosen option id goes back verbatim. `plans.ts` preserves complete plan documents separately from the live to-do list. Verify with `scripts/probe-modes.ts` (a one-off probe, since removed) and the `--plan` flag of `probe-agent-host.ts`.
- Plan execution: `plan_document` cards stay outside process folds, preserve the file path and Markdown, and apply the chosen model before releasing approval. Model-switch failure leaves approval pending. Kimi 0.41.0 omits `current_mode_update` after approval; synchronize Default only after its successful ExitPlanMode output explicitly confirms deactivation. Grok's structured follow-up questions (`_x.ai/ask_user_question`) are a separate request handled by `questions.ts` (see the questions bullet); plan approval support does not imply question-form support and vice versa.
- The SDK's `ctx.request(method, params)` generic inference is fragile: when params is a separate variable, annotate it explicitly as `acp.XxxRequest` or it silently degrades to `unknown`
- Permission requests usually carry only `toolCall.title`; get the command/verb from the corresponding tool call. The codex/claude adapters add `_meta.permission` v1 — `title` / `description` override the tool-derived card text, per-option `_meta.permission.description` becomes the option's `detail`, and `defaultToNo` makes the reject button primary; the webview's quick buttons are always the first `allow_once` / `reject_once` by kind (`permissionOptions.ts` `quickChoices`), never guessed from labels — unknown labels stay verbatim
- Controls are not hardcoded into "model / mode" buckets: `modes` come from `session/new` (each `SessionOption` keeps the adapter's `_meta.kind` — codex/claude `full_access` gets the warning glyph, names never rewritten); every other select- or boolean-type configOption goes into `controls.options` (ordered by category: model → thought_level → model_config → rest; a boolean becomes a synthetic Off/On control while `configOptionSetValue` sends a real `type: 'boolean'` value on every `set_config_option` path — a `"false"` string parses truthy on some agents — and the client advertises `session.configOptions.boolean` so adapters don't degrade booleans to selects), rendered through the shared Composer presentation adapter and switched via `setConfig(configId, value)`; native `thought_level` selects join the model panel footer instead of creating separate toolbar chips. User config/mode clicks go through `selectConfig` / `selectMode`, which overlay the pick on `view()` at once and serialize/collapse the wire requests, reverting to agent truth on failure — `agentControls` and `toRecord()` always stay agent truth. A `category=mode` configOption only stands in as modes when the protocol didn't send any (legacy Grok path); when modes exist it's a duplicate (Kimi sends both) and stays out of the control list. Every Fast shape reads as one "Fast" switch and chip (`isFastControl` / `fastOn` / `fastValue`): Devin's native `speed` Standard / Fast select, Codex's `fast-mode` and Claude's `fast` booleans, and the embedded model-name variant. `initialize` advertises the AIR `recommendedValue` capability, so claude-agent-acp drops its placeholder `default` effort row and the `default` model row whenever a concrete model matches it (the `default` model stays only when nothing matches), and reports concrete current values. A user's model switch (`setConfig` on a `model` control) re-sets the previous native effort when the new model offers it — Devin resets `thought_level` on every model change and claude-agent-acp re-seeds effort per model — and `selectConfig` holds the effort in the overlay meanwhile; `adoptControls` skips that restore because it sets the remembered effort itself right after
- Follow-ups sent while a turn runs are a host-side queue (`AcpSession.queued`, in-memory, in send order): each entry is staged the moment it is queued (`preparePrompt` writes the blobs, per-draft problems are reported once) so `SessionView.queued: QueuedPrompt[]` carries `Attachment`s the webview renders like a sent turn's; `flushQueued` hands the staged payload to `prompt` (`StagedSend`, `edited` only for `editTurn`). `dequeue` / `editQueued` (kept attachments by index + new drafts, replaced in place) address entries by id; `chat/Queue.tsx` shows one row per entry above the composer with a pencil (inline bare Composer) and a bin
- Sessions belong to a project: `SessionRecord.cwd` / `SessionSummary.cwd` is the workspace folder the session was opened in (also the agent's working directory; `homedir()` without a folder). `acpira.sessionScope` (`workspace` default | `all`, `shared/settings.ts` `SessionScope` / `inWorkspace`) decides what the list shows: the webview filters `SessionList` by `InitState.cwd` (the active session always stays listed; the settings General page writes `acpira.sessionScope`), and the host consults `ManagerDeps.scope` for the picks a viewer makes on its own (`mostRecent()` at `attach({ mostRecent })`, the next session after `deleteSession`) so a sidebar never lands on another project's conversation. Under `all`, rows from other projects carry `projectName(cwd)` (faint, `max-w-project`) before the time and a `FolderInput` "move here" hover action → `moveSession` (`SessionManager.moveSession`): a stored record is patched, a live idle session is disposed and reopened in the new folder through `selectSessionFor` (the agent is respawned there, `session/resume` / `load` carry the new cwd, unknown-id fallbacks apply), a running one refuses with `host.moveWhileRunning`. `lab/session-scope.preview.html` shows the tag / move; `tests/engine/session_manager.rs` "workspace scope" covers the host side (project folders must exist — the fake agent is spawned in them)
- Session deletion is soft: `SessionManager.deleteSession` removes from the list and moves the record + blobs into `sessions/trash/` for 30 s (out of the live directory, so no other window's reconcile lists it); the webview shows an undo Toast; `restoreSession` moves them back, files are really deleted on timeout or dispose, and `init` sweeps trash entries older than the window (a crash's leftovers) while leaving fresh ones another host may still undo. Deletion wins over another window that has the same session live: `TranscriptStore.write` refuses to recreate a record the store once had on disk (`knew`) and that is gone, and `SessionManager.syncIndex` treats a live session missing from the reconciled list as deleted elsewhere (`forget` + `rehome` its viewers, toast). Verify with the "live in two managers" test
- Queue UI siblings use role-prefixed keys (`plan:<sessionId>`, `queue:<sessionId>`, `composer:<sessionId>`). Sharing a session-only key leaves orphaned queue rows and duplicates them on deletion. `sendQueued` prioritizes the existing staged entry, cancels the active turn, and lets prompt completion flush it; never send a concurrent ACP prompt from the cancel notification response. Repeated send-now clicks are ignored while cancellation is pending. Verify the real App routing in `lab/queue.preview.html` and cancellation / attachment order in `tests/engine/acp_session.rs`.
- Per-agent memory of the last chosen mode and config values lives in `~/.acpira/sessions/prefs.json` (`SessionManager.remember` on user `setConfig`, `rememberMode` on a user `setMode` the session then shows). Only the user's own picks are remembered: a mode the agent switches by itself (Devin's "switch to bypass mode" permission answer, Kimi leaving plan after approval, `current_mode_update` in general) stays that session's business and does not touch the memory, and a config pick keeps the remembered mode instead of capturing the session's current one. A remembered mode the agent no longer offers is skipped like any stale value. `newSession` snapshots the inheritable values before `start` (a choice made elsewhere mid-spawn must not land on the new session) and replays them through `AcpSession.adoptControls`, one `set_config_option` per differing value in control order (model before effort), skipping values the agent no longer offers. Restored sessions keep their own persisted controls; `rebindAccount` re-adopts the same session's settings including its mode; `editTurn` restores exact per-turn settings and does not touch the memory
- Accounts are bound per session: one agent process uses one credential. Switching accounts rebinds the current session (`AcpSession.rebindAccount`: wait for the old process to exit, authenticate a replacement, then resume/load the same `acpSessionId`). Devin 3000.6.14 supports loading local sessions across accounts; a two-account round trip preserves native history and compacted context. Never clear the native session ID or serialize the entire UI transcript into the next prompt when switching accounts: long histories exceed the model window. `SessionRecord.accountId` is persisted so restored sessions keep their bound account; the chosen account also becomes the agent's default for the next new session. Running turns reject switching before changing that default. Verify with `test/accounts.test.ts` and `scripts/probe-account-switch.ts` (a one-off probe, since removed). Automatic switch on exhausted quota (`session_prompt.rs` `reserve_switch` / `switch_after_exhaustion`): only a settled turn whose error `is_quota_exhausted` (`session_errors.rs`: Devin `resource_exhausted` / -32011, AIR `quota_exhausted` or category `limit` without retry / new-session remedies, the Codex / Claude usage-limit sentences) on a session bound to a saved account reserves the session (`Core.switching`, part of `busy`, so manual switches refuse and `flush_queue` holds new prompts) under the same lock that settles it. The fallback account (see `accounts/switch.rs`) is bound through `rebind_reserved`, the native session resumes on it, and the exhausted turn keeps its output with the error card replaced by a `Limit` / warning `NoticeBlock` (`host.accountSwitched`); then a hidden continue prompt in the host language (`host.autoContinuePrompt`, `UserTurn { auto, autoReason: accountSwitch }`, rendered as nothing, exported as a note) carries the task on and the queue follows it. No fallback, strategy `off`, or a replacement that does not come up Ready: the original error (and its failure notice) is restored, the switch is released and the queue moves on; an exhausted account stays parked, so repeated exhaustion walks the list instead of looping. Sessions without a bound account (created before any account was saved) never switch. Verify with `tests/engine/accounts.rs` (`FAKE_EXHAUSTED_KEYS` in `test/fake-agent.ts`).
- Auto-compaction: ACP has no compact request, so the shared host uses the agent's advertised `/compact` at a turn boundary when reported usage meets `acpira.compactAtTokens` and `acpira.autoCompact` is enabled. This policy neither enlarges the model window nor changes native CLI compaction. Kimi's post-response usage is awaited before flushing queued work; late idle usage is re-evaluated. Grok polls through quiet running intervals. The ring and panel use the same native window; no transcript-based estimate is shown. See `CONTEXT.md` for source ownership, verified backend limits, ordering, and probes.
- Background compaction: Devin 3000.6.14 and Kimi 0.41.0 acknowledge manual `/compact` before it finishes, using plain-text completion messages; Devin can acknowledge before its first status notification. `compaction.ts` holds the host queue until completion, cancellation, or failure, and also tracks structured `compaction_update` IDs. Releasing on the RPC response alone cancels Devin's compaction or loses Kimi's follow-up reply from the ACP stream. Grok 1.0.18 waits inside the request. Verify with `scripts/probe-compaction.ts` (a one-off probe, since removed) and `scripts/probe-compaction-queue.ts` (a one-off probe, since removed).
- Compaction rows are one block type for every agent. Structured `compaction_update` is handled by protocol, not by agent (a failed one keeps its `error` on `CompactionBlock.error`); the host advertises `clientCapabilities.session.compaction`, which switches claude-agent-acp 0.81.0 and codex-acp from a `Compact conversation` tool call to it. Adapters that report compaction as prose go through `acp/compaction_text.rs`: a per-agent table (devin / kimi / pi) of the exact adapter sentences, matched only against a whole `agent_message_chunk` (model prose streams as deltas, so a chunk that is exactly an adapter sentence is the adapter). A start opens a `text-compaction-*` row in place — a second start while this turn's row is open is ignored — an outcome settles the latest open prose row, even in an earlier turn (background /compact), or stands alone; Kimi / Pi statistics lines are absorbed only directly under a compaction row. Anything else stays text. `webview/chat/compactionDisplay.ts` remains for records persisted before this and for the wait before the first chunk of a /compact reply. Verify with the compaction cases in `tests/engine/normalize.rs` and the unit tests in `compaction_text.rs`; a new adapter sentence goes into that table with the version it was seen on.
- `getConfiguration().get()` returns a read-only Proxy: it cannot be `structuredClone`d or `postMessage`d (`#<Object> could not be cloned`) — round-trip through JSON first
- A failed `session/prompt` usually leaves the session `ready`: `AcpSession.prompt` catches the JSON-RPC error and `failTurn` puts it on the turn (`AgentTurn.stop = 'error'`, `AgentTurn.error = { message, code, kind, retryable }`); `stopReason` other than `end_turn` / `cancelled` lands on `AgentTurn.stop` too. Devin's typed cause is `data['cognition.ai/errorKind']` / `data['cognition.ai/retryable']` (the same fields as the -32015 / -32016 load errors). The webview shows the last turn's short stop as a card above the composer (`chat/Alert.tsx`, dismiss is webview-local) plus a faint closing row in the message; `retryTurn` drops both turns and re-sends the user turn on the same connection with drafts rebuilt from the blobs (`restoreDrafts`). Three failures do flip the status — `-32000` to `auth_required`, and a peer reporting the native session gone or a dead process to `error`, since resending into a dead channel can only fail the same way; the Notice's Retry then does a full reconnect + resume. A live process that keeps answering -32603 on an old session (Grok) stays `ready`, so the Alert also offers Reconnect (`reconnect` → `AcpSession.reconnect`: refused mid-turn, otherwise `reopen` = drop the process, `start` resumes the same `acpSessionId`, then `adoptControls` restores this session's own choices — the same tail `rebindAccount` uses); the failed turn stays so Retry can then resend over the new connection
- Questions (the agents' ask-user-question tools) all land in `host/acp/questions.ts` (`QuestionGate`) as one `QuestionBlock` in the current agent turn; the webview pins the open card above the composer (`chat/Questions.tsx`, Cursor's layout: lettered options, `Other…`, Skip / Continue, `1 of N` pager) and answers with `answer { blockId, answers, skip }`; a resolved block stays in the message as the `QuestionRecord` (`outcome` answered / skipped / cancelled + `answers`). Three dialects, verified with `scripts/probe-questions.ts` (a one-off probe, since removed) (raw wire) and `scripts/probe-questions-host.ts` (a one-off probe, since removed) (AcpSession path):
  - Devin 3000.6.14: `ask_user_question` is gated on the client's `elicitation.form` capability (without it the model asks in prose). Flow: `tool_call` (`_meta['cognition.ai/inferenceToolName'] = 'ask_user_question'`, `rawInput.questions[{ header, question, options[{ label, description }] }]`) → `elicitation/create` `mode: 'form'` **without** `toolCallId`, `message` = first question, `requestedSchema.properties.qN` = `{ title: header, description: question, oneOf: [{ const: label, title: description }] }` (label in `const`, description in `title` — the opposite of the spec's reading), all `required`, `_meta['cognition.ai/allowOther']`. `accept` with every key → `tool_call_update` `_meta['cognition.ai/answers']` then `completed`; free text comes back as `Other, <text>`; `accept` with keys missing is treated like `decline` ("The user wants to clarify these questions", tool `failed` with `cognition.ai/rejected`); `cancel` → "User canceled the question"
  - Kimi 0.41.0: same `elicitation/create` form **with** `toolCallId`; `properties.qN` = `{ title: header, oneOf: [{ const: label, title: label }] }` and no `description` — the question texts are joined with `\n` in `message`. Partial `accept` is fine (missing keys are simply unanswered), a string outside `oneOf` is dropped, `decline` / `cancel` → `{"answers":{},"note":"User dismissed the question without answering."}`
  - Grok 1.0.18: a private request `_x.ai/ask_user_question` `{ sessionId, toolCallId, questions[{ question, options[{ label, description }], multiSelect }], mode }` (an unhandled method fails the tool with method-not-found); the response is tagged on `outcome`: `{ outcome: 'accepted', answers: { [question]: label | string | string[] } }` (free strings allowed, unanswered questions simply omitted; `{}` yields the awkward "User has answered your questions: ."), `{ outcome: 'skip_interview', partial_answers? }` ("proceed with the information you have", answers listed with `(No answer provided)`), `{ outcome: 'chat_about_this', partial_answers? }` ("ask them what they would like to clarify"). The model sometimes claims the tool is unavailable and asks in prose instead — that is not a client failure
  - Mapping: Continue → Grok `accepted` / form `accept` (typed: boolean, number, string[]); Skip → Grok `skip_interview` + `partial_answers`; a form with some answers is `accept`ed as far as it goes, an untouched one is `decline`d; Stop / turn end → `cancel`. `QuestionGate.rememberToolInput` keeps `rawInput.questions` per tool call so form choices get the agent's own labels / descriptions (Devin's form has no `toolCallId`: the latest input with the same question count is used); `formQuestions` also handles `boolean` (Yes / No), `array` (`items.anyOf` / `enum`, multi-select), `enum`, `number` / `integer` (numeric text) and plain `string` (text). Tool rows titled `ask_user_question` / `AskUserQuestion` / `Ask(ed|ing) … questions` get `verb.ask` and drop the title target
- The live to-do list is `chat/PlanBar.tsx`: the latest `plan` block in the transcript (each update replaces the whole list), pinned above the composer while it has open entries; a fully completed list stays only until that same turn ends and must not reappear just because a later prompt is running; the `plan` block inside the message is the history copy. `plan_update` / `plan_removed` (ID-addressed, items / markdown / file) are only sent to clients advertising `clientCapabilities.plan`, which the extension does not, so agents keep sending the legacy `plan`
