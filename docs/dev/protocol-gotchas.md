# Protocol gotchas

Cross-agent ACP behaviour the host depends on. Agent-specific facts are in `agent-quirks.md`; the verified / source / unverified matrix is `docs/acp-agents-compat.md`.

Hard-won facts about the ACP implementations we drive; check here before assuming the spec:

- Historical message editing uses a fresh `session/new` plus retained transcript context because standard ACP has no turn-addressed rewind. Never truncate only the UI while keeping the old peer context, and never replay historical tool actions as prompts. `AcpSession.editTurn` stages attachments and exact model/config/mode selections before replacing the local continuation; failed edited-turn retries rebuild that context. Workspace files are not rolled back. Oversized full-history editing automatically continues in the same native session with only the edited prompt and selected attachments; the full transcript remains intact. Only the history and text blocks count toward that limit, never image pixels (`edit.rs` `rebuilt_text_bytes`). On 2026-10-04 Devin 3000.11.3 edited a message carrying a 316 KB screenshot: its base64 pushed the edit onto the native-continue path, so the old prompt and its `已停止` turn stayed on screen above the edited prompt. Verify with `tests/engine/acp_session/edit_context.rs` `a_large_image_does_not_turn_an_edit_into_a_native_continue`. The editor keeps a single send action. `intent: 'continue'` on `EditTurnRequest` requests that path explicitly. Verify Grok / Devin / Kimi capability boundaries with `scripts/probe-edit-turn.ts` (a one-off probe, since removed). The editor reuses the composer's picker but its controls are a local snapshot (no `set_config_option` until send), so a model switch there would keep the previous model's dependent controls. `SessionManager.learnShape` records, per agent and model option id, the non-model controls a ready session's agent truth carries (`shared/modelShapes.ts`, structure changes only, persisted as `modelShapes` in `sessions/prefs.json` and merged per model across windows, carried on `SessionView.modelShapes`); `openTurnControls` / `editTurnConfig` (`shared/turnSettings.ts`) take the model's learned shape first, then the live controls for the live model, then a same-family sibling's shape, and keep the snapshot only for a model never seen live. The learned shape outranks the live view because the view can pair a model with another model's parameters (`previewControls` while starting, the optimistic overlay while a composer model switch is in flight) — trusting it showed Luna with SWE-2's Medium / High / Max and no Fast. `refreshIndex` (webview ready, window focus) also merges shapes other windows wrote and `republish`es that agent's live sessions, since a push without a newer `rev` is dropped by the webview. `applyEditSettings` is strict about the model and mode, while a dependent value the chosen model no longer offers yields to the agent's own value (an offered value the agent refuses still fails the edit). Devin 3000.11.3, from stored session controls: GPT-6 Luna / Claude Opus 5.5 carry `speed` [standard|fast] and `thought_level` low–max, SWE-2 has no `speed` control and `thought_level` [medium|high|max]; Luna Fast → SWE-2 in the editor used to fail with "Selection unavailable: speed" (`tests/engine/acp_session/edit.rs` "dependent controls", fake `FAKE_SPEED`).

- Resending an unchanged historical message after only identical empty failed attempts is a retry: `sessionEdit.unchangedFailedRetry` keeps the native session and sends only that message. Text and attachments must be unchanged and every discarded agent turn must be an empty error, but the retry may carry changed model/config/mode selections, applied natively through `applyEditSettings` on the live session rather than by rebuilding. This preserves native compaction; reserializing a multi-megabyte UI transcript for a plain retry exceeded Devin's model window. Genuine edited turns still rebuild their context.
- Model identity must preserve the ACP option ID and source/group identity, independently of the display name. Kimi's `kimi-code/k3` and `asgard/kimi-k3` both advertise `K3`; merging them by name routes selection to the first provider. Sources come from each CLI's own config (`acp/agents/model_sources.rs`, applied by `acpira-shared` `model_sources.rs` on every publish): Grok `[model.<alias>]` with `base_url` (aliases such as `asgard` arrive without source metadata), Kimi / Pi / OpenCode `provider/` id prefixes (custom when the provider declares an endpoint in `models.json` / `opencode.json`), Codex's non-openai `model_provider` and Claude's `ANTHROPIC_BASE_URL` off `api.anthropic.com` (the one endpoint sources every model). Pi and OpenCode prefix the display name with the provider (`asgard/Kimi K3`, `Asgard/GLM-5.3`); the label moves into `source.name` once (already-sourced options are skipped, so a republish never strips twice), and `familyHidden` still honours a `Provider/Name` preference stored before that. Keep ACP select groups through normalization. New agent integrations must verify official/custom same-name selection, independent hiding, restoration, and config updates; unknown sources stay unclassified, and ambiguous duplicate parameter tuples remain separate by their original option IDs. Devin's genuine effort/Fast/1M variants still group normally.
- Effort narrowing (`acpira-shared` `model_catalog.rs`, host `model_catalog.rs`): the reasoning selects are cut to what the current model really takes, and only the displayed set changes (option ids stay the wire values). Custom-source models are intersected with the official catalogue (models.dev `reasoning_options`, first-party vendors only; `none` / `toggle` allow off); official models trust the agent unless it reports its own levels (`NativeLevels`, today Pi's `thinkingLevelMap`, with `catalog_fallback` for models pi's files do not list). Identity is exact after normalization (last `/` segment, lowercase, `_` / space / `.` → `-`, no date / `-latest` suffix; id first, then name; a vendor listed first wins a duplicate, alibaba last); unknown models, off-scale labels (`on`, `ultra`) and a cut that would leave no level on the scale are left alone. It runs in `touch` and right after every `set_config_option` answer, so the effort restore and `sync_thought` only pick offered values; `start` runs `sync_thought` once, so a value narrowed away at load is corrected too. The catalogue is `assets/model-catalog.json` built into the sidecar (`pnpm catalog:update` regenerates it), replaced by `<root>/catalog/models.json` when newer, refreshed from models.dev at most daily with ETag (`ACPIRA_CATALOG_REFRESH=0` disables the download; the vitest sidecars set it). Verify with `tests/engine/acp_session/controls.rs` `a_pi_custom_model_offers_only_the_efforts_pi_and_the_catalogue_both_allow` and the unit tests in both `model_catalog.rs` / `model_sources.rs`

- The SDK's `ctx.request(method, params)` generic inference is fragile: when params is a separate variable, annotate it explicitly as `acp.XxxRequest` or it silently degrades to `unknown`
- Permission requests usually carry only `toolCall.title`; get the command/verb from the corresponding tool call. The codex/claude adapters add `_meta.permission` v1 — `title` / `description` override the tool-derived card text, per-option `_meta.permission.description` becomes the option's `detail`, and `defaultToNo` makes the reject button primary; the webview's quick buttons are always the first `allow_once` / `reject_once` by kind (`permissionOptions.ts` `quickChoices`), never guessed from labels — unknown labels stay verbatim
- A permission request is an approval ladder only when its kinds say so. Several `allow_once` options and no `allow_always` are a list of answers (antigravity-acp 1.2.1 sends its `ask_question` tool this way: every answer `allow_once`, only `deny` / `dont_trust` / `block` ids become `reject_once`), so nothing picks one for a person: `errors.rs` `auto_allow` returns none and synthesized yolo opens the card, switching into yolo (`flush_permissions`) leaves such a card open, and the webview (`permissionOptions.ts` `ambiguousChoices`) lists every option as an equal button in wire order with none emphasized. Codex's permission-profile card has two `allow_once` grants under an `allow_always`, so it keeps the usual layout and yolo picks the `allow_always`. Under the built-in antigravity id the request does not reach a permission card at all: `Vendor::question_permission` (an `interaction_*` toolCallId with empty `rawInput`) opens a single-choice question card (`other: false`, `toolCallId` set so the pending `interaction_*` tool row folds into it); an answer goes back as `{ outcome: selected, optionId }`, while skip, an answer that is not an offered option, or a withdrawn card goes back as `cancelled`, which the server reports as "Interaction cancelled" on a failed tool row. Questions never ride yolo. - Controls are not hardcoded into "model / mode" buckets: `modes` come from `session/new` (each `SessionOption` keeps the adapter's `_meta.kind` — codex/claude `full_access` gets the warning glyph, names never rewritten); every other select- or boolean-type configOption goes into `controls.options` (ordered by category: model → thought_level → model_config → rest; a boolean becomes a synthetic Off/On control while `configOptionSetValue` sends a real `type: 'boolean'` value on every `set_config_option` path — a `"false"` string parses truthy on some agents — and the client advertises `session.configOptions.boolean` so adapters don't degrade booleans to selects), rendered through the shared Composer presentation adapter and switched via `setConfig(configId, value)`; native `thought_level` selects join the model panel footer instead of creating separate toolbar chips. User config/mode clicks go through `selectConfig` / `selectMode`, which overlay the pick on `view()` at once and serialize/collapse the wire requests, reverting to agent truth on failure — `agentControls` and `toRecord()` always stay agent truth. A `category=mode` configOption only stands in as modes when the protocol didn't send any (legacy Grok path); when modes exist it's a duplicate (Kimi sends both) and stays out of the control list. Every Fast shape reads as one "Fast" switch and chip (`isFastControl` / `fastOn` / `fastValue`): Devin's native `speed` Standard / Fast select, Codex's `fast-mode` and Claude's `fast` booleans, and the embedded model-name variant. `initialize` advertises the AIR `recommendedValue` capability, so claude-agent-acp drops its placeholder `default` effort row and the `default` model row whenever a concrete model matches it (the `default` model stays only when nothing matches), and reports concrete current values. A user's model switch (`setConfig` on a `model` control) re-sets the previous native effort when the new model offers it — Devin resets `thought_level` on every model change and claude-agent-acp re-seeds effort per model — and `selectConfig` holds the effort in the overlay meanwhile; `adoptControls` skips that restore because it sets the remembered effort itself right after. Claude's ultracode is an effort level the host adds: `refine_controls` appends `{ id: "ultra", name: "Ultra" }` after Max on Claude's effort select (re-inserted after every agent answer or update, the catalogue narrowing keeps it as an off-scale label) and shows `ultra` as the select's value while ultracode is on, even after `config_option_update` / `set_config_option` answers report `xhigh`, so `agentControls`, `toRecord()` and remembered prefs carry `effort: "ultra"`. `ultra` never goes out as an effort value: picking it turns ultracode on and sets wire effort `xhigh` (the highest level the model offers without one; no level, no Ultra), picking any other level turns it off and sets that level. Either switch rebuilds the live native session through session/resume or load with `_meta.claudeCode.options.settings` and re-applies model / effort / Fast / mode; the pick overlay shows the choice through it, and while a turn or background work (async task, subagent, relay round, open card) runs it is deferred to right before the next prompt goes out. A remembered `ultra` rides the first session/new; a model switch keeps Ultra (re-setting its wire effort) while the new model has an effort select and turns ultracode off otherwise (`session/ultracode.rs`, `agent-quirks.md`)
- Follow-ups sent while a turn runs are a host-side queue (`AcpSession.queued`, in-memory, in send order): each entry is staged the moment it is queued (`preparePrompt` writes the blobs, per-draft problems are reported once) so `SessionView.queued: QueuedPrompt[]` carries `Attachment`s the webview renders like a sent turn's; `flushQueued` hands the staged payload to `prompt` (`StagedSend`, `edited` only for `editTurn`). `dequeue` / `editQueued` (kept attachments by index + new drafts, replaced in place) address entries by id; `chat/Queue.tsx` shows one row per entry above the composer with a pencil (inline bare Composer) and a bin. Steering: with `acpira.steerQueued` on and `SessionView.canSteer` (the peer advertised `_meta.steering.supported`, `vendors/steering.rs`), the row's send button becomes Steer while a turn runs → `steerQueued` → `AcpSession::steer_queued` sends `_session/steering` with `idleBehavior: promptRequired`. `Core.steering_id` marks the entry sending and holds `flush_queue` (dequeue / edit / send-now refuse it) until the answer; the reply is taken with `request_ordered`, so `injected` removes the entry and pushes an `AgentBlock::Steer` (`normalize::push_steer`, sealing the streaming blocks before it) into the running turn before any later update is applied; `promptRequired` (the turn ended meanwhile) re-queues it first and flushes, an error leaves it in place with a toast. Without a running turn or support the request is the ordinary send-now. The same setting makes a composer send mid-turn steer on the spot: the webview adds `steer: true` to `send` (placeholder `composer.placeholder.steer`), and `AcpSession::steer_prompt` queues the prompt then steers that entry with the send-now fallback off, so a steer that cannot land (no support, staging, peer idle, another steer on the wire, `promptRequired`, an error) leaves an ordinary queued row and never cancels the turn; idle it is the ordinary prompt (`a_steered_composer_send_*` in `steer.rs`). No steer goes out while a compaction runs (`CompactionCompletion::running`: the turn is a /compact, or a mid-turn `compaction_update` has not ended): a steer then failed the agent's own compaction `aborted` and it started over (reported 2026-10-09), and the Steer button's send-now fallback would cancel it. Both the composer send and the button park the entry in `PromptQueue.steer_after_compaction`; when that compaction ends with the turn still running, `steer_after_compaction` steers them in send order, and a turn that settles first leaves them as ordinary follow-ups (`a_steer_during_the_agents_own_compaction_*`, fake `slow compacting`). codex-acp answers an idle steer `startedNewTurn` whatever the opt-in, so the race around a turn's end is read off its `_meta.codex.threadStatus` bracket (`steering::thread_idle`, `Core.thread_status_seen` / `peer_idle`): once the peer reported `idle` for the running turn no steer goes out (the click is send-now, i.e. queued first); a `startedNewTurn` that still slips through, on a peer that sends the bracket, marks the session `detached`: the steer block stays in the last agent turn, the session shows running (a settle meanwhile reopens that turn), the queue holds and new prompts queue, and the next `idle` settles it `end_turn` and flushes the queue. The webview keeps a steer block inside the turn's one process (no section split, so nothing before it reads as finished while the turn runs) and renders it as a user card at its place in the stream; the whole-process fold (`CodexFold`) is split around the cards (`splitAtSteers`: the first part is the root's `Collapsible.Panel`, later parts `Collapsible.Section` on the same `open`), so a closed fold leaves them under its head, ahead of the reply, the way Codex shows a steered message under its "Worked for" fold, and opening or closing slides the one card with the parts around it. Lifting a second copy out of the panel on `!open` drew the card twice for the whole 320 ms close and jumped on open (recorded in the IDE, 2026-10-07; after the split, frames at 0.1× playback in `lab/steer-fold.preview.html` via `lab/steer-fold.capture.mjs` show one card throughout; browser layout, no CLI calls) (`lab/steer-flow.preview.html`, `?auto=1` steers by itself); export writes it as a user section inside the reply, retained history context as `{ user }`. Verify with the steer cases in `tests/engine/acp_session/steer.rs` (`FAKE_STEERING=1|idle|fail|codex|codex-late|codex-gap`), `scripts/probe-steering-host.ts <claude|codex>` (real CLI) and `lab/queue.preview.html` (`?steer=0` for the old button)
- Sessions belong to a project: `SessionRecord.cwd` / `SessionSummary.cwd` is the workspace folder the session was opened in (also the agent's working directory; `homedir()` without a folder). `acpira.sessionScope` (`workspace` default | `all`, `shared/settings.ts` `SessionScope` / `inWorkspace`) decides what the list shows: the webview filters `SessionList` by `InitState.cwd` (the active session always stays listed; the settings General page writes `acpira.sessionScope`), and the host consults `ManagerDeps.scope` for the picks a viewer makes on its own (`mostRecent()` at `attach({ mostRecent })`, the next session after `deleteSession`) so a sidebar never lands on another project's conversation. Under `all`, rows from other projects carry `projectName(cwd)` (faint, `max-w-project`) before the time and a `FolderInput` "move here" hover action → `moveSession` (`SessionManager.moveSession`): a stored record is patched, a live idle session is disposed and reopened in the new folder through `selectSessionFor` (the agent is respawned there, `session/resume` / `load` carry the new cwd, unknown-id fallbacks apply), a running one refuses with `host.moveWhileRunning`. Grouped under `all`, a session dragged onto another project's group (header, loose area, or one of its categories) moves there: `moveSession { id, cwd, category? }` takes an explicit destination (absent = the window's folder), refuses a folder that no longer exists (`host.moveFolderMissing`, the agent is spawned there) and files it under `category` in the same step only when that category belongs to the destination (filing unpins); `chat/sessionTree.ts` `dropAction` decides file vs move (2026-10-08). The row's menu (the "…" dropdown and, on right-click, the same rows as a Base UI context menu: `SessionContextMenu`) offers "move to project": every other project the list knows (sessions' folders plus categories' own, the window's first, then by recency), which sends `moveSession { id, cwd }` and replaces the plain "move here" item. `lab/session-scope.preview.html` shows the tag / move; `tests/engine/session_manager/windows.rs` "workspace scope" covers the host side (project folders must exist — the fake agent is spawned in them)
- User categories (2026-10-06): `sessions/categories.json` (`SessionCategories`: `categories` in display order, each `{ id, name, cwd, collapsed? }`, plus `collapsedProjects`) is shared by every window; `TranscriptStore::update_categories` applies each `categoryOp` (create / rename / delete / collapse / reorder / collapseProject) to the disk copy under `with_file_lock`, so two windows' edits compose, and `refresh_index` (focus / ready) re-reads it and pushes `HostMsg` `categories` only when it changed. A category belongs to one project (`cwd`); `SessionRecord.category` files a session there only when the cwds match (`setSessionCategory`, `newSession { category }`). Placement is exclusive: pinning clears the category, filing unpins, `moveSession` and import clear it (a move with a destination category files it there instead), a fork keeps it. A dangling or foreign category id reads as unfiled and deleting a category rewrites no record. A view's messages run concurrently (`util::run_prefix`), so "new category… → file this session" is one message (`categoryOp` create with `file: <sessionId>`), never a create followed by a separate `setSessionCategory` that could overtake it. `tests/engine/session_manager/categories.rs` and the list-operations case of `test/sidecarContract.test.ts` cover it; `chat/sessionTree.ts` (`test/sessionTree.test.ts`) builds the webview tree
- Session deletion is soft: `SessionManager.deleteSession` removes from the list and moves the record + blobs into `sessions/trash/` for 30 s (out of the live directory, so no other window's reconcile lists it); the webview shows an undo Toast; `restoreSession` moves them back, files are really deleted on timeout or dispose, and `init` sweeps trash entries older than the window (a crash's leftovers) while leaving fresh ones another host may still undo. Deletion wins over another window that has the same session live: `TranscriptStore.write` refuses to recreate a record the store once had on disk (`knew`) and that is gone, and `SessionManager.syncIndex` treats a live session missing from the reconciled list as deleted elsewhere (`forget` + `rehome` its viewers, toast). Verify with the "live in two managers" test
- Queue UI siblings use role-prefixed keys (`plan:<sessionId>`, `queue:<sessionId>`, `composer:<sessionId>`). Sharing a session-only key leaves orphaned queue rows and duplicates them on deletion. `sendQueued` prioritizes the existing staged entry, cancels the active turn, and lets prompt completion flush it; never send a concurrent ACP prompt from the cancel notification response. Repeated send-now clicks are ignored while cancellation is pending. Verify the real App routing in `lab/queue.preview.html` and cancellation / attachment order in `tests/engine/acp_session/queue.rs`.
- Per-agent memory of the last chosen mode and config values lives in `~/.acpira/sessions/prefs.json` (`SessionManager.remember` on user `setConfig`, `rememberMode` on a user `setMode` the session then shows). Only the user's own picks are remembered: a mode the agent switches by itself (Devin's "switch to bypass mode" permission answer, Kimi leaving plan after approval, `current_mode_update` in general) stays that session's business and does not touch the memory, and a config pick keeps the remembered mode instead of capturing the session's current one. A remembered mode the agent no longer offers is skipped like any stale value. `newSession` snapshots the inheritable values before `start` (a choice made elsewhere mid-spawn must not land on the new session) and replays them through `AcpSession.adoptControls`, one `set_config_option` per differing value in control order (model before effort), skipping values the agent no longer offers. The new session shows the remembered values from its first frame: `preview_controls` paints them over the options (and, for a remembered mode, the protocol modes) an earlier session of the agent showed, and `hold_settings` pins them in the pick overlay until the replay ends, so `session/new`'s defaults never flash (Claude used to show Fable 5.1 Medium / Manual for the seconds its model / effort / mode switches took). The overlay only shows a held value the controls offer. While the hold is on, prompts queue and `adopt_controls` runs under the pick lock: a first prompt never goes out under the defaults, and a composer pick made meanwhile skips that key's replay and lands after it (`tests/engine/session_manager/prefs.rs`, fake `FAKE_CONFIG_DELAY_MS`). A queue held while no turn runs (starting, this replay, an account switch) is not shown as a queued row: `chat/heldPrompt.ts` renders its head entry as the sent user message with a working reply, and the flush hands the entry id to `Staged.id` so the recorded user turn keeps it and the bubble lands in place (reported 2026-10-03 on Claude: a new session's first message sat as a queue row over an empty transcript for ~4 s). Restored sessions keep their own persisted controls; `rebindAccount` re-adopts the same session's settings including its mode; `editTurn` restores exact per-turn settings and does not touch the memory
- Accounts are bound per session: one agent process uses one credential. Switching accounts rebinds the current session (`AcpSession.rebindAccount`: wait for the old process to exit, authenticate a replacement, then resume/load the same `acpSessionId`). Devin 3000.6.14 supports loading local sessions across accounts; a two-account round trip preserves native history and compacted context. Never clear the native session ID or serialize the entire UI transcript into the next prompt when switching accounts: long histories exceed the model window. `SessionRecord.accountId` is persisted so restored sessions keep their bound account; the chosen account also becomes the agent's default for the next new session. Running turns reject switching before changing that default. Verify with `test/accounts.test.ts` and `scripts/probe-account-switch.ts` (a one-off probe, since removed). Automatic switch on exhausted quota (`session/prompt.rs` `reserve_switch` / `switch_after_exhaustion`): only a settled turn whose error `is_quota_exhausted` (`session/errors.rs`: Devin `resource_exhausted` / -32011, AIR `quota_exhausted` or category `limit` without retry / new-session remedies, the Codex / Claude usage-limit sentences) on a session bound to a saved account reserves the session (`Core.switching`, part of `busy`, so manual switches refuse and `flush_queue` holds new prompts) under the same lock that settles it. - Workspace hooks (2026-10-08): a project's `<root>/.agents/hooks.json` (root = `shared_config::project_root`, JSONC, unknown keys rejected) gates every agent the same way, whatever its CLI does with hooks of its own — `hooks/` loads it (`context`, `beforeEdit`, `afterTurn` as a bare command or `{ run, timeout?, rounds? }`, `watch`), `hooks/run.rs` runs a command through `/bin/sh -c` (Windows `cmd /d /s /c`) in the root with `ACPIRA_PROJECT_DIR` / `CLAUDE_PROJECT_DIR` / `ACPIRA_SESSION_ID` / `ACPIRA_AGENT`, the payload on stdin, and reads the answer the way Claude Code reads its hooks (exit 2 = block with stderr; exit 0 = JSON `hookSpecificOutput.permissionDecision: deny` or `decision: block` with `reason`; any other exit, a spawn failure or the timeout — 30 s / 120 s by default, capped at `hooks::MAX_TIMEOUT` (3600 s; `Duration::from_secs_f64` panics past its range) — is a warning notice row, never a block; the payload is written while the output is read, both under the timeout, so a hook that never reads a large stdin cannot stall the gate). Denials and blocks join into one reason: below `rounds` (default 2) it pushes a `host.gateFailed` notice and sends `host.gatePrompt` as `Origin::Gate` (a reserved origin like the account-switch continue: hidden `auto` user turn with `autoReason: gate`, joined to the reply like a continue, Retry continues it); at the limit a `host.gateGaveUp` error notice and the queue flushes. A broken hooks file is logged every turn and notified once per distinct error. The gate covers a span: a turn that ends any other way (stopped, failed, `max_tokens`, out of quota, a reconnect, a context overflow) keeps its snapshot (`HookState.before`, carried while the watch list is unchanged) and its edit rows (`since`), and the next turn that finishes is gated over both. A detached turn (a steer's `startedNewTurn`, a Claude autonomous cycle) that ends `end_turn` is gated too (`hooks_after_detached`), over the edit rows after the last gate's mark (`audited`) and the snapshot that gate took (`settled`); one ending while a gate decides makes it run once more (`rerun`), and a gate blocked while a detached turn holds the session keeps its reasons for that turn's gate. Known limits: another person's edits in a shared work tree during the span (the idle time after an unfinished turn included) count as the turn's; edits a background task makes after `end_turn` outside a detached turn land in the next turn; a stopped span never prompted again is never audited; a fork / edited-history fresh peer gets no context.
