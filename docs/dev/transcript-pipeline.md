# Transcript pipeline

How ACP updates become transcript blocks: prompt staging, tool content, native import, subagents, JetBrains AIR extensions, empty completions, attachments, per-turn usage, forking and export.

- Prompt staging follows the agent's advertised `promptCapabilities` (`attachments.rs` `PromptCaps` / `promptCapsOf(init, def)`, threaded into every `preparePrompt` call: live prompt, queue staging, edit rebuild, `historyContext`): `embeddedContext: false` turns a dropped text attachment into a `text` block bracketed by `[Attachment: <name>]` / `[End of attachment: <name>]` (the blob is still saved); `image: false` drops image drafts and image files with a `host.imageUnsupported` problem unless the agent declares `imagesRegardless`. DSH and pi-acp advertise `embeddedContext: false` and reject embedded `resource` blocks. Verify with `test/pastedText.test.ts` and the `FAKE_PROMPT_CAPS=strict` cases in `tests/engine/acp_session/prompts.rs` and `edit.rs`
- Tool content is a list: `ToolCallBlock.contents?: ToolContent[]` holds every renderable item of a `tool_call_update` in wire order (a diff per `diff` item, one merged text per run of `content` items) whenever there is more than one; `content` stays the primary item (a diff wins over text) so records written before the field render unchanged, and `diffStat` sums every diff. `ToolCall.tsx` stacks `contents` with each diff under its own `source.path`; `Terminal.tsx` joins the texts. `terminal` items carry no body of their own: pi-acp streams bash output through `_meta.terminal_output.data` deltas and `_meta.terminal_exit.exit_code` (a non-zero code appends `exit code N`), codex-acp/claude-agent-acp use `_meta.terminal_output_delta` + `terminal_exit` the same way (the host advertises `clientCapabilities._meta.terminal_output_delta`), all of which `mergeTool` folds into the text content; codex-acp's completion `rawOutput { formatted_output, exit_code }` renders as its plain text instead of JSON, and a bare terminal item from an agent that expects a client terminal keeps the `host.terminalNotWired` note (replaced the moment real output arrives). `image` items (a `content` item carrying an image content block) become image contents whose base64 payloads `NormalizeState.saveImage` parks in the session blob store under the content-hash name (`AcpSession.saveImage`, capped by `MAX_OUT_IMAGE_BYTES`, mime allowlist png/jpeg/gif/webp; a refused payload degrades to a `[image: <mime>, not shown]` note), and a `resource_link` to a local image file (codex-acp's `view_image` preview) is read through `saveImageFile` into the same blob store, the link's uri kept as the caption; `agent_message_chunk` images become standalone transcript blocks that split the text run. The webview renders them via `chat/AgentImage.tsx` (blobBase URL, click to the Lightbox, Open in editor on right-click, `uri` as an openable caption). Permission requests are low-fidelity: OpenCode's `session/request_permission` embeds a `toolCall` with `kind: 'other'`, the parent directory as `title`, and both the file and its directory as `locations`, racing the real `tool_call_update`; `permissions.ts` `permissionToolUpdate` applies it only as an upgrade to an existing block (never `other` over a specific kind, locations only when there are none, title / rawInput only without a target), the whole thing when no block exists yet (Devin / Kimi plan approvals). OpenCode's `write` completes with text only (`rawOutput.output` "Wrote file successfully.", `metadata.exists: false`); `NormalizeState.pendingWrites` remembers the in_progress `rawInput.content` per tool id and, on that evidence of a new file, synthesizes an all-add diff as the primary content (an overwrite keeps the receipt text — an all-add diff would lie). Verify with `tests/engine/normalize.rs` and the `tool-downgrade` / `tool-downgrade-late` cases in `tests/engine/acp_session/permissions.rs`
- Diff sources stay out of page views (2026-10-06): the record keeps every diff's `source { path, oldText, newText }`, but `view_encoded` and `subagent_transcript` serialize inside `encode_for_view`, which writes `source` as `{ path, omitted: true }` (an edit of a large file carried both whole texts into every view; one 8.6 MB session view was 7.3 MB of them). The visible `lines` are unchanged, so expanding and scrolling render from what the view already has; `highlightDiff` falls back to tokenizing the visible segments (no whole-file grammar state). Copying the file asks the host for the full source on click: `WebviewMsg.diffSource { sessionId, toolCallId, nth, subagentId?, seq }` (nth is the diff's index among the tool call's diff items, `toolDetails.ts` `diffIndex`) is answered by `HostMsg.diffSource { seq, source? }` from `AcpSession.diff_source` (newest match first, live sessions and mirrors). Only the transcript the diff was shown in is searched: the session's visible turns, or with `subagentId` (set by the subagent inspector's `DiffSourceContext`) that child's transcript alone, since ACP keeps tool call ids unique per session only and a child may reuse its parent's (2026-10-06, `a_root_call_reusing_a_native_childs_tool_id_stays_on_the_root`), and `useCopied` hands the clipboard a `ClipboardItem` whose text is that pending promise, inside the click's user activation; a missing answer (10 s) copies the visible text. The Storage tab's slim review writes that view encoding back into old records (2026-10-15, `slimSessions` in `session_manager/storage.rs`): the record is rewritten under `hold_record` with every source `{ path, omitted: true }` (skipped when nothing would shrink), so the diff lines stay and copying the file falls back to the visible text (`AcpSession.diff_source` returns nothing for an omitted source). Pinned sessions may be slimmed; a session running, held by another engine or open in this one is not, because its transcript in memory still holds the texts and its next flush would write them back. Verify with the omitted cases in `test/code-diff.test.ts`, `diff_source_tests` in `acpira-shared/src/transcript.rs` and `permission_card_approve…` in `tests/engine/acp_session/permissions.rs`, and slimming with `storage_slim_drops_diff_texts_and_leaves_open_sessions_alone` in `tests/engine/session_manager/windows.rs`
- Image generation calls: `normalize.rs` names a tool `verbKey: 'verb.imagegen'` by identity: the `Image generation` title (codex-acp), `image_gen` / `image_edit` in `_meta["x.ai/tool"].name`, or an `imagine:` / `imagine-edit:` title (Grok). The key survives later title-less packets, and the title never becomes the target (`rawInput.prompt` / `description` does when present). A completed call with no image item gets the absolute image paths in its text results or `rawOutput` read into the blob store (`attach_saved_images`, same saver and 20 MB cap as `resource_link` images, relative paths ignored). In the webview, `shared/imageTools.ts` (`isImageGenTool` / `toolImages` / `toolTexts`) drives the row: `ImagePlus` icon, the revised prompt as its disclosure body, and `chat/GeneratedImage.tsx` renders the images. In the shared Codex-style process fold, images stay below their tool row while the fold is open, and move outside the panel only while it is closed so a collapsed history keeps the result visible; this applies to every agent, including Claude. In cursor mode they sit under the row. A call first seen running in this view gets a square `--agent-image` inset card (`bg-chip`, `--image-gen-card-shadow`) with img-fx's `ImageGeneration` mosaic in it, recoloured from the theme (`effects/imageGen.ts` / `imageGenPalette.ts`, parameters in `effects/presets.ts` `IMAGE_GEN`): `cardBg` is the opaque colour actually painted behind the card (translucent layers composited), the palette mixes `--fg-1` into it per slot with the `--image-gen-peak` colour in the highlight slot, and light paper takes lighter steps. The preset palettes shipped a fixed `#0f0f0f` card and near-white light colours, which read as a black hole on the `#181818` / `#1f1f1f` bases and vanished on light themes (with the former `strength: 0.4` on top); img-fx's default 10 fps stuttered at card size, so the frame rate is 30. On completion the card decodes the blob, takes the image's aspect ratio (--dur-open width transition), fades the mosaic out and dissolves the image in on a canvas cell by cell from the centre (`dissolveIn`, 1.2 s), then (or after a 6 s timeout) hands over to `AgentImage`, whose `box-content` border keeps the layout still. The look was picked in `lab/image-gen-fx.preview.html` (frame / loader / reveal / tone axes, with a long-task readout). The hitch when the card appeared was img-fx building its shared WebGL renderer and three linking the shader synchronously on first use (a 137 ms long task in headless Chrome 2026-09, against 0 ms for Canvas 2D loaders); img-fx also disposes that renderer with its last instance, so every card paid it again. The mosaic therefore mounts on the next idle slot rather than with the row, and `keepImageGenRenderer` parks a paused 1 px instance that keeps the renderer alive for later cards (paused instances are skipped by the render loop and the GL canvas sizing). The first card in a webview still pays the one-time build. History, replay, a remount after completion, `motion: none`, reduced motion and no WebGL (`effects/webgl.ts`, shared with metal-fx) all render the static image (placeholder: a plain / pulsing chip square). img-fx injects its own unlayered `<style>`, so its root needs `block!`; the webview CSP already allows inline styles. `three` is its peer dependency and makes up most of the bundle cost (~600 KB). - Images an agent shows the reader. (1) Reply markdown: `normalize.rs` `resolve_markdown_images` scans each `agent_message_chunk` append (from 1 KB before the new text, so syntax split across chunks is caught) for `![alt](src)` / `![alt](<src>)`, resolves file:// URLs, absolute paths and paths relative to the session cwd (`ToolCtx.cwd`), and reads image files through the same `save_image_file` saver into `TextBlock.images` (`ImageRef.uri` = the source as written; each source is tried once, an unreadable one is kept without `blob`). In the webview `fileLinks.ts` `rewriteFileHrefs` turns local `img` sources into `/__acpira-image__/<encoded>` (rehype-harden accepts `#` fragments for links only; a path-relative image URL survives sanitize and harden) and a paragraph holding one into a `div`; `Prose.tsx` `MarkdownImage` matches the decoded source against the block's images (the parser percent-encodes spaces / non-ASCII) and renders `AgentImage`, or the named no-pixels card before the file is read. (2) Acpira's MCP tool: `session_request` hands every session/new, load and resume `mcpServers: [{ name: "acpira", command: <sidecar exe>, args: ["mcp"], env: [] }]` (`host_mcp.rs`, `HostMcp` built from the runtime's executable path; no `type` field — claude-agent-acp treats only a type-less entry as stdio). `acpira mcp` is a stdio MCP server with one tool, `show_image { path | paths, caption? }`: it validates absolute, existing, image, ≤ 20 MB and answers a text receipt; the pixels never go back to the model. The tool description (not only the optional server `instructions`, which a CLI may drop) also names the Markdown route, `![caption](/abs/path.png)`, with "one or the other for a given image, never both", since doing both shows the image twice. `normalize.rs` recognizes the call by name (`SHOW_IMAGE`: claude-agent-acp 0.83.0 `name` / `title` `mcp__acpira__show_image` with the arguments as rawInput; codex-acp 1.13.0 title `mcp.acpira.show_image`, kind `execute`, rawInput `{ server, tool, arguments }`; OpenCode-style `acpira_show_image`; a bare `show_image`), sets `verbKey: 'verb.showImage'`, kind `other`, keeps the paths as `locations`, and on `completed` reads them into image contents ahead of the receipt text (`attach_shown_images`; a failed call shows none). The webview (`shared/imageTools.ts` `isShowImageTool` / `isImageResultBlock`) renders a plain row and keeps its images below that row while the process fold is open, lifting them outside only while it is closed, without the generation placeholder and without the path caption (the row names the files). A session/new that fails with the server is retried once without it and the agent is remembered per manager (`HostMcp::refuse`). Both adapter namings were read from the installed adapter sources (2026-09-30); no real CLI has called the tool yet. - HTML widgets (`show_widget`, 2026-10-22, modelled on Antigravity's generative UI). `acpira mcp` offers `show_widget { path, title? }` to every session (always, like `show_image`; `readOnlyHint`, so the built-in agent and Claude Code run it without a card): the server checks an absolute, existing `.html` / `.htm` file of at most 512 KB (`MAX_WIDGET_BYTES`) and answers a receipt; the tool description is the authoring guide (no network, inline CSS / JS, Tailwind v4 built in, the theme colour names, keep it compact, no viewport-sized layouts), the server instructions name the tool once. `normalize.rs` recognizes the call in the `show_image` namings (`SHOW_WIDGET`), sets `verbKey: 'verb.showWidget'`, kind `other`, the path as its location and the title (else the file name) as target, and on `completed` reads the file through the same file saver into the blob store (`attach_shown_widget`; the saver takes `.html` up to the widget cap besides images). The HTML is kept as an **image** content with `mimeType: 'text/html'` ahead of the receipt: a new `ToolContent` variant would make engines up to 1.10.8 refuse the whole record in the shared `~/.acpira`, while this shape is read by all of them (an old webview shows a broken image card; iOS renders no tool images at all). `shared/imageTools.ts` keeps it out of `toolImages` (`toolWidget`, `isShowWidgetTool`) and counts the row among the image results, so it sits like a shown image: under its row while the process fold is open, outside the fold once it closes (that move remounts the frame, which reloads the widget). The webview (`chat/AgentWidget.tsx`, `chat/widgetDoc.ts`) fetches the blob (retried: the write lands just after the row completes), loads Tailwind's browser build as its own chunk (`@tailwindcss/browser` `?raw`, `chat/widgetRuntime.ts`) once the widget nears the viewport, and runs `buildWidgetDoc` in a `sandbox="allow-scripts"` srcdoc frame. Checked in Chrome 156.0.8078.48 (2026-10-22) against the VS Code page CSP: srcdoc, data: and blob: frames all inherit the page's CSP, so inline scripts need the page's nonce (`pageNonce`, read from `script[nonce]`, random where the page has none: harness, LAB); every inline `<script>` of the widget gets it, a script with `src` gets none (a nonce admits external scripts from anywhere), the widget's own CSP metas and `<base>` are dropped, and our head comes first with a second CSP (`default-src 'none'; script-src 'nonce-…'; style-src 'unsafe-inline'; img-src data: blob:; …`). The widget's own `<!doctype>` / `<html>` / `<head>` that follow are merged by the parser, so a fragment and a full page both work. Inline handlers (`onclick="…"`) are blocked by any nonce CSP, so the frame's bootstrap removes each on* attribute and rebinds it through a nonce'd script, also on nodes added later (MutationObserver); Chromium still logs one CSP violation per attribute as it parses, which changes nothing. The bootstrap reports the document height (ResizeObserver → `postMessage`, accepted only from the frame's own window, capped by `max-h-widget`, which also ends the loop of a page sized to its viewport), takes theme updates from the page (`readWidgetTheme`: host tokens → `--background`, `--card`, `--primary` … read from the frame's own element, with `dark` as a class for Tailwind's `dark:` variant), so a theme or appearance switch keeps the widget's state, and keeps links from navigating the frame. The frame's own `color-scheme` matches the page inside, or Chromium paints an opaque canvas behind it. `App.tsx` ignores every message whose source is a widget frame (`isWidgetFrame`), so a widget cannot forge a host message. Verified in the LAB (`lab/show-widget.preview.html`, both themes, 360 px, open fold) with a CDP probe: oninput / onclick (with `return false`) / innerHTML handlers, a live theme switch keeping the slider value, `fetch` and `parent.document` blocked; `packages/ui/chat/widgetDoc.test.ts`, the `show_widget` host_mcp test and `the_host_show_widget_tool_reads_its_html_into_the_row_in_every_adapter_naming`. Not yet exercised: a real CLI calling the tool, a VS Code or IntelliJ webview (the CSP behaviour was reproduced in Chrome only), and a navigation of the frame in the harness, whose page has no CSP to block it.
