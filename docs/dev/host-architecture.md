# Host architecture

The sidecar protocol and the shells around the engine, the composition root, session hub, agent launching and availability, stores and accounts. The engine is Rust (`rust/`); the TypeScript under `src/host` is the VS Code shell.

- `src/shared/transcript.ts` — normalized transcript shape, the single contract between host and webview; `SessionView` is the full state pushed to the webview
- `src/shared/protocol.ts` — `HostMsg` / `WebviewMsg` message contract; `src/shared/appearance.ts` — appearance axes
- The platform seam: `rust/crates/acpira-host/src/sidecar/platform.rs` `SidecarPlatform` is what the engine asks of a shell — environment facts (`cwd`, `home`, `hostLanguage`), settings (`read_setting` / `write_setting` / `on_settings_changed`), window focus, and IDE actions that only take resolved arguments (`openResolvedFile(absPath, line1)`, `openPlanDocument({ path } | { markdown })`, `openExternal` (already allowlisted), `revealInOS`, `openInEditor(sessionId?)`, `runInTerminal(title, command, args, env?)` with `null` env values meaning delete, `toast`, `searchFiles`), each one a `PlatformRequest` envelope
- `rust/crates/acpira-host/src/runtime.rs` — `HostRuntime::create(platform, root, bridge_exe)` is the single composition root (registry, `FileVault`, `AccountStore`, `AccountManager`, `TranscriptStore`, ChatGPT store, `SessionManager`, `SettingsCenter`, host locale); it subscribes to the platform's settings / focus events (appearance → push to views, `agents` → registry swap, `hiddenOptions` → `emit_hidden`, anything else → settings emit; focus → `reprobe` + `refresh_index`) and hands out one `BridgeCore` per view. Never re-create this wiring in another entry point
- `rust/crates/acpira-host/src/bridge_core.rs` — `BridgeCore`, one per view: routes `WebviewMsg` (`ready` → `init`, `openFile` resolved against the session's `cwd`, `openPlan` through the manager's plan document + `stat`, `openExternal` behind the URL allowlist, `openPath` → reveal / open, `searchFiles` always answered, `editTurn` results, settings page requests, the rest to its viewer) and pushes changes back through `MsgBatch` (30 ms coalescing per message type, per session + subagent for `subagent`; an idle session flushes at once with whatever is pending). Transport-agnostic: `post` and `blobBase` come from whoever created the view. Verify with `test/sidecarRuntime.test.ts` (envelopes against the binary) and `tests/engine/bridge.rs`
- The VS Code / Cursor extension is a sidecar shell like the IntelliJ plugin (since 2026-09-24; before that it ran the runtime in the extension host). `src/host/extension.ts` — `activate`: merges the legacy `globalStorage` / SecretStorage tree into `~/.acpira` with `migrateOnce` (only VS Code can read SecretStorage, so this stays in the shell and runs before the sidecar starts), creates the `SidecarClient`, registers the activity-bar WebviewView, editor WebviewPanels and commands (`acpira.newSession` posts `newSession` to the sidebar view, focusing it first; `acpira.connectChatgpt` opens a tab, posts `connectChatgpt` to it and copies the first `external.connectionPrompt` it shows); `deactivate` returns the sidecar's shutdown. `src/host/bridge.ts` — `WebviewBridge`, one per webview: HTML + CSP, `asWebviewUri` of the sessions directory as the view's own `blobBase` (sent in every `attachView`, so each webview keeps its URI across a sidecar restart), relays `WebviewMsg` / `HostMsg` for its `viewId`, reloads the page when the sidecar comes back after the page initialized. `src/host/vscodePlatform.ts` — `VscodePlatform`: the hello payload (all nine capabilities, `cwd`, `vscode.env.language`, a snapshot of every `acpira.*` key the manifest declares, JSON round-tripped), `settingsChanged` / `windowFocus` / `envChanged` (workspace folders) events, and the platform requests (`vscode.open` with a 0-based `Range`, `revealFileInOS`, terminals with quoted args, `WorkspaceFiles` from `files.ts`, `writeSetting` at user scope). Only these three and `files.ts` import `vscode`
- `src/host/shell/` — the shell side of the sidecar protocol for a Node-hosted shell, no `vscode` import. `SidecarClient`: spawns the engine, sends `hello` (payload re-read on every start), queues envelopes until `helloOk` — platform events included, since the hello in flight may predate them; at `helloOk` queued events go first, then every `attachView`, then the rest, because a view reads the environment when it attaches (the outbox is never cleared by an exit, since it only holds undelivered pre-handshake traffic) — re-attaches every view on the session it last showed with its own `blobBase`, answers `platformRequest`s, restarts with backoff (1 s doubling to 30 s, `FAILED` after 5 in a row, a run over 60 s starts a new burst, `retry()` starts over), and shuts down with `shutdown` → 3 s → SIGTERM → 2 s → SIGKILL. It takes a list of candidate commands (one that cannot be spawned or exits before `helloOk` hands over to the next), but the extension only ever has one: `sidecarLocator.ts` returns `ACPIRA_SIDECAR_BIN`, else `<extension>/bin/acpira[.exe]` (every VSIX is a platform package; a lost executable bit is restored), else — a repository checkout run with F5 — `dist/sidecar/<os>-<arch>/acpira` from `pnpm build:sidecar`, else nothing (`FAILED`, "no sidecar binary for this platform"). The extension has no Node fallback. Verify with `test/sidecarClient.test.ts` (against the Rust binary)
- Sidecar (`acpira [--home DIR]`, `rust/crates/acpira-host/src/sidecar/`): the engine behind an ndjson envelope channel for the shells (the VS Code extension, the IntelliJ plugin, the browser harness). `src/shared/sidecar.ts` (mirrored in `rust/crates/acpira-shared/src/sidecar.rs`) is the wire contract (`SIDECAR_PROTOCOL_VERSION`; shell → `hello` / `attachView` / `detachView` / `webviewMessage` / `platformResponse` / `platformEvent` / `shutdown`; sidecar → `helloOk` (with `sessionsDir`, the shell serves blobs from it) / `helloReject` / `hostMessage` / `platformRequest` / `shutdownOk`). `hello` carries the shell's `capabilities` (the `PlatformRequest` methods it implements), the IDE env (`cwd`, `hostLanguage`, `blobBase` — the fallback for a view whose `attachView` carries none) and a flat `acpira.*` settings snapshot — the shell owns the settings store; `writeSetting` is an RPC to it and `settingsChanged` events bring the new snapshot back. `sidecar/platform.rs` is the platform over that channel (the RPC methods await a `platformResponse`, 30 s timeout, all pending ones fail on shutdown; the rest are notifications; an undeclared capability falls back — `searchFiles` walks the workspace with `node_files.rs`, `runInTerminal` becomes an error toast with the command line — or is logged). `sidecar/server.rs` is the per-wire state machine: a version mismatch answers `helloReject` and exits 2; control messages run strictly in order while a view's `WebviewMsg`s are dispatched in order but never awaited — each handler is polled once inline and the rest runs as its own task, so a `send` claims its turn before the next message while `stop` never queues behind the whole turn; lines that are not JSON envelopes are logged to stderr and skipped; EOF on stdin still honours the lines received before it (a shell that writes `shutdown` and closes gets `shutdownOk`). Shutdown (or EOF) ends every agent process before the sidecar exits: sessions close and kill theirs, the pool kills its idle and still-warming ones (a `take` waiting on a warming slot leaves the slot in the pool and claims it only if the same generation is still there, so `invalidate` / `dispose` keep owning the spawn; `tests/engine/agent_process.rs`), and whatever is alive after 2.5 s (`DISPOSE_GRACE`, below the shells' 3 s wait before SIGTERM) is SIGKILLed — the process exits right after, so the usual SIGTERM → 5 s → SIGKILL timer would never fire (`test/sidecarContract.test.ts`, an agent that ignores SIGTERM). Teardown first raises a closing flag that silences every sender handed to views and the platform, so a view operation failed by the teardown cannot answer after it and `shutdownOk` is the last envelope. stdout is envelopes only (logs go to stderr, agent processes get pipes); the stdio writer stops at an end marker queued after the server returns rather than waiting for every sender to drop. `acpira --ws [PORT] [--token T]` runs `sidecar/ws.rs`, a dependency-free HTTP + WebSocket server for the browser harness (one server per connection; `/webview/*`, `/host-preview/*`, `/blobs/*` served with root confinement; the token and a loopback `Origin` are required, and the page's hello `agents` is ignored). Verify with `test/hostServer.test.ts`, `test/sidecarContract.test.ts`, `test/sidecarRuntime.test.ts` and by chatting in `pnpm harness`
- The engine (`rust/`, binary `acpira`; both shells ship it): a Cargo workspace of two crates — `acpira-shared` (transcript / protocol / sidecar DTOs mirroring `src/shared`, i18n dictionaries exported from the TS source by `scripts/export-rust-i18n.ts` and pinned by a vitest check) and `acpira-host` (`acp/` the ACP client: registry, launching, process, `session*.rs` the session state machine split into lifecycle, gates, prompt / queue and controls / history editing, `normalize.rs`, subagents; `session_manager.rs`; `store/`; `accounts/`; `external/` ChatGPT mirrors; `sidecar/`). `acpira bridge <action>` is the ChatGPT bridge CLI (the connection prompt names this binary); `acpira agents [--json]` prints every built-in agent, where its CLI resolved and the exact `initialize` it gets. ACP JSON-RPC is written directly over `serde_json::Value` (no SDK: vendor extensions and unknown fields must survive). Each session is one short-held mutex; waits (prompt on the wire, permission / question cards, platform RPC) happen with it released. `SessionManager` never holds its lock across a session lock or an await; `on_change` only marks a session dirty (recording a running edge on the spot, so a turn shorter than a flush still counts as one) and one flush task serializes its view once for every viewer (first change immediately, then at most every 16 ms); the list, health and index follow on that flush. Records, index, prefs, blobs, locks and accounts are byte-compatible with the stores the TypeScript engine wrote before 2026-09-25. Tests: `cargo test --workspace` (unit tests plus `crates/acpira-host/tests/engine/`, one module per former TS suite, driving `test/fake-agent.ts` through the tsx loader; skipped without `node_modules`); `test/fixtures/engine-*.json` are golden normalize / diff output shared with the webview suites (`ACPIRA_UPDATE_FIXTURES=1 cargo test golden` rewrites them). `node scripts/bench-sidecar.mjs [runs]` measures cold start and idle RSS (2026-09-24, macOS arm64, release build: Rust 5 ms / 7.3 MB, the former Node engine 58 ms / 70.8 MB; no agent process). Distribution: `scripts/sidecar-targets.mjs` lists the six platforms (`mac` / `linux` / `windows` × `arm64` / `x86_64`; Linux is static musl, Windows links the CRT statically through `rust/.cargo/config.toml`); `pnpm build:sidecar [--all | <platform>…]` builds release binaries into `dist/sidecar/<os>-<arch>/` (Linux through `cargo zigbuild` off a matching Linux host); `node scripts/package-vsix.mjs [--all | <vsce-target>…]` stages one binary as `bin/acpira[.exe]` per `vsce package --target` (eight targets, the musl builds also serve `alpine-*`). There is no universal VSIX, so a platform without its own package (`linux-armhf`, `web`) cannot install the extension; `pnpm package` builds everything and packages this machine's target. The crate version follows `package.json` (`test/rustWorkspace.test.ts`). The IntelliJ backend picks the binary in `sidecar/SidecarLocator.kt` (see `docs/dev/intellij.md`)
- `rust/crates/acpira-host/src/session_manager.rs` — session hub (live processes, summaries); all webview actions enter here. The active session is per viewer (`Viewer`, one per webview via `attach(initial)`), so the sidebar and any number of editor tabs each show their own conversation over the shared list and process pool; `session` events go only to viewers showing that session, global events to all. `drop_empty_current` leaves a session another viewer shows alone; `delete_session` re-homes every viewer that was on it. `acpira.openInEditor` opens a fresh session unless given a session id; `acpira.openInNewWindow` opens the same tab then moves it into a fresh auxiliary window (`workbench.action.moveEditorToNewWindow`)
- `rust/crates/acpira-host/src/acp/` — `AgentRegistry` (built-in grok / devin / kimi / codex / claude / opencode / dsh / pi + user-defined via `acpira.agents`, binary probing), `AgentProcess` (spawn + ndjson JSON-RPC), `AcpSession` (`session*.rs`, state machine: start → resume | load | new → ready, with auth_required / readonly / error states), `adapter_info.rs` (adapter / bundled-engine versions read off npm `package.json` files), `normalize.rs` (`session/update` → blocks, pure functions)
- Agent order and switches: `acpira.agentOrder` / `acpira.disabledAgents` (application scope, id lists sanitized to unique trimmed strings). `SessionManager::agents()` returns the list through `shared/agentOrder.ts` `arrangeAgents` (saved ids first, the rest in registry order, external ChatGPT last; disabled agents are flagged `AgentInfo.disabled`, never dropped), so every webview list follows one order; `runtime.rs` re-pushes it through `emitAgents` when either key changes. `launchable()` feeds the plus menu, the default-agent select and the native-import picker; history, the settings rail and a disabled agent's own sessions (Retry, Notice "new session") stay available. A new session without an explicit agent goes through `pickDefaultAgent` (a disabled default falls back to the first enabled installed agent). The settings rail (`settings/Nav.tsx` `AgentRows`) reorders by pointer drag (4 px slop, click swallowed after a drop) or Alt+↑/↓ and toggles with a compact `Switch` hidden in the icon rail; both show the local result until the host's list arrives, and the last enabled agent cannot be switched off. The header's person icon (`chat/AccountPanel.tsx`) is account-only: Devin's stored logins or Grok / Kimi's read-only official account; agents with neither (OpenCode, DSH, Pi) have no person icon, and starting another agent's session is the plus menu's job (the old `selectAgent` message is gone). Verify with `test/agentOrder.test.ts` and the ordering case in `tests/engine/session_manager.rs`
- Launching: `acp/launch.rs` is pure and unit-tested from macOS. `resolve_executable` requires the execute bit on POSIX; on win32 it tries the bare name then every `PATHEXT` suffix (as given and lower-cased) and requires a regular file (a PATH directory named like the command must not resolve). `spawn_spec` routes `.cmd` / `.bat` through `ComSpec` `/d /s /c` with cross-spawn's escaping and a verbatim command line — not yet run on a real Windows machine. `AgentProcess::spawn` bounds `initialize` with `INIT_TIMEOUT` (30 s, overridable for probes) and kills the child on timeout; `KILL_GRACE` is 5 s (DSH's own teardown window). `AgentDef.requires` names helper commands that must also resolve (Pi: `pi-acp` spawns `pi`); the ones not found land in `AgentInfo.missing` and on the settings page's install description. `AgentDef.controls.ignoreModes` hides an agent's protocol modes and drops its `current_mode_update`s (pi-acp advertises its thinking levels both as modes and as `thought_level`). `AgentDef.prompt.imagesRegardless` is the per-agent override for a lying `promptCapabilities.image` (Grok). `AgentDef.adapter` marks an npm-packaged adapter (Codex / Claude): `adapterInfo.ts` finds the adapter's `package.json` near the resolved binary (realpath, ≤8 dirs up; a `.cmd` / `.ps1` shim on win32 falls back to a sibling `node_modules`) and the bundled engine's in `node_modules` from the adapter root up, so the settings facts show adapter and engine versions without launching the CLI, and an `engine.overrideEnv` value (e.g. `CODEX_PATH`) is shown instead of a version. `initialize` advertises `clientCapabilities.auth.terminal = true` (unrelated to the terminal-content capability, still false) unless the def opts out — `AgentDef.auth.terminal` / custom `acpira.agents.<id>.terminalAuth` (Devin opts out: with `ACP_BACKEND=windsurf` the ACP process ignores the local login a terminal method would write). An agent may then offer `type: 'terminal'` auth methods, mapped to `AuthMethodInfo.terminal { args, env }` — `SessionManager.login` runs them in a host terminal as `<binary> <agent args> <method args>` with `{ ...def.env, ...method.env }` and never passes the id to `authenticate` (`AcpSession.authenticate` refuses terminal ids defensively); a plain `authenticate` failure still falls back to `AgentDef.login`. Launch health is classified per agent (`AgentInventory.health`, newest wins): a spawn-time child `error` (`AgentSpawnError`) → `spawn_failed`, any other start rejection → `handshake_failed`, a `session/new` auth error → `auth_required`, reaching `ready` → `ready`; both `probeControls` and real `AcpSession` starts feed it through `manager.agentHealth` → `SettingsDeps.health`. Custom agents get the same fields (`requires`, `ignoreModes`, `prompt`), never `adapter`. Verify with `tests/engine/registry.rs`, `tests/engine/registry.rs`, `tests/engine/agent_process.rs`, `tests/engine/registry.rs`
- Agent availability is live, never a reload-time snapshot: `AgentRegistry.probeAll` / `resolveBinary` re-verify cached paths (`access X_OK`) and notify `subscribe`rs when the available set changes; `SessionManager` re-pushes `agents` on that, polls every 10 s while `registry.missing()`, and `reprobe()`s on webview `ready` and window focus (`onDidChangeWindowState`). The first `probeAll` only sets the baseline (returns false). `AgentInfo.install` (`AgentDef.install` posix / windows / docs, custom agents via `acpira.agents.<id>.install`) feeds the settings page's install section (copy, `installAgent` → `bash -c` / `powershell -Command` in a terminal, docs link); the webview drops an agent's cached inventory when its `available` flips so the facts card rescans. Verify with `tests/engine/registry.rs` and the manager poll test in `tests/engine/session_manager.rs`
- The settings page's option lists (models / thinking) only ever come over ACP: `manager.knownControls(agent)` is the newest session's `configOptions` (live or stored), so a hand-edited CLI config (a model added to `~/.kimi-code/config.toml`) is invisible until a fresh process runs `session/new`. The page's refresh button (`refreshAgent` → drops both caches → the `controls` effect re-requests with `fresh: true`) makes the host run `manager.probeControls(agent)`: `acp/probe_controls.rs` spawns a throwaway process (`initialize` + `session/new`, 20 s timeout, killed in `finally`), the result is cached in `probed` and preferred by `knownControls` / `runtimeInfo` until the next real session of that agent starts, the agent's warm slot is invalidated (`pool.invalidate(agent)`) and re-warmed so the next new session never borrows a process spawned before the change, and the bridge core re-posts `inventory` after it so the facts card shows the probe's version. Failure (no binary, auth, timeout) falls back to the last known list. Verify with the probe cases in `tests/engine/session_manager.rs` (`FAKE_MODELS` on the fake agent)
- Data root: `ACPIRA_HOME` or `~/.acpira` (`rust/crates/acpira-host/src/store/data_dir.rs`). The VS Code shell's `src/host/store/dataDir.ts` `migrateOnce` merges a legacy `globalStorage` / SecretStorage tree in once per source (`.migrated` is JSON `{ sources: [...] }`; a legacy timestamp marker means "one unknown source", and a source whose UUIDs already exist in the destination is that one). VS Code and Cursor each have their own `globalStorage` but share `~/.acpira`, so the second IDE to start still brings its sessions / accounts along; nothing in the destination is overwritten and `index.json` is not copied (the store rebuilds it). Old files are left in place
- `rust/crates/acpira-host/src/store/transcript_store.rs` — `~/.acpira/sessions` holds `index.json` + `<id>.json` + `<id>/` (attachment blobs, content-hash names) + `trash/` (soft-deleted records during their undo window); record writes are debounced, every file is written tmp + rename. The directory is shared by every extension host (each VS Code / Cursor window), so `index.json` is a cache, never the truth: `sync_index(mine, own)` re-reads it and reconciles with the record files (a file no index knows is loaded and summarized, an id without a file drops out; `mine` wins only for `own` ids — live or just patched — the disk for the rest), and `SessionManager` runs it debounced after changes plus `refresh_index()` on webview `ready` and window focus so two windows converge without a reload. Record writes are chained per id (`inflight`) and `sync_index` / `trash` / `remove` wait for writes already on their way: the save and index debounces are both 400 ms, so a fresh session's first write was regularly still mid-rename when the reconcile listed the directory, and the manager took its own brand-new session for one "deleted in another window" (toast + rehome on every new session). Verify with the two-store / two-manager tests in `tests/engine/store.rs` and `tests/engine/session_manager.rs`
- `rust/crates/acpira-host/src/accounts/` — account layer. `provider.rs` (`AccountProvider`: import_local / login / spawn_env / authenticate / quota), `account_store.rs` (metadata → `~/.acpira/accounts.json`, secrets → `FileVault` at `secrets.json` mode 600), `account_manager.rs` (import / terminal login / removal + the two session hooks), `devin.rs` (first provider). The VS Code shell keeps a TypeScript `AccountStore` / `FileVault` for the one-time legacy migration only. VS Code, Cursor and IDEA sidecars share the directory, so `accounts.json`, `secrets.json` and `sessions/prefs.json` are edited read → change → write under the shared file lock (`store/file_lock.rs`, same protocol as the shell's `store/fileLock.ts`; `with_file_lock`: `<file>.lock` created O_EXCL carrying `pid\ntoken`, in-process callers chained; a lock whose pid is dead and older than 10 s is claimed by renaming the unique `<file>.lock.<token>` generation — never the published path — then dropping the published file only if it still holds that token; release deletes the published path only when it still holds our token; 5 s wait then error; `write_atomic` tmp + rename). `AccountStore` / `FileVault` re-read the file inside the lock before every change (an id another host removed is not resurrected) onto a private snapshot published only after the write; `reload` and `mutate` share one in-process queue so a focus refresh cannot replace `items` while add/remove awaits the vault; `FileVault.get` re-reads under the lock (another host may have rotated that key), `AccountStore.reload()` runs on window focus and emits `accounts` when the list differs; `savePrefs(prefs, [agent])` replaces only that agent's `lastSettings` entry (never deletes one this window lacks) and merges its `modelShapes` per model id. Verify with `test/fileLock.test.ts` (four `tsx` processes incrementing one counter) and the two-store case in `test/accounts.test.ts`
- Official CLI quota monitoring is read-only: `accounts/local.rs` reads Grok `auth.json` and Kimi `credentials/kimi-code.json` / `device_id`, or an explicit `KIMI_CODE_API_KEY`. `LocalAccounts` publishes safe metadata through `AgentInfo.localAccount`; it never imports a switchable account or changes a session's credentials. Grok uses `cli-chat-proxy.grok.com/v1/billing?format=credits` plus `/v1/settings`; only explicit `creditUsagePercent` makes a bar, and on-demand balances are separate. Kimi uses `api.kimi.com/coding/v1/usages` for weekly and advertised short windows; custom endpoint overrides disable official credential reuse. Missing or expired credentials and unavailable percentages stay explicit states. Refresh on startup, after turns, and every minute while an account view is open; requests deduplicate and cache for 30 s. `ui/AccountLabel` shares the inline identity / plan layout, and `ui/QuotaBars` places the period, compact reset countdown badge and remaining percentage above a colored tube. Healthy allowance is green, at or below 30% amber, at or below 10% red. Multiple windows sit side by side in wide rows and stack in narrow views. Research references: [CodexBar Grok](https://github.com/steipete/CodexBar/blob/main/docs/grok.md), [CodexBar Kimi](https://github.com/steipete/CodexBar/blob/main/docs/kimi.md). Verify parsers and credential boundaries with `tests/engine/local_accounts.rs`; current-machine missing logins are not live quota success.
