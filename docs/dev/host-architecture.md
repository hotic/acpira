# Host architecture

The sidecar protocol and the shells around the engine, the composition root, session hub, agent launching and availability, stores and accounts. The engine is Rust (`rust/`); the TypeScript under `src/host` is the VS Code shell.

- Windows terminal authentication (2026-10-02, reported Acpira 1.8.0): the engine's `platform/terminal.rs` prepares one UTF-16LE `powershell.exe -NoProfile -NoExit -EncodedCommand` launch for both VS Code / Cursor and IDEA. Account-provider logins (Devin, Codex, Claude), ACP terminal methods, and registry fallbacks (Grok, Kimi, OpenCode, DSH, Pi) all use this `runInTerminal` path; non-terminal ACP `authenticate` does not. Native argv goes through `ProcessStartInfo` to preserve empty arguments and embedded quotes that PowerShell 5.1's native binder otherwise damages; CMD / BAT reuse `spawn_spec`. Environment values travel inside the encoded script, `null` removes a variable, and refreshed PATH is inherited unless explicitly overridden. The VS Code `terminalLaunch.ts` only forwards the prepared shell path and argv; Windows script construction has no TypeScript fallback. Native Windows 11 / PowerShell 5.1.26100.8115 tests passed with EXE / CMD fixtures, account env and all nine built-in login argument shapes; the previous missing `&` parser failure and Legacy argv corruption were both reproduced. Real OAuth, terminal TTY interaction and IDE button acceptance remain separate checks (`windows-compatibility.md`).

- Agent launch configuration (`store/agent_config.rs`, 2026-10-02): the engine owns `$ACPIRA_HOME/agents.json` (normally `~/.acpira/agents.json`), an object of agent ids to the former `acpira.agents` definition shape. Every VS Code / Cursor / IDEA sidecar on that machine uses the same file; `acpira agents --json [--home DIR]` reads it too. On first startup only, local IDE definitions seed a missing file under the cross-process file lock (tmp + rename, mode 600); an existing file, including `{}`, always wins. VS Code Remote windows omit the entire legacy Agent setting because its merged values cannot establish which machine supplied commands or env; custom remote agents must be configured in the new file. Migration also drops foreign-OS paths from older shells. Later IDE `agents` events never replace the registry. File edits are checked every second and on window focus; valid changes invalidate the warm pool and apply to new sessions, while malformed JSON / definitions keep the last good registry, leave the file intact and report an error without printing values. General settings → Agent launch configuration opens the engine-resolved file on the execution host. Other UI preferences remain shell settings. Evidence: gen1 / Linux, Acpira 1.7.4, Devin 3000.11.3: the same session first spawned `/home/hotic/.local/bin/devin acp`, then failed on `C:\Users\Spark\AppData\Local\devin\cli\bin\devin.exe` received as a custom definition; direct CLI discovery still found the Linux binary. Regression coverage: `store::agent_config`, `test/legacyAgents.test.ts`, `test/sidecarRuntime.test.ts`. The patched Linux x86_64 sidecar (1.8.0 working tree) was also run on gen1 in a temporary HOME / store: hello carried the reported Windows override, the resulting agents.json was `{}`, and `agents --json` resolved `/home/hotic/.local/bin/devin`; hello / shutdown succeeded without any model prompt. This did not replace the installed extension.

- Windows ACP launch (2026-10-02, reported Acpira 1.8.0): npm creates an extensionless POSIX shim alongside `.cmd` / `.ps1` entries. The resolver now accepts EXE / COM / CMD / BAT and skips the bare shim that fails with Windows error 193. `platform/command.rs` owns native command construction, `spawn_spec` and Windows argument escaping; its inputs contain no Agent registry or PATH policy. `acp::agents::launch::command` adds refreshed PATH for ACP processes and account probes. Terminal launches reuse the same platform primitives without depending on the Agent layer. `tests/windows_launch.rs` reproduces the native 193 error and completes `initialize` / `session/new` for native EXE and npm CMD entries, with spaces / Chinese paths, empty arguments, quotes, shell metacharacters and literal environment-variable syntax; all three tests passed on Windows x64 with Node 24.13.0. `scripts/test-windows.ps1` runs these checks in both push / PR CI and release CI.
- Windows discovery (2026-10-02, Devin installer / CLI 3000.11.3): `login_path` reads Machine and User registry PATH through native APIs, expands environment references and appends new directories after the IDE's inherited PATH, deduplicating Windows case / slash variants. Startup and refresh use the existing throttle. `registry.rs` also retains `%LOCALAPPDATA%/devin/cli/bin` as a Devin fallback. Native read-only regression compares the registry and Known Folder results with Windows' own APIs; no registry writes are made. A newly installed CLI can be found without restarting the IDE.
- Windows install terminals use a complete PowerShell source block directly when the request is `powershell -Command <source>`; nesting it through Bash quoting caused the reported Antigravity installer parser error. The encoded transport avoids the user's default-shell quoting rules. POSIX terminal actions retain their existing path. Installer source and native auth argv regressions live in `platform::terminal`; `test/terminalLaunch.test.ts` and `test/windowsTerminal.test.mjs` verify shell delivery. `ACPIRA_TEST_POWERSHELL` enables the PowerShell fixtures on non-Windows hosts.
- Devin's Windows installer (`cli.devin.ai/install.ps1`, manifest version 3000.11.3 on 2026-10-01) copies over `%LOCALAPPDATA%/devin/cli/bin/devin.exe`; a user report confirmed `Copy-Item` fails when the destination is in use. The registry embeds `acp/agents/install-devin.ps1` in its Windows command: fetch the official script, move an existing entry to a unique sibling, run the vendor script in a child scope, and restore the old entry if installation fails before a replacement appears. If setup fails after replacement, retain both files. Successful cleanup is best-effort; an old executable still mapped by a process can remain as `devin.exe.acpira-<guid>.old`, with its path printed in the terminal. Existing sessions are not terminated. `test/devin-install.test.ps1` runs offline against a fake vendor script; its Windows-only case reproduces `Copy-Item` failing on a running executable and checks that replacement leaves the process alive. Offline cases passed on macOS with PowerShell 7.6.6 and on Windows 11 with PowerShell 5.1.26100.8115 (2026-10-02), including replacement of a running EXE while its process stays alive. This exercises a vendor fixture, not a live update of an installed Devin.

- Windows process ownership (`platform/windows_process.rs`, 2026-10-02): each ACP child starts suspended, joins a non-inheritable kill-on-close Job Object, then resumes. Natural leader exit, explicit termination and abrupt sidecar death clean that job, including detached helpers, without a PID-based sweep. ChatGPT bridge commands share this ownership and drain final stdout / stderr after closing descendants; their CMD shell source uses raw `/d /s /c` transport. Session takeover checks native parent / executable metadata, accepts only another `acpira` sidecar's direct child and holds a process handle across revalidation / termination. Native fixtures cover all these cases and leave an unrelated process alive.

- Windows storage and file paths (2026-10-02): the shared lock probes real process handles instead of treating every holder as dead; stale-by-age locks remain held while their PID is alive. Existing-file tmp + rename replacement passes natively. `platform/file_url.rs` centralizes drive, UNC and verbatim-path conversion, percent encoding and fragment handling for attachments / file navigation. See `windows-compatibility.md` for regression coverage and remaining platform acceptance.

- `src/shared/transcript.ts` — normalized transcript shape, the single contract between host and webview; `SessionView` is the full state pushed to the webview
- `src/shared/protocol.ts` — `HostMsg` / `WebviewMsg` message contract; `src/shared/appearance.ts` — appearance axes
- The platform seam: `rust/crates/acpira-host/src/sidecar/platform.rs` `SidecarPlatform` is what the engine asks of a shell — environment facts (`cwd`, `home`, `hostLanguage`), settings (`read_setting` / `write_setting` / `on_settings_changed`), window focus, and IDE actions that only take resolved arguments (`openResolvedFile(absPath, line1)`, `openPlanDocument({ path } | { markdown })`, `openExternal` (already allowlisted), `revealInOS`, `openInEditor(sessionId?)`, `runInTerminal(title, command, args, env?)` with `null` env values meaning delete, `toast`, `searchFiles`), each one a `PlatformRequest` envelope
- `rust/crates/acpira-host/src/runtime.rs` — `HostRuntime::create(platform, root, bridge_exe)` is the single composition root (registry, `FileVault`, `AccountStore`, `AccountManager`, `TranscriptStore`, ChatGPT store, `SessionManager`, `SettingsCenter`, host locale); it subscribes to the platform's settings / focus events (appearance → push to views, `hiddenOptions` → `emit_hidden`, anything else → settings emit; focus → `reprobe` + `refresh_index`) and hands out one `BridgeCore` per view. Never re-create this wiring in another entry point
- `acpira mcp` (`host_mcp.rs`): the stdio MCP server the runtime hands every agent session (`ManagerDeps.host_mcp` → `SessionDeps.host_mcp`, built from the same executable path as the ChatGPT bridge; absent when the path is unknown). Tool `show_image`; the transcript side is in `transcript-pipeline.md`. An agent that fails session/new, resume or load carrying the server gets the same request again without it, and the refusal is remembered per agent for the life of the sidecar (`HostMcp::refuse`; restores retry since 2026-10-01, before that a restart left such sessions unrestorable)
- Cross-harness subagents (`relay/`, 2026-10-04): personas the user defines once on the settings page "Subagents" (`SettingsView.subagents`, key `subagents`), stored in `~/.acpira/subagents.json` (`relay/roster.rs`: read on demand, written tmp + rename under the file lock, `SettingsCenter.set("subagents")` writes the file instead of a host setting, so every window and IDE sidecar shares it. The page sends `{ base, personas }` (the list it showed, the list it wants; `SettingsHandlers.saveSubagents`); under the lock the save applies only what changed against that base onto the file's current list, so two windows editing different personas keep both edits, and a persona new to the page is added even when another window took its id meanwhile (renumbered). A bare list replaces the file. Other sidecars' views are not pushed the change; settings never were. `sanitize_personas` / TS `sanitizePersonas` go field by field: name + agent required, an unknown mode is a consult, ids unique slugs, text clipped; `test/fixtures/personas-sanitize.json` runs through both). The page's "Good at" field is `when`: free text listed after the persona in `ask_agent`'s description for the model to judge by (no keyword matching; naming it is `@name`); `brief` (standing instructions appended to every task) is no longer offered, and its box shows only for a persona that already stores one, since the relay still appends it. `relay/hub.rs` `RelayHub` is a loopback TCP listener the runtime starts next to `HostMcp` (`HostMcp::with_hub`): one ndjson request per connection (the line within 10 s, at most 32 connections waiting for theirs), `list` answers the enabled personas, `ask` streams `progress` lines and one `done` / `error`. Every session request carries the `acpira` MCP entry with `env` `ACPIRA_RELAY` (address) / `ACPIRA_RELAY_TOKEN`, a grant minted for that entry alone (`RelayHub::env`): the hub maps it to the session (held weakly), the summoned thread whose CLI got the entry and its depth, so a request names only its token and an op, and cannot reach another session or reset its depth. Grants go when their session does. `acpira mcp` then offers `ask_agent` next to `show_image` when the hub lists at least one persona; each call runs on its own thread (an agent may summon several children at once; the tool is annotated `readOnlyHint: true` because Claude Code 2.1.224 runs an MCP tool concurrently only then, `isConcurrencySafe` = `annotations.readOnlyHint ?? false`, and ran a message's ask_agent calls one by one before), carries `_meta` `anthropic/alwaysLoad` (+ a `searchHint`) so Claude Code (2.1.224 / agent SDK 0.3.284) keeps it out of ToolSearch, and with the relay env the server's `instructions` add that `@name` means an `ask_agent` persona, one call per agent in one message (before, a summon took ListAgents + ToolSearch first: the model saw only the deferred name and took `@name` for one of its own agents), forwards `_meta.progressToken` progress as `notifications/progress`, and waits at most 25 min for an MCP client whose `clientInfo.name` contains `claude`, else 50 s (Codex's `tool_timeout_sec` default is 60 s; the other clients' bounds are not verified), after which it answers "still working" with the thread id. The engine side is in `transcript-pipeline.md` (Cross-harness subagents)
- `rust/crates/acpira-host/src/bridge_core.rs` — `BridgeCore`, one per view: routes `WebviewMsg` (`ready` → `init`, `openFile` resolved against the session's `cwd`, `openPlan` through the manager's plan document + `stat`, `openExternal` behind the URL allowlist, `openPath` → reveal / open, `searchFiles` always answered, `editTurn` results, `diffSource` (a diff's full file texts, `docs/dev/transcript-pipeline.md`), settings page requests, the rest to its viewer) and pushes changes back through `MsgBatch` (30 ms coalescing per message type, per session + subagent for `subagent`; an idle session flushes at once with whatever is pending); a session view leaving the batch goes out as a `sessionPatch` against the last view that page was sent of the same session (`SentViews`, the most recent sessions are kept) when the page asked for patches (`docs/dev/webview.md`). Transport-agnostic: `post` and `blobBase` come from whoever created the view. Verify with `test/sidecarRuntime.test.ts` (envelopes against the binary) and `tests/engine/bridge.rs`
- The VS Code / Cursor extension is a sidecar shell like the IntelliJ plugin (since 2026-09-24; before that it ran the runtime in the extension host). `src/host/extension.ts` — `activate`: merges the legacy `globalStorage` / SecretStorage tree into `~/.acpira` with `migrateOnce` (only VS Code can read SecretStorage, so this stays in the shell and runs before the sidecar starts), creates the `SidecarClient`, registers the activity-bar WebviewView, editor WebviewPanels and commands (`acpira.newSession` posts `newSession` to the sidebar view, focusing it first; `acpira.connectChatgpt` opens a tab, posts `connectChatgpt` to it and copies the first `external.connectionPrompt` it shows); `deactivate` returns the sidecar's shutdown. `src/host/bridge.ts` — `WebviewBridge`, one per webview: HTML + CSP, `asWebviewUri` of the sessions directory as the view's own `blobBase` (sent in every `attachView`, so each webview keeps its URI across a sidecar restart), relays `WebviewMsg` / `HostMsg` for its `viewId`, reloads the page when the sidecar comes back after the page initialized. `src/host/vscodePlatform.ts` — `VscodePlatform`: the hello payload (all nine capabilities, `cwd`, `vscode.env.language`, a snapshot of every `acpira.*` key the manifest declares, JSON round-tripped), `settingsChanged` / `windowFocus` / `envChanged` (workspace folders) events, and the platform requests (`vscode.open` with a 0-based `Range`, `revealFileInOS`, terminals with quoted args, `WorkspaceFiles` from `files.ts`, `writeSetting` at user scope). Only these three and `files.ts` import `vscode`
- Shell-originated host messages: `editorSelection` (the live editor selection, absent = cleared), `addSelection` (the editor context menu / palette command `acpira.addSelection`, the caret's line when nothing is selected) and `editorCopy` (a copy in a `file:` editor) are `HostMsg`s the shells build themselves; the sidecar never sees them. `src/host/editorSelection.ts` (no `vscode` import, so `test/editorSelection.test.ts` runs it) turns a 0-based range into the 1-based inclusive `EditorSelection` — a range ending at column 0 of a later line leaves that line out, blank or over-`MAX_TEXT_BYTES` text is not offered. `extension.ts` debounces selection changes 150 ms and broadcasts to every bridge only while `acpira.shareEditorSelection` is on (default on; turning it off sends one clear); focus moving into the chat does not clear it, switching to another editor or closing its document does (the close also cancels a pending debounce, and a closed document is never read). `addSelection` goes to the chat used last, whatever the setting: the page posts `viewFocus` on window focus (intercepted by `WebviewBridge`, a no-op if it reaches the sidecar), and an editor tab turning active or the sidebar becoming visible count too, because clicking into an already visible view changes nothing VS Code reports; editor tabs are revealed through their panel, the sidebar is focused. The last `editorCopy` is kept and replayed with the selection to every page that initializes (a tab opened after the copy, a reload after a sidecar restart). Copies are observed through a `DocumentPasteEditProvider` that only implements `prepareDocumentPaste` (`providedPasteEditKinds: []`, a private copy MIME type), so it never offers a paste edit of its own; whether VS Code calls it for every copy was not confirmed in a live editor. `WebviewBridge.postShell` queues these until the page's `init` (only the latest `editorSelection` is kept) and resets that gate when the page reloads for a sidecar restart
- `src/host/shell/` — the shell side of the sidecar protocol for a Node-hosted shell, no `vscode` import. `SidecarClient`: spawns the engine, sends `hello` (payload re-read on every start), queues envelopes until `helloOk` — platform events included, since the hello in flight may predate them; at `helloOk` queued events go first, then every `attachView`, then the rest, because a view reads the environment when it attaches (the outbox is never cleared by an exit, since it only holds undelivered pre-handshake traffic) — re-attaches every view on the session it last showed with its own `blobBase`, answers `platformRequest`s, restarts with backoff (1 s doubling to 30 s, `FAILED` after 5 in a row, a run over 60 s starts a new burst, `retry()` starts over), and shuts down with `shutdown` → 3 s → SIGTERM → 2 s → SIGKILL. It takes a list of candidate commands (one that cannot be spawned or exits before `helloOk` hands over to the next), but the extension only ever has one: `sidecarLocator.ts` returns `ACPIRA_SIDECAR_BIN`, else `<extension>/bin/acpira[.exe]` (every VSIX is a platform package; a lost executable bit is restored), else — a repository checkout run with F5 — `dist/sidecar/<os>-<arch>/acpira` from `pnpm build:sidecar`, else nothing (`FAILED`, "no sidecar binary for this platform"). The extension has no Node fallback. Verify with `test/sidecarClient.test.ts` (against the Rust binary)
- Sidecar (`acpira [--home DIR]`, `rust/crates/acpira-host/src/sidecar/`): the engine behind an ndjson envelope channel for the shells (the VS Code extension, the IntelliJ plugin, the browser harness). `src/shared/sidecar.ts` (mirrored in `rust/crates/acpira-shared/src/sidecar.rs`) is the wire contract (`SIDECAR_PROTOCOL_VERSION`; shell → `hello` / `attachView` / `detachView` / `webviewMessage` / `platformResponse` / `platformEvent` / `shutdown`; sidecar → `helloOk` (with `sessionsDir`, the shell serves blobs from it) / `helloReject` / `hostMessage` / `platformRequest` / `shutdownOk`). `hello` carries the shell's `capabilities` (the `PlatformRequest` methods it implements), the IDE env (`cwd`, `hostLanguage`, `blobBase` — the fallback for a view whose `attachView` carries none) and a flat `acpira.*` settings snapshot — the shell owns UI preferences and supplies legacy Agent definitions only for initial migration; `writeSetting` is an RPC to it and `settingsChanged` events bring the new snapshot back. `sidecar/platform.rs` is the platform over that channel (the RPC methods await a `platformResponse`, 30 s timeout, all pending ones fail on shutdown; the rest are notifications; an undeclared capability falls back — `searchFiles` walks the workspace with `node_files.rs`, `runInTerminal` becomes an error toast with the command line — or is logged). `sidecar/server.rs` is the engine (one runtime) behind its wires; over stdio and for each harness connection the engine is *attached* to exactly one wire and ends with it: a version mismatch answers `helloReject` and exits 2; control messages run strictly in order while a view's `WebviewMsg`s are dispatched in order but never awaited — each handler is polled once inline and the rest runs as its own task, so a `send` claims its turn before the next message while `stop` never queues behind the whole turn; lines that are not JSON envelopes are logged to stderr and skipped; EOF on stdin still honours the lines received before it (a shell that writes `shutdown` and closes gets `shutdownOk`). Shutdown (or EOF) ends every agent process before the sidecar exits: sessions close and kill theirs, the pool kills its idle and still-warming ones (a `take` waiting on a warming slot leaves the slot in the pool and claims it only if the same generation is still there, so `invalidate` / `dispose` keep owning the spawn; `tests/engine/agent_process.rs`), and whatever is alive after 2.5 s (`DISPOSE_GRACE`, below the shells' 3 s wait before SIGTERM) is SIGKILLed — the process exits right after, so the usual SIGTERM → 5 s → SIGKILL timer would never fire (`test/sidecarContract.test.ts`, an agent that ignores SIGTERM). Teardown first raises a closing flag that silences every sender handed to views and the platform, so a view operation failed by the teardown cannot answer after it and `shutdownOk` is the last envelope. stdout is envelopes only (logs go to stderr, agent processes get pipes); the stdio writer stops at an end marker queued after the server returns rather than waiting for every sender to drop. `acpira --ws [PORT] [--token T]` runs `sidecar/ws.rs`, a dependency-free HTTP + WebSocket server for the browser harness (one server per connection; `/webview/*`, `/host-preview/*`, `/blobs/*` served with root confinement; the token and a loopback `Origin` are required, and the page's hello `agents` is ignored). Verify with `test/hostServer.test.ts`, `test/sidecarContract.test.ts`, `test/sidecarRuntime.test.ts` and by chatting in `pnpm harness`
- Persistent engine (`acpira serve --socket PATH [--idle-grace S]`, Unix only, since 2026-10-05): the VS Code shell's default on macOS / Linux; Windows and `ACPIRA_ENGINE=stdio` keep the attached stdio sidecar, and the IntelliJ plugin still runs one attached sidecar per project. Motivation, observed over Remote-SSH with Devin on acpira 1.8.5: the laptop slept, the reconnect needed a window reload, the new extension host started a second sidecar, its `session/resume` met Devin's `session_locked` held by the first sidecar's agent (still alive, VS Code Server keeps an orphaned extension host for its reconnection grace), and "Take over" killed the turn; the reopened record showed the turn interrupted (`restore_interrupted_turns`). Now sessions live in an engine that is not a child of any window. `src/host/shell/engine.ts` derives the socket from the real binary's path / size / mtime, ACPIRA_HOME and the workspace folder (`<home>/run/engine-<16 hex>.sock`, or `<tmp>/acpira-<uid>/` when that path exceeds 100 bytes; directories forced to mode 700 and owned by the user, checked before connecting as well as by `serve` before it binds), connects, and when nothing listens spawns `acpira serve --socket … <args>` detached (own session, stdin ignored, stdout / stderr appended to `<home>/run/engine-<key>.log`, rotated at 4 MB) and polls the socket for up to 15 s. The engine takes an OS lock on `<socket stem>.lock` for its whole life (a second launcher waits up to 10 s for an ending engine, then exits 0 and the shell reaches the winner), removes a stale socket file and binds with mode 600. Each connection is a wire with the stdio protocol; a wire's EOF or `shutdown` (answered with `shutdownOk`) only detaches its views and fails the platform RPCs routed to it; IDE actions go to the wire that last said hello, sent a view message or reported window focus, and a later hello re-binds the platform's capabilities, env and settings snapshot (a key that differs fires `settingsChanged`). View ids are per wire. `SidecarClient` treats a closed connection like an exited process (reconnect with backoff, re-attach every view on its last session) and `dispose` only ends the connection, so closing / reloading a window or quitting VS Code leaves turns running; a `helloReject` saying the engine is shutting down reconnects instead of failing. The engine ends once it has had no wire and no running turn for the grace (30 s default, 3 h when `SSH_CONNECTION` / `SSH_CLIENT` is set to match VS Code Server's 10800 s reconnection grace: a reconnected Remote-SSH window is a new macOS security session with the login keychain locked again, so only the engine unlocked under the earlier connection still reads Claude Code's login; observed 2026-10-06 on acpira 1.8.7, where the engine ended 30 s after the drop and the reconnected window's new engine found the keychain locked; an explicit `--idle-grace` wins; a permission card or question waiting on the user keeps the turn running, so the engine waits for it): the decision is taken under the runtime-creation lock that a hello holds until its wire is registered, after which every hello is refused with "shutting down" (the shell reconnects and launches the next engine), the socket is removed and the engine tears down like an attached engine; a teardown waits for a runtime being created. The engine never holds its own state lock while calling into the runtime, since platform calls come back through it. Upgrades are blue-green: a new binary means a new socket and engine, the old one drains its turns and ends. Cross-engine safety is `store/session_lease.rs`: an engine holds a `File::try_lock` on `<home>/run/leases/<session>.lock` for every session it has open (live), so a session is driven from one engine at a time, like Devin's native session lock but for every agent. `SessionManager.load_session` claims before it reads the record; another engine's lease gives a mirror instead of an agent — `AcpSession::mirror`, readonly with `host.sessionElsewhere` and `canTakeOver`, turns as that engine last saved them (not sealed as interrupted), inert deps that never save, revs counting up from −2⁴⁰ so pages accept each copy and the live session (rev 0 up) after it — re-read every second when the record's mtime changed, and opened normally once the lease is free (that engine closed the session or ended). Take over (`takeOverSession` on a mirror) writes `<id>.takeover` naming the requesting engine (a random token per manager; ignored after 15 s); the holder polls its leases every 500 ms, cancels a running turn (up to 3 s to settle), flushes, closes the session, shows its viewers a mirror with `host.sessionTakenOver` (which can take it back) and lets go; the requester waits up to 10 s for the lease (`host.takeOverTimeout`), clears the request and opens the session. A mirror does not reopen by itself while a takeover request from another engine is fresh. Turns, historical edits, loads and record edits claim numbered pins on top of that (a turn's pin lives on the session as `lease_pin`, set under the core lock together with `running` and handed back after its final flush succeeded; a failed flush keeps the lease and retries with backoff up to 30 s); a lease file that cannot be opened or locked is `Claim::Failed`, which refuses turns with `host.sessionLeaseFailed` and opens stored sessions read-only. Rename / pin / delete / move are refused on a mirror and wait up to 2 s for another engine's short hold; a failed edit save is reported. `TranscriptStore::set_write_guard` skips every record write while another engine holds the session. Files, pins and the last synced set share one mutex; the lease root is `ManagerDeps.lease_root` (ACPIRA_HOME; tests use a directory inside their own temp dir). Known limits: an engine keeps every session it ever opened leased until it ends, so another workspace needs a takeover even for a session nobody looks at any more; the engine keeps the environment of the extension host that launched it (an `SSH_AUTH_SOCK` from an earlier connection goes stale for agents spawned later). Record writes are chained per id (`inflight`) and `sync_index` / `trash` / `remove` wait for writes already on their way: the save and index debounces are both 400 ms, so a fresh session's first write was regularly still mid-rename when the reconcile listed the directory, and the manager took its own brand-new session for one "deleted in another window" (toast + rehome on every new session). A record file that does not parse is remembered with its (size, mtime) and skipped by later syncs until the file changes: one truncated at exactly 512 KB was re-read and logged as unreadable six times in the first 10 s of a window (2026-10-04). `knownControls` / a new session's first chips read a stored record through `load_controls`, which parses only `id` and `controls` and skips the transcript. Verify with the two-store / two-manager tests in `tests/engine/store.rs` and `tests/engine/session_manager/windows.rs`
- `rust/crates/acpira-host/src/store/session_search.rs` — the history list's conversation search (`searchSessions { query, seq }` → `sessionHits { seq, hits: [{ id, snippet }] }`, always answered). Only user prompts, steered messages and agent `text` blocks are indexed (tool output, thoughts, plans and attachments are not); every whitespace-separated term must occur, case-insensitively, in the record's title or conversation, and a session whose terms all sit in its title is left to the webview's own title / agent-name match. `SessionSearch` (one per `SessionManager`) caches each record's extracted text keyed by the file's mtime + size and revalidates against the directory on every search on the blocking pool, so other windows' writes are picked up and a typed query parses each record once; hits are capped at 200, most recently written first. A streaming reply is found once the save debounce has written it; ChatGPT mirrors have no record and match by title only. Verify with `history_search_reads_saved_conversations_and_follows_later_writes` in `tests/engine/store.rs` and the `searchSessions` case in `test/sidecarContract.test.ts`
