# Host architecture

The platform seam, composition root, sidecar, session hub, agent launching and availability, stores and accounts under `src/host`.

- `src/shared/transcript.ts` — normalized transcript shape, the single contract between host and webview; `SessionView` is the full state pushed to the webview
- `src/shared/protocol.ts` — `HostMsg` / `WebviewMsg` message contract; `src/shared/appearance.ts` — appearance axes
- `src/host/platform.ts` — `HostPlatform`, what a host application provides: environment facts (`cwd`, `home`, `hostLanguage`), settings storage (`readSetting` / `writeSetting` / `onSettingsChanged`), `onWindowFocus`, and IDE actions that only take resolved arguments (`openResolvedFile(absPath, line1)`, `openPlanDocument({ path } | { markdown })`, `openExternal` (already allowlisted), `revealInOS`, `openInEditor(sessionId?)`, `runInTerminal(title, command, args, env?)` with `null` env values meaning delete, `toast`, `searchFiles`), plus an optional `legacy` tree to migrate. Nothing in it imports `vscode`
- `src/host/runtime.ts` — `createHostRuntime(platform)` is the single composition root (registry, `FileVault`, `AccountStore`, `AccountManager`, `TranscriptStore`, `SessionManager`, `SettingsCenter`, `migrateOnce` when the platform declares a legacy source, `setHostLocale`); it subscribes to the platform's settings / focus events (appearance → push to views, `agents` → registry swap, `hiddenOptions` → `emitHidden`, anything else → `settings.emit`) and hands out one `BridgeCore` per view through `attachView` / `detachView`. Never re-create this wiring in another entry point — the VS Code extension and the sidecar both call it
- `src/host/bridgeCore.ts` — `BridgeCore`, one per view: routes `WebviewMsg` (`ready` → `init`, `openFile` resolved against the session's `cwd`, `openPlan` through `manager.planDocument` + `stat`, `openExternal` behind `isSafeExternalUrl`, `openPath` → reveal / open, `searchFiles` always answered, `editTurn` results, settings page requests, the rest to its `SessionViewer`) and pushes changes back through `HostMsgBatch` (30 ms coalescing, idle sessions flush at once). Transport-agnostic: `post` and `blobBase` come from whoever created the view. Verify with `test/hostRuntime.test.ts` (fake platform)
- `src/host/vscodePlatform.ts` — `VscodePlatform`: the `HostPlatform` over the vscode module (configuration, terminals, `vscode.open` with a 0-based `Range`, `revealFileInOS`, the `acpira.openInEditor` command, `WorkspaceFiles`, the `globalStorage` / SecretStorage legacy source). `src/host/files.ts` (`findFiles` index) stays vscode-specific behind it
- `src/host/extension.ts` — `activate`: builds `VscodePlatform` + `createHostRuntime`, registers the activity-bar WebviewView, editor WebviewPanel and commands; `src/host/bridge.ts` — `WebviewBridge`, the vscode.Webview wrapper (HTML + CSP + `asWebviewUri`, `postMessage`) around a `BridgeCore`. Only these two, `vscodePlatform.ts` and `files.ts` import `vscode`
- Sidecar (`src/host/server.ts` → `dist/host-server.cjs`, not `external: vscode`, so a stray import fails the build): the same runtime behind an ndjson envelope channel for shells that are not VS Code (the IntelliJ plugin). `src/shared/sidecar.ts` is the wire contract (`SIDECAR_PROTOCOL_VERSION`; shell → `hello` / `attachView` / `detachView` / `webviewMessage` / `platformResponse` / `platformEvent` / `shutdown`; sidecar → `helloOk` (with `sessionsDir`, the shell serves blobs from it) / `helloReject` / `hostMessage` / `platformRequest` / `shutdownOk`). `hello` carries the shell's `capabilities` (the `PlatformRequest` methods it implements), the IDE env (`cwd`, `hostLanguage`, `blobBase`) and a flat `acpira.*` settings snapshot — the shell owns the settings store; `writeSetting` is an RPC to it and `settingsChanged` events bring the new snapshot back. `sidecar/SidecarPlatform.ts` is the `HostPlatform` over that channel (RPC methods in `PLATFORM_RPC_METHODS` await a `platformResponse`, 30 s timeout, all pending ones fail on shutdown; the rest are notifications; an undeclared capability falls back — `searchFiles` walks the workspace with `nodeFiles.ts`, `runInTerminal` becomes an error toast with the command line — or is logged). `sidecar/SidecarServer.ts` is the per-wire state machine: a version mismatch answers `helloReject` and exits 2; control messages run strictly in order while a view's `WebviewMsg`s are dispatched in order but never awaited (a `send` resolves at turn end, `stop` must not queue behind it); lines that are not JSON envelopes are logged to stderr and skipped; EOF on stdin still honours the lines received before it (a shell that writes `shutdown` and closes gets `shutdownOk`). stdout is envelopes only: `console.log` is redirected to stderr at startup and agent processes are spawned with pipes. `--ws [port]` runs `sidecar/ws.ts`, a dependency-free HTTP + WebSocket server for the browser harness (one `SidecarServer` per connection; `/webview/*`, `/host-preview/*`, `/blobs/*` served with root confinement). Verify with `test/hostServer.test.ts` (spawns `tsx --tsconfig tsconfig.host.json src/host/server.ts` — plain `tsx` cannot resolve `@shared/*` because the root tsconfig has no `paths`) and by chatting in `pnpm harness`
- `src/host/SessionManager.ts` — session hub (live processes, summaries); all webview actions enter here; must not import `vscode`. The active session is per viewer (`SessionViewer`, one per webview via `manager.attach(initial)`), so the sidebar and any number of editor tabs each show their own conversation over the shared list and process pool; `session` events go only to viewers showing that session, global events to all. `dropEmptyCurrent` leaves a session another viewer shows alone; `deleteSession` re-homes every viewer that was on it. The single-view API (`activeId` / `active()` / `handle()` / `newSession()`) is a lazily created default viewer for tests and scripts. `acpira.openInEditor` opens a fresh session unless given a session id; `acpira.openInNewWindow` opens the same tab then moves it into a fresh auxiliary window (`workbench.action.moveEditorToNewWindow`)
- `src/host/acp/` — `AgentRegistry` (built-in grok / devin / kimi / codex / claude / opencode / dsh / pi + user-defined via `acpira.agents`, binary probing), `AgentProcess` (spawn + ndjson + `acp.client`), `AcpSession` (state machine: start → resume | load | new → ready, with auth_required / readonly / error states), `adapterInfo.ts` (adapter / bundled-engine versions read off npm `package.json` files), `normalize.ts` (`session/update` → blocks, pure functions)
- Agent order and switches: `acpira.agentOrder` / `acpira.disabledAgents` (application scope, id lists sanitized to unique trimmed strings). `SessionManager.agents()` returns the list through `shared/agentOrder.ts` `arrangeAgents` (saved ids first, the rest in registry order, external ChatGPT last; disabled agents are flagged `AgentInfo.disabled`, never dropped), so every webview list follows one order; `runtime.ts` re-pushes it through `emitAgents` when either key changes. `launchable()` feeds the plus menu, the default-agent select and the native-import picker; history, the settings rail and a disabled agent's own sessions (Retry, Notice "new session") stay available. A new session without an explicit agent goes through `pickDefaultAgent` (a disabled default falls back to the first enabled installed agent). The settings rail (`settings/Nav.tsx` `AgentRows`) reorders by pointer drag (4 px slop, click swallowed after a drop) or Alt+↑/↓ and toggles with a compact `Switch` hidden in the icon rail; both show the local result until the host's list arrives, and the last enabled agent cannot be switched off. The header's person icon (`chat/AccountPanel.tsx`) is account-only: Devin's stored logins or Grok / Kimi's read-only official account; agents with neither (OpenCode, DSH, Pi) have no person icon, and starting another agent's session is the plus menu's job (the old `selectAgent` message is gone). Verify with `test/agentOrder.test.ts` and the ordering case in `test/SessionManager.test.ts`
- Launching: `acp/launch.ts` is pure and unit-tested from macOS. `resolveExecutable` requires the execute bit on POSIX; on win32 it tries the bare name then every `PATHEXT` suffix (as given and lower-cased) and requires a regular file (a PATH directory named like the command must not resolve). `spawnSpec` routes `.cmd` / `.bat` through `ComSpec` `/d /s /c` with cross-spawn's escaping and `windowsVerbatimArguments` — not yet run on a real Windows machine. `AgentProcess.spawn` bounds `initialize` with `INIT_TIMEOUT_MS` (30 s, `opts.initTimeoutMs` for probes) and kills the child on timeout; `KILL_GRACE_MS` is 5 s (DSH's own teardown window). `AgentDef.requires` names helper commands that must also resolve (Pi: `pi-acp` spawns `pi`); the ones not found land in `AgentInfo.missing` and on the settings page's install description. `AgentDef.controls.ignoreModes` hides an agent's protocol modes and drops its `current_mode_update`s (pi-acp advertises its thinking levels both as modes and as `thought_level`). `AgentDef.prompt.imagesRegardless` is the per-agent override for a lying `promptCapabilities.image` (Grok). `AgentDef.adapter` marks an npm-packaged adapter (Codex / Claude): `adapterInfo.ts` finds the adapter's `package.json` near the resolved binary (realpath, ≤8 dirs up; a `.cmd` / `.ps1` shim on win32 falls back to a sibling `node_modules`) and the bundled engine's in `node_modules` from the adapter root up, so the settings facts show adapter and engine versions without launching the CLI, and an `engine.overrideEnv` value (e.g. `CODEX_PATH`) is shown instead of a version. `initialize` advertises `clientCapabilities.auth.terminal = true` (unrelated to the terminal-content capability, still false) unless the def opts out — `AgentDef.auth.terminal` / custom `acpira.agents.<id>.terminalAuth` (Devin opts out: with `ACP_BACKEND=windsurf` the ACP process ignores the local login a terminal method would write). An agent may then offer `type: 'terminal'` auth methods, mapped to `AuthMethodInfo.terminal { args, env }` — `SessionManager.login` runs them in a host terminal as `<binary> <agent args> <method args>` with `{ ...def.env, ...method.env }` and never passes the id to `authenticate` (`AcpSession.authenticate` refuses terminal ids defensively); a plain `authenticate` failure still falls back to `AgentDef.login`. Launch health is classified per agent (`AgentInventory.health`, newest wins): a spawn-time child `error` (`AgentSpawnError`) → `spawn_failed`, any other start rejection → `handshake_failed`, a `session/new` auth error → `auth_required`, reaching `ready` → `ready`; both `probeControls` and real `AcpSession` starts feed it through `manager.agentHealth` → `SettingsDeps.health`. Custom agents get the same fields (`requires`, `ignoreModes`, `prompt`), never `adapter`. Verify with `test/launch.test.ts`, `test/AgentRegistry.test.ts`, `test/AgentProcess.test.ts`, `test/adapterInfo.test.ts`
- Agent availability is live, never a reload-time snapshot: `AgentRegistry.probeAll` / `resolveBinary` re-verify cached paths (`access X_OK`) and notify `subscribe`rs when the available set changes; `SessionManager` re-pushes `agents` on that, polls every 10 s while `registry.missing()`, and `reprobe()`s on webview `ready` and window focus (`onDidChangeWindowState`). The first `probeAll` only sets the baseline (returns false). `AgentInfo.install` (`AgentDef.install` posix / windows / docs, custom agents via `acpira.agents.<id>.install`) feeds the settings page's install section (copy, `installAgent` → `bash -c` / `powershell -Command` in a terminal, docs link); the webview drops an agent's cached inventory when its `available` flips so the facts card rescans. Verify with `test/AgentRegistry.test.ts` and the SessionManager poll test
- The settings page's option lists (models / thinking) only ever come over ACP: `manager.knownControls(agent)` is the newest session's `configOptions` (live or stored), so a hand-edited CLI config (a model added to `~/.kimi-code/config.toml`) is invisible until a fresh process runs `session/new`. The page's refresh button (`refreshAgent` → drops both caches → the `controls` effect re-requests with `fresh: true`) makes the host run `manager.probeControls(agent)`: `acp/probeControls.ts` spawns a throwaway process (`initialize` + `session/new`, 20 s timeout, killed in `finally`), the result is cached in `probed` and preferred by `knownControls` / `runtimeInfo` until the next real session of that agent starts, the agent's warm slot is invalidated (`pool.invalidate(agent)`) and re-warmed so the next new session never borrows a process spawned before the change, and `bridgeCore` re-posts `inventory` after it so the facts card shows the probe's version. Failure (no binary, auth, timeout) falls back to the last known list. Verify with the `probeControls` cases in `test/SessionManager.test.ts` (`FAKE_MODELS` on the fake agent)
- `src/host/store/dataDir.ts` — `ACPIRA_HOME` or `~/.acpira`; `migrateOnce` merges a legacy `globalStorage` / SecretStorage tree in once per source (`.migrated` is JSON `{ sources: [...] }`; a legacy timestamp marker means "one unknown source", and a source whose UUIDs already exist in the destination is that one). VS Code and Cursor each have their own `globalStorage` but share `~/.acpira`, so the second IDE to start still brings its sessions / accounts along; nothing in the destination is overwritten and `index.json` is not copied (the store rebuilds it). Old files are left in place
- `src/host/store/TranscriptStore.ts` — `~/.acpira/sessions` holds `index.json` + `<id>.json` + `<id>/` (attachment blobs, content-hash names) + `trash/` (soft-deleted records during their undo window); record writes are debounced, every file is written tmp + rename. The directory is shared by every extension host (each VS Code / Cursor window), so `index.json` is a cache, never the truth: `syncIndex(mine, own)` re-reads it and reconciles with the record files (a file no index knows is loaded and summarized, an id without a file drops out; `mine` wins only for `own` ids — live or just patched — the disk for the rest), and `SessionManager` runs it debounced after changes plus `refreshIndex()` on webview `ready` and window focus so two windows converge without a reload. Record writes are chained per id (`inflight`) and `syncIndex` / `trash` / `remove` wait for writes already on their way: the save and index debounces are both 400 ms, so a fresh session's first write was regularly still mid-rename when the reconcile listed the directory, and the manager took its own brand-new session for one "deleted in another window" (toast + rehome on every new session). Verify with the two-store / two-manager tests in `test/TranscriptStore.test.ts` and `test/SessionManager.test.ts`
- `src/host/accounts/` — account layer. `types.ts` (`AccountProvider`: importLocal / login / spawnEnv? / authenticate?), `AccountStore` (metadata → `~/.acpira/accounts.json`, secrets → `SecretVault`: `FileVault` at `secrets.json` mode 600, `MemoryVault` in tests), `AccountManager` (import / terminal login / removal + two hooks for `AcpSession`), `devin.ts` (first provider). Must not import `vscode`. VS Code, Cursor and IDEA sidecars share the directory, so `accounts.json`, `secrets.json` and `sessions/prefs.json` are edited read → change → write under `store/fileLock.ts` (`withFileLock`: `<file>.lock` created O_EXCL carrying `pid\ntoken`, in-process callers chained; a lock whose pid is dead and older than 10 s is claimed by renaming the unique `<file>.lock.<token>` generation — never the published path — then dropping the published file only if it still holds that token; release deletes the published path only when it still holds our token; 5 s wait then error; `writeAtomic` tmp + rename). `AccountStore` / `FileVault` re-read the file inside the lock before every change (an id another host removed is not resurrected) onto a private snapshot published only after the write; `reload` and `mutate` share one in-process queue so a focus refresh cannot replace `items` while add/remove awaits the vault; `FileVault.get` re-reads under the lock (another host may have rotated that key), `AccountStore.reload()` runs on window focus and emits `accounts` when the list differs; `savePrefs(prefs, [agent])` replaces only that agent's `lastSettings` entry (never deletes one this window lacks) and merges its `modelShapes` per model id. Verify with `test/fileLock.test.ts` (four `tsx` processes incrementing one counter) and the two-store case in `test/accounts.test.ts`
- Official CLI quota monitoring is read-only: `host/accounts/local.ts` reads Grok `auth.json` and Kimi `credentials/kimi-code.json` / `device_id`, or an explicit `KIMI_CODE_API_KEY`. `LocalAccounts` publishes safe metadata through `AgentInfo.localAccount`; it never imports a switchable account or changes a session's credentials. Grok uses `cli-chat-proxy.grok.com/v1/billing?format=credits` plus `/v1/settings`; only explicit `creditUsagePercent` makes a bar, and on-demand balances are separate. Kimi uses `api.kimi.com/coding/v1/usages` for weekly and advertised short windows; custom endpoint overrides disable official credential reuse. Missing or expired credentials and unavailable percentages stay explicit states. Refresh on startup, after turns, and every minute while an account view is open; requests deduplicate and cache for 30 s. `ui/AccountLabel` shares the inline identity / plan layout, and `ui/QuotaBars` places the period, compact reset countdown badge and remaining percentage above a colored tube. Healthy allowance is green, at or below 30% amber, at or below 10% red. Multiple windows sit side by side in wide rows and stack in narrow views. Research references: [CodexBar Grok](https://github.com/steipete/CodexBar/blob/main/docs/grok.md), [CodexBar Kimi](https://github.com/steipete/CodexBar/blob/main/docs/kimi.md). Verify parsers and credential boundaries with `test/localAccounts.test.ts`; current-machine missing logins are not live quota success.
- `src/webview/` and `src/host/acp/` must never import `vscode`
