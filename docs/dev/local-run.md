# Local run: stand-in CLIs

A CLI under local run in an `ssh://` folder (`remote.md`) keeps its login, models and loop on this machine. It starts in an empty stand-in folder here, its native project tools stopped and Acpira's host tools (`host_tools::REMOTE`, served by `acpira mcp`) in their place. Code: `acp/local_run/`, `acp/session/stand.rs`. The built-in agent and Codex get there their own way (`remote.md`, `agent-quirks-codex.md`).

## Contract

- Every ACP agent can run here, `sshLocalAgents` (`id -> bool` override map, defaulting to on for installed external ACPs and off for uninstalled CLIs and the built-in agent) deciding. A built-in CLI has a profile (`local_run::builtin`), which wins over a custom entry of its id; any other agent gets the generic profile unless its entry says `localRun: false`. Withheld, whatever an entry says, and run in the host's engine: Pi, Hermes, Kimi Code (`withheld`, reasons below).
- With the switch off a host folder never starts a session here: `new_session_for` refuses rather than fall back to this machine's login when the host's engine is not there to ask.
- Stand-ins live under `<data root>/remote/`: `hosts/` for Claude Code (it keys sessions by folder), `antigravity/`, else `stand/<agent>/`. The pool warms the next process there, unless the profile adds launch arguments or environment.
- Gates, strongest first: the native tools taken off the model's list (launch arguments, an environment's configuration, Claude's `disallowedTools`); a stand-in `PreToolUse` hook running `acpira tool-guard <agent>`; always, the engine refusing a native write or command's permission request (`stand::blocked_native`, ahead of full access).
- Admission: a profile is checked against the real CLI and a real host with `scripts/probe/local-run-host.ts`. It needs a gate of its own unless the probe shows the CLI asking before every write and command, read-only commands included. A gateless profile holds only while the CLI asks: a full-access pick stays the engine's (`hosts_full_access`), where a native request of kind `other` still shows its card (`stand::unjudged`); a CLI that runs a native tool unasked (a rule the user gave it, a bypass mode it starts in) works on this machine. The generic profile is gateless, unprobed by definition.
- A gate file that cannot be written stops the start (`gated_remote_stand`), a borrowed warm process included.
- A CLI spells Acpira's tools its own way, and some call them through a tool of their own, so rows and cards are matched by `StandProfile::prefix` or else by the name's words, with the arguments unwrapped (`tools::tool_named`, `call_input`). A hyphen keeps a word whole (`acpira-tool` is another server). A CLI's lookup row (Droid's `ToolSearch`, Grok's `search_tool`, Devin's listing) stays as it is. A custom CLI whose spelling is not matched asks twice (its own card, then the engine's) until its entry gives the `prefix`.
- Some CLIs call an MCP tool without asking. For those (`own_cards` off) the engine raises the request itself before a write or command (`ask_remote`), decided like any other, so the session's access answers it. An approval belongs to one call: a row found only by its tool's name lends the call its looks, never its approval. A CLI with cards of its own is not asked again, which trusts its rules for a call it did not ask about.
- The hook guard reads only the call's arguments: every `agy` payload names its `~/.gemini` transcript, so matching the whole payload let every call through.
- Skills (`local_run/skills.rs`): a CLI scans only this disk, so the host's skills for the folder (from `places`, the built-in agent's set) reach it as a list in the note, as menu entries, and as `<skill>` instructions behind a prompt that calls one up. A leading `/name` goes out rewritten as a request, so the CLI never gets a command it does not know (what each CLI does with one is untried). Never copied into the stand-in: its paths mean host files to the guard, and a CLI loading a skill with its native read would be refused. A host user skill with the same name as one in this machine's `~/.agents/skills` is dropped; the agent's own command name always wins. Read once per session request.
- Host writes pass `beforeEdit` too (allow-once under acceptEdits); the CLI's own folders (`OwnFiles`) and the data root stay here. `Write` also takes `source_local_path` to copy bytes verbatim from a CLI-owned local file (validated via `stand::copy_source_path`, rejecting symlinks escaping allowed roots and private engine state files) to the host (inline `write` up to 2 MiB for older helpers, `writeStream` above that) so binary artifacts do not travel through the model's context as base64. A folder an account names in the child's environment (`OwnFiles::env_dirs`: a saved or plugin account's gemini dir) is in no engine's environment: the hook inherits it, the engine's checks take it from the process (`AgentProcess::own_dirs`, `Stand::own`). `agy` 1.5.13 ends its turn with an empty `end_turn` on any rejected permission request, so an engine refusal reads as a silent stop; a hook deny does not, single, parallel or on an image: the model reads the reason and goes on.
- A cancelled MCP request closes the hub socket, killing the host process group and taking a pending card down; a stop cancels every call, a row's or not, its question included (a host command outlived a stop on Claude Code 2.1.300).
- Limits: a slash command's inline `!` shell finds no Bash (the turn ends silently); no Monitor, NotebookEdit, LSP or worktrees; the host's own CLI folders (`.claude/`, `.gemini/`, `.factory/` …) are unread; a summoned child other than the built-in agent is refused (`relay/round.rs`).

## Per CLI

Observed against a Linux host; the profile in `local_run/mod.rs` holds the tool names.

- claude-agent-acp 0.93.0 / Claude Code 2.1.300: the adapter spreads `_meta.claudeCode.options` into the SDK options and takes `systemPrompt: { mode: "append" }` on new / load / resume; a `tools/call` carries its row's id in `_meta["claudecode/toolUseId"]`. A row names the MCP call in a top-level `name` and an AIR permission request repeats it in `_meta.jetbrains.air.permission.title`; both are rewritten, or the row reads "Call Acpira".
- `agy` 1.5.9: no tool-disable list over ACP, so a hook in `.agents/hooks.json`. It injects a `toolSummary` field into tool inputs, stripped from rows and calls. On Windows (1.5.13) a row's title and `locations` carry a file URL's path (`/C:/Users/…`), not absolute there as sent (`located_path`); the hook runs there under the line `guard_command` writes.
- Droid 1.14.0: reads Claude Code's hook format from the project's `.factory/settings.json` with no trust step, and applies it to calls made inside `Script`. `Script` itself must stay allowed: Droid calls an MCP tool it loaded late through it. Names a tool `acpira___Bash`, with `_meta.factory.{server,tool}`. A read-only command (`hostname`) runs without asking, so the engine's refusal alone did not hold.
- Grok 1.0.77: project hooks (`.grok/hooks/*.json`) and the project's `AGENTS.md` both load only in a trusted folder; `GROK_FOLDER_TRUST=0` lifts that for the process. Calls MCP tools through `use_tool` (`rawInput.{tool_name,tool_input}`); the native tool's name is in `_meta["x.ai/tool"].name`, the title is the command. A hook's deny on stdout or exit code 2 both block.
- OpenCode 1.18.15: `OPENCODE_CONFIG_CONTENT` merges over the user's configuration; a tool whose permission is `deny` leaves the model's list. `edit` covers every writing tool. MCP tools (`acpira_Bash`) run unasked. Its GPT prompt insists on `apply_patch`, so the note has to name the replacement or the model shells out a patch.
- DSH 0.2.2: never asks before any tool and files them all under kind `other`. `--patch <file>` overlays its profile; a patch entry of `id` + `disabled: true` switches a tool plugin off and keeps its config.
- Devin 3000.14: asks before every native command and write (`hostname` too) and before each MCP call, read-only ones included. Titles an MCP call `Calling Bash from acpira`, the name in `_meta["cognition.ai/toolName"]`; its permission request carries only the call's id. It reads Claude-format hooks, untried here.
- Hermes 0.22.5 (source, `acp_adapter/permissions.py`): asks only before a command it rates dangerous and runs the rest in its local terminal backend; its toolsets live in `~/.hermes/config.yaml`. Kimi Code 2.2.0: `[tools] disabled` and hooks only in the user's `~/.kimi-code/config.toml`; no real turn run. Neither takes a gate from a project folder or a start, so both are withheld.
- pi-acp 0.0.34 + pi 1.5.2: pi-acp keeps a session's `mcpServers` and never gives them to pi. A way in, untried: `PI_ACP_PI_COMMAND` as a wrapper adding `--approve --exclude-tools …`, a `.pi/mcp.json` in the stand-in whose `env` takes the hub grant from the process environment.
