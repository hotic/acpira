# UI conventions: motion and layout

Orb, motion, rails, sticky prompts, scrollbars, to-do presentation, folding, appearance axes and rendering preferences. Component rules are in `ui-conventions.md`.

- The turn's top-level activity owns the only `Orb` (thinking-orbs), with a stable Working label throughout active execution, independent of folding and the latest tool. Initialization reuses the Orb with its built-in `connecting` state; turn activity uses `breathing`. The connecting label stays stable and the status row fades in together. Approval and question waits use static icons and their waiting labels. Expanded thought rows keep static icons, show Thinking with shimmer while streaming, and retain expandable text after completion. Empty streamed text adds no second waiting indicator. In-progress tool rows use the same static icon as their completed state plus a shimmer on the verb (`ui/Shimmer`, or `RowLabel shimmer`; pass a real boolean — an explicit `undefined` takes the active default) — never an Orb. The Orb is deliberately outside the motion switch: it is the one "still working" signal and a 20 px canvas on its own layer, so `motion: none` leaves it turning (the library itself goes static under the OS reduced-motion preference). The one spinner is the session list's `working` state (`LoaderCircle` + `animate-spin` in the time slot): a list item has no verb to shimmer, and a dot reads as "unread". Like the Orb it is a live status signal, so it carries `.live-spin` and `motion: none` leaves it turning (the OS reduce-motion query still stops it). Streamed prose and thought text are paced by `useSmoothText` (`chat/streamMotion.ts`): the visible text advances at the stream's measured throughput (a time-weighted EMA of characters per ms that counts stalls too), so agents that push 30–60 characters twice a second read as one continuous stream, and a big block after a stall plays at the running speed instead of all at once (draining each chunk within the next arrival gap burst 8× the median speed there); lag beyond `lagMs` (500 ms) raises the target speed proportionally, `maxLagMs` (1.5 s) is a hard floor, the actual speed eases toward the target over 180 ms, the tail flushes within 220 ms once the stream ends, a non-appending change (edit, replay) and motion-off show at once, and cuts land on grapheme boundaries and never right after markdown punctuation / whitespace / an ordered-list number (while streaming, a received tail that ends on syntax is held back): streamdown's animate plugin renders as many characters of a block as it already animated with a 0 ms duration, so a transient literal (`- *`, `**`, `1`) made the real text replacing it appear without an entrance. On top of that each grapheme gets a 180 ms opacity-only fade on inline spans (`sd-acpGlyph` in `motion.css`, `--stream-char-duration`), with no stagger. The duration is fixed in CSS rather than read from `--sd-duration`: streamdown re-renders the whole live block every pass and stamps already-animated characters 0 ms, which snapped mid-fade glyphs to full while an earlier block, no longer re-rendered, kept fading — text looked out of order (verified with the `整段砸下` scenario: 57 characters out of order before, 0 after). Inline spans keep CJK line-breaking rules; the former inline-block glyphs let a full stop start a line. The pacing was chosen in `lab/stream-pace.preview.html` (same chunk schedule, five configs side by side); the previous per-chunk cascade (22 ms stagger, 320 ms backlog, 380 ms entrance) stalled for ~1.2 s over a 4 s reply from a slow-chunk agent. Live row slots enter in sequence; restored history stays static. Rail growth is eased in JS by `ConnectedRail` (a CSS transition retargeted every frame stalls on the main thread), and motion-off / reduced-motion settings snap it instead. The stream and row animation rules live in `styles/motion.css`.
- Motion decisions (after the rules distilled at [animations.dev](https://animations.dev/)): gate by frequency before designing anything — keyboard-initiated actions (slash / `@` completion, the command-style pickers, shortcuts) get no animation at all, elements seen tens of times a day stay near-imperceptible, occasional UI (menus, dialogs, toasts) gets standard motion, and the delight budget is spent only on rare / first-time moments. A new animation must name its purpose (feedback, spatial consistency, state indication, preventing a jarring change) or it is not built. Animate `transform` / `opacity` only, extend the existing `--dur` / `--enter-*` tokens and curves instead of adding a parallel system, prefer `transition` over `keyframes` for anything rapidly re-triggerable (keyframes restart from zero), enter from `scale(0.95)` + `opacity: 0` never `scale(0)`, and ship `prefers-reduced-motion` plus `@media (hover: hover) and (pointer: fine)` gating with the animation, not after. If a trigger-anchored popover ever scales in, its `transform-origin` is Base UI's `var(--transform-origin)` (the trigger anchor), not center — modals are exempt. When tuning, work down this order before reaching for new values: delete the animation → shorten duration / distance → fix the easing → fix the origin → make it interruptible → move it to the GPU. Deliberate exceptions a reviewer must not "fix": row entrances exceed 300 ms by design, streamed text trails the received text by about 500 ms (continuity comes from arrival-rate pacing, not from long per-glyph entrances — lengthening the entrance again brings back the blurred leading edge), and the rail is JS-eased because retargeting a CSS transition every frame stalls the main thread — both measured, see `scripts/probe-fold-perf.ts`.
- Rail rule: indented disclosure bodies and tool result rows share `ui/ConnectedRail`. The solid line attaches to the actual icon strokes, ends with a short solid dot, and grows with streamed content. Result rails stop at the final row before its output card. Full-width diff / output cards and process fold bodies get no outer rail. Thought text renders `trimEnd()`ed: models close thoughts with `\n\n`, and under `whitespace-pre-wrap` those blank lines push the end dot below the text (`lab/thought.preview.html` → `trailing`). The easing step (`railStep`) measures elapsed time with `performance.now()` at both ends and clamps it at zero: the rAF timestamp is the frame start, which on a busy main thread precedes the effect that scheduled it, and since an opening panel restarts that effect every measured frame, the negative interval compounded and drove `--rail-length` below zero — the line vanished and the dot flickered at the icon while the thought opened (reproduced in `lab/performance.preview.html` under 6× CPU throttling; no drop after the fix)
- User prompts (`chat/HistoryMessage`) stick within their exchange and have no hover actions — clicking the card opens the inline editor, which is also where the full text is copied from. Once stuck at the top the text folds to `--user-message-stuck-lines` (3) with a `scroll-fade` edge and `overflow-hidden` (the wheel keeps moving the conversation); the stuck state comes from an `IntersectionObserver` sentinel at the exchange's top (`section` is `relative`, the scroller carries `data-thread`), and the fold is instant and never changes the exchange's flow height: a spacer after the sticky frame (outside the sticky box, `-mt-msg` so an empty one adds nothing) is set in a layout effect to the unfolded height measured just before the fold minus the folded height. Letting the reply move up with the fold jumped the reply and, at the bottom of the thread, shortened the scroll range so the sentinel came back into view — unstick, grow, stick again, an endless flicker; freezing the natural height via `min-height` on the frame instead trailed an empty strip under the card while the next exchange pushed it out. Trailing blank lines in the prompt are not displayed (`trimEnd`). A hidden sidebar webview collapses the thread to no box: ignore those observer/scroll records and re-check when it has a box again, or coming back leaves a still-visible prompt folded as if the history had been compressed. The observer's first record lands after the first paint, so a session opened at its bottom painted every prompt at full height for two frames and then folded it through the `max-height` transition; `HistoryMessage` therefore also measures once in a `queueMicrotask` from the sentinel ref (after the whole commit, including `Thread`'s scroll-to-bottom layout effect, but before paint — `promptIsStuckAt` on plain rects) and `flushSync`es the fold with `--dur-open` zeroed on the frame for that one style change. Verify with `lab/history.preview.html?long` and a rAF logger injected before the page (`Page.addScriptToEvaluateOnNewDocument`): no frame may show a prompt whose sentinel is above the thread top unfolded
- Bottom follow (`Thread` in `chat/Shell.tsx`, `SubagentInspector`'s session tab): a `ResizeObserver` on the scroller re-pins when the area above the composer grows, and the scroll listener decides the follow through `promptStuck.followsBottom` — only an upward scroll away from the bottom releases it. Scroll events arrive a frame late, so the one caused by a pin can read the gap left by a second shrink a few ms later (the connecting `Notice` appearing on an account switch, then the composer's chips changing); judging by gap alone released the follow and left the transcript tail under the notice. Reproduced in a Shell LAB page with two 60 px shrinks 1–12 ms apart
- Scrollbars are overlay-style everywhere: `scrollbar-gutter: stable` keeps layout still, the track is transparent, and the hairline thumb shows only while its element scrolls (`ui/useScrollReveal` on the shell roots stamps `data-scrolling` for 800 ms) or under the pointer — never on focus. `scroll-thin` is the 6px variant for lists and card text. All scrollbar rules (including `.scroll-thin`, a plain class rather than an `@utility`) are unlayered in `base.css`: the host webview stylesheet paints `::-webkit-scrollbar-thumb` / `:hover` / `:active` with `--vscode-scrollbarSlider-*` unlayered, so a layered rule loses and every scroller grows a permanent grey bar. `lab/webview-defaults.css` replicates those host rules; import it in any LAB page that judges scrollbars
- To-do presentation separates history from the live dock: `chat/Plan` is a lightweight disclosure with a stable title, done/total and chevron; its entries expand to natural height without a card or current-task summary. `PlanBar` uses a two-level `PlanCard`: stable title/count on top, current task below while collapsed, replaced by the full `PlanEntries` list when expanded. The current task appears once per view. Only the dock list is height-limited and uses `useScrollFade`; each disclosure keeps its own state across plan updates.
- Process prose uses `--process-prose-gap` around action boundaries; consecutive tools retain `--process-row-gap`. Expanded process history stays in the conversation scroll flow, while thoughts retain their bounded viewport.
- Folding (`acpira.appearance.fold`, default `codex`): `codex` keeps one process fold per turn from the first moment of a live turn (chosen in `lab/live-head.preview.html` over a merged Thinking/Working head, a quiet thought row and the former separate Working row: a Working row above a sibling Thinking row read as the same status twice, and swapping it for the fold head at the first tool replayed its entrance). Before any tool call the fold is open, so thoughts read as its children; it collapses only when the turn is first opened with tools already present, and a live turn keeps it open across its first tool call when content was already visible (`CodexFold.visibleBeforeTools`). A turn with no process blocks shows the head only while running and retires it with a fade then collapse; a finished turn with thoughts but no tools shows `已完成 用时 …` over them. The head keeps the Working label and Orb while running, including when expanded, and shows `用时 4 分钟 46 秒` after completion. Manual expansion survives updates and completion; grouped tool outputs start collapsed. The manual toggle is also kept outside the component tree in `chat/foldMemory.ts` (keyed `<sessionId>:<turnIndex>:<startedAt>`, module cache plus the webview's `setState`, 200 most recent entries), so an explicit choice survives a rebuilt message tree or a reloaded webview. This cache does not cover the pre-tool default: visible thought/commentary must stay open across the first tool call even when nothing was clicked. Tool rows enter once per tool id (`ui/Row` `EntranceOnce`, scoped by the message's `memoryKey`): a running read is a `ToolCall` and a completed one joins a `ReadGroup`, and the remount replayed every row's entrance; file rows that genuinely appear later get their own `:files` identity. Nested rows still start closed after a rebuild. Process prose and resolved question records stay inside at their chronological position (a record hoisted after the fold reads as if the answer arrived after every later action), trailing reply text and permission cards stay outside. ACP does not distinguish commentary from final text, so trailing text moves into history when another action arrives — but only a real action counts: thoughts and `plan` (to-do) updates after the last tool call do not end the reply (`splitCodexBlocks` `TAIL_PROCESS`), they join the end of the fold while every text after that action stays outside. Otherwise a summary followed by one more thought and a short coda collapsed to just the coda. In turns without tool calls only the trailing text run is the reply. Verify with `test/folding.test.ts`. Duration uses `AgentTurn.startedAt` / `endedAt`, never summed thought durations; older turns without timestamps show `已完成`. `cursor` folds only runs of read-only actions. Fold bodies are not indented
- Appearance axes: the combo code is positional (`encodeAppearance`), so new axes go at the end of `AXES`; baseline is `201110200302100`. Only `motion` is exposed to users (settings → Appearance, a `Switch`, over `setAppearance` → `acpira.appearance.motion` = `on` | `none`); the rest stay LAB decisions. `none` is kept as the off value so an existing "off" survives; the former `subtle` / `full` fail validation and fall back to the baseline `on`, which is what they meant
- User-facing rendering preferences are plain `acpira.*` settings (`theme` / `uiFontSize` / `codeFontSize` / `diffMarkers` / `fontSmoothing`, sanitized in `shared/settings.ts`) shown on the settings Appearance page. `webview/look.ts` turns them into root attributes (`lookAttrs`: `data-theme-fixed`, `data-diff`, `data-smoothing`, inline `--ui-font-size` / `--code-font-size`) that both shells spread after `appearanceDataAttrs`; the LAB omits `look` so defaults paint. Theme: `resolveTheme` in `App` maps `auto` to `useVsCodeTheme()` (body's `vscode-*` class) and a fixed scheme sets `data-theme-fixed`; the host-derived roles in `tokens.css` (`--fg-1`, `--bg-0`, `--line-strong`, `--focus`) go through `--host-*` indirections that the fixed rule sets to `initial` (guaranteed-invalid → the `var()` fallbacks paint), otherwise a light shell would keep VS Code's dark sidebar background. Components read the resolved scheme from `ThemeContext` (`useTheme`), never from the body class. Type scale: `--text-*` are declared on `:root, .acp-shell` in terms of `--ui-font-size` / `--code-font-size` — a custom property resolves where it is declared, so the shell's inline override only reaches tokens redeclared on the shell; density / settings line heights are `calc(var(--ui-font-size) + Npx)` offsets, keep new sizes that way. `data-diff="signs"` just blanks `--diff-add` / `--diff-del` (the lines already carry `+` / `-` / space prefixes from `host/acp/diff.ts`)
- `Collapsible.Panel` always keeps its DOM mounted and uses an inert grid transition when closed. Disclosure retains ConnectedRail, streamed text and row entrance ownership remain unchanged, and nested folds preserve state. The menu and settings switches share one primitive with separate skins. Image Dialog stays absolute inside the shell, preserves natural image size, and neither locks document scrolling nor transfers focus. Toast remains timer-driven because its eight-second lifetime must continue during hover, focus and window blur; its viewport stays in the Thread area above the composer.
