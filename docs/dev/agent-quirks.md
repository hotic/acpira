# Agent quirks

Per-agent facts observed on the wire (Devin, Grok, Kimi, Codex, Claude, OpenCode, DeepSeek Harness, Pi), with the versions they were verified against.

- Devin 3000.10.21 sends 420 flat model options, 210 of them Fusion pairs named `Fusion (<lead> + <sidekick>)` (`fusion-gpt-6-astra-high-fast-sidekick-swe-2-medium`, description "Pairs frontier intelligence with cost-efficient execution"). Dimensions: 4 leads × Low–Max × 6 sidekicks (their own effort baked into the label) × Fast, not a full product (Luna / Sol sidekicks pair with a subset of leads). Fast is one pair-level switch — `-fast-` after the lead, `-priority` on the sidekick — and the name marks it on whichever side supports it, so a Fable lead (no Fast of its own) still reads Fast off its sidekick. `shared/models.ts` `parseFusionName` folds them into one `Fusion` family (`brand: devin`, `ModelVariant.lead` / `sidekick`, `ModelFamily.fusion.leads` / `sidekicks`); the ambiguity detector's tuple includes lead + sidekick or every pair would look duplicate. The picker shows one `Fusion` row, and while it is current the footer is Devin's own four controls (Lead / Effort / Sidekick menus + pills, Fast switch, `chat/ModelPicker.tsx` `FusionParams` over `ui/Field` `SelectRow`) resolved through `findFusionVariant` (exact → drop Fast → the lead's first sidekick → nearest effort); switching a plain model into Fusion makes it the lead when it is one. The chip reads only `Fusion` (pair in the tooltip); the settings page has one Fusion row whose switch hides all pairs. Verify with `test/models.test.ts` "fusion pairs" and `lab/model-params.preview.html?fusion`
- Devin hides an opt-in for standard ACP select groups: `clientCapabilities._meta['cognition.ai/groupedSessionConfigOptions'] = true` at `initialize` (stderr logs `grouped_options=true`) makes `session/new` return the same 420 ids as `{ group, name, options }` families (62 groups, some empty — `SWE-check`, `Subagent Default`, `Fusion Sidekick (…)` — which `flattenSelect` drops). Fusion stays one flat 210-option group there too, so the name parser is still needed; not advertised yet because `flattenSelect` would turn every option's `description` into the group name and `groupModels` would show it as `source` under an identical family name. The binary also names `cognition.ai/isFusion`, `isFusionCompatible`, `isFastSpeedVariantOf` option meta and a `cognition.ai/windsurfConfigBridge` capability, none of which appear in 3000.10.21's responses
- Grok echoes our prompt back as `user_message_chunk`; ignore it while a turn is in flight, and suppress content updates during load/resume replay
- Grok's first `tool_call` packet carries only `title` (e.g. `"read_file"`); kind/locations arrive in later `tool_call_update`s. A target inferred from the title is a fallback only — never overwrite rawInput/locations
- Grok does not advertise modes in the protocol, but CLI ≥ 0.2.117 accepts `session/set_mode`, so the registry declares synthetic modes (`AgentDef.modes`): default / plan go over the protocol, yolo is host-side auto-approval of permissions while the CLI stays in default; `AcpSession.applyControls` backfills when the protocol gave no modes.
- Grok 1.0.18 advertises standard `reasoning_effort` / `thought_level` selects when the active catalog entry declares `reasoning_efforts`; `session/set_config_option` accepts a string value. The official grok-4.6 catalog has xhigh / high / medium / low. A custom alias without that declaration omits the select and rejects effort changes with -32602 (`unknown reasoning_effort value`). Synthesizing a client control cannot fix the CLI gate, and legacy `session/set_model` can acknowledge an ignored `_meta.reasoningEffort`. Declare supported efforts in the CLI model config; never infer successful application from acknowledgement alone. Verify with `scripts/probe-controls.ts` (a one-off probe, since removed) and `scripts/probe-controls-host.ts` (a one-off probe, since removed).
- Grok 1.0.18 does not emit standard `usage_update`. Its prompt `_meta.usage` is per prompt, not cumulative — a two-prompt probe's second response reported `inputTokens 38140`, `cachedReadTokens 37888`, `outputTokens 20`, `modelCalls 1`, fresh spend for that one prompt — and not current context occupancy. `grokUsage.ts` reads `_x.ai/session/info` → `result.context.used` / `total`, the same snapshot as the CLI context view. Refresh on start/resume, model selection and prompt completion before automatic compaction; prefer standard usage notifications when available. Invalid/unsupported snapshots stay unknown, and stale responses cannot replace newer usage. Kimi 0.41.0 asgard/kimi-k3 already advertises thinking low / high / max and emits `usage_update` asynchronously after the prompt response; keep probe processes alive for that notification. Switching models appends the previous thinking value when the new model does not offer it (K3 grows a leftover `on`, K2.7 a leftover `high`; DeepSeek legitimately mixes `off` with low / medium / high / max). `composerControls.presentReasoning` drops the stranger, renders `off` as a Thinking switch rather than a radio sibling, and `AcpSession.syncThought` writes a native value so the leftover does not stay on the wire.
- Devin credentials are a long-lived API key (`windsurf_api_key` from a PKCE login) stored at `~/.local/share/devin/credentials.toml`. With `ACP_BACKEND` set, `devin acp` only accepts credentials handed over by the host (the registry sets `ACP_BACKEND=windsurf`): `session/new` fails with -32000 until `authenticate({ methodId, _meta: { api_key, api_server_url } })` — any advertised methodId works if `_meta` has the key
- Devin's browser login (`devin-browser`) authenticates only the current process: the response is `{}`, the key is never returned or persisted. Durable accounts come from the toml only: import the local login, or run `devin auth login` in an isolated XDG directory (needs a TTY, so it runs in a VS Code terminal with file polling)
- `devin auth status` reads only the toml (ignores `WINDSURF_API_KEY`); delete `ACP_BACKEND` from the env before running it or it reports "Not logged in"
- Devin quota is not on the ACP wire: `/usage` is TUI-only (`Unknown command` over ACP) and `/session-stats` is per-session. The CLI reads it from the Windsurf seat service, a Connect RPC that also answers JSON: `POST {api_server_url}/exa.seat_management_pb.SeatManagementService/GetUserStatus` with `{ metadata: { apiKey, ideName, ideVersion, extensionVersion } }` (all four required, else 400; a bad key is 401). `userStatus.planStatus` carries `dailyQuotaRemainingPercent` / `weeklyQuotaRemainingPercent` (whole numbers) and `*QuotaResetAtUnix` (int64 as strings); `planInfo.hideDailyQuota` / `hideWeeklyQuota` say which windows the plan has (Max: weekly only, Pro: both). proto3 JSON omits zero fields, so on `billingStrategy === 'BILLING_STRATEGY_QUOTA'` a missing percent is 0%, not a missing window. `DevinAccountProvider.quota` → `AccountManager` cache (30 s max-age, forced after each turn of a bound session) → `AccountInfo.quota` → `ui/QuotaBars` in the account menu / settings rows
- Devin quota exhaustion and the automatic switch (devin 3000.11.3, verified 2026-09-26 with a real account): the default model `swe-2-high` (SWE-2) does not count against the window — two accounts at weekly 0% still answered with it — so a probe must pick a metered model (`claude-sonnet-5-medium` was used). With it, the Max account at weekly 0% failed the prompt with "Your weekly usage quota has been exhausted. Visit https://app.devin.ai/settings/usage to purchase on-demand usage or turn on auto-reload. (trace ID: …)"; the host replaced the error with the switch notice, skipped the Pro account (weekly 0%, daily 17%) under earliestReset, bound the Max account with allowance left, resumed the same native session with the chosen model kept, and the hidden continue prompt got the reply (`end_turn`, no error)
- Devin sweeps empty sessions that never received a message when the creating process exits: `session/resume` then returns `-32016 Session not found`. `AcpSession.openSession` sorts every restore failure into one of three outcomes — the peer has no restore path at all (readonly, `host.cannotResume`), it answered the session is gone (`session_not_found`, `session not found` text, or an invalidParams on resume/load whose message names none of DSH's other causes — see `classifyRestoreError` under the DSH bullet), it knows the session but refuses to continue it (`session is not resumable`: readonly with the peer's reason, `host.notResumable`), or it tried and failed (e.g. -32603: thrown as `host.resumeFailed` → the error Notice, where Retry does a full reconnect + resume). "Gone" transparently falls back to `session/new` only when the transcript is still empty; with turns present the session goes readonly (`host.sessionGone`) instead of silently continuing the visible conversation on an empty native context. A `session/prompt` answered session_not_found likewise leaves `ready` for the error state. Another common errorKind is `session_locked` (-32015, retryable: another process holds the session) — the one case with real evidence of occupation, so it gets its own error text (`host.sessionLocked`) and the same retryable error state
- Devin background shells: an `exec` (kind execute, `rawInput.command` / `timeout`) that outlives its timeout is parked, not finished — a `tool_call_update` keeps `status: in_progress` and adds `_meta['cognition.ai/background'] = true`, `cognition.ai/backgroundShellId`, `cognition.ai/backgroundCommand`; the call stays in_progress until the process exits (`_meta.terminal_exit`), and its output lands on that exec's `content`. Later `get_output` (title `Read shell`, **no kind**, `rawInput { shell_id, timeout }`, `_meta['cognition.ai/inferenceToolName'] = 'get_output'`) blocks for up to its timeout waiting on that process; `kill_shell` is `Kill shell` with the same shape, `write_to_process` arrives as kind execute titled ``Wrote to `cmd` ``. Rendered generically this read as `正在调用工具 shell` for minutes and was mistaken for a hang (one such session was cancelled and told to continue for no reason). `normalize.rs` marks the parked exec `background` (skipped by `activityOf` / `foldActivity`, so a streaming thought wins), and gives `get_output` / `kill_shell` `verb.wait` / `verb.kill` with the parked command as target via `NormalizeState.shells` (shell id → command, in-memory). Verify with `scripts/probe-questions.ts devin "<prompt asking for a backgrounded sleep + get_output>"` (a one-off probe, since removed)
- `promptCapabilities.image` is not authoritative for Grok: it advertises `image: false` yet accepts inline `{ type: 'image', data, mimeType }` blocks in `session/prompt` and the model really sees the pixels (Devin / Kimi / OpenCode / DSH / pi-acp advertise `true`). The registry declares `prompt.imagesRegardless` for Grok; every other agent's flag is honoured (DSH rejects images its route cannot take). `pnpm probe <agent> --image PATH "describe it"` verifies. Grok also echoes the image block back as a `user_message_chunk` with `content.type === 'image'`, so user chunk handling must tolerate non-text content. Grok / Devin / Kimi / OpenCode advertise `embeddedContext: true`; DSH and pi-acp advertise `false`
- Codex via codex-acp 1.13.0 (`codex-acp`, bundled `@openai/codex` 0.155.1, `CODEX_PATH` overrides): `loadSession` + `list / resume / close / delete / fork / additionalDirectories / subagents`, image + embeddedContext, `sessionCapabilities`; auth methods `api-key` (env `CODEX_API_KEY` / `OPENAI_API_KEY`) and `chat-gpt` (the adapter opens a browser) — no terminal methods, so its sign-in buttons go through `authenticate`; the terminal fallback is `codex-acp cli login` because bare `codex-acp login` shells out to a separately installed `codex`. `modes` read-only / agent / agent-full-access plus `model` / `reasoning_effort` selects, a `fast-mode` boolean and a `collaboration_mode` select (default / plan) that the composer shows as a Build / Plan chip left of the permission modes (`composerControls` `collaboration` bucket); skills are published as `/$<name>` commands. `session/resume` restores context and `session/list` + fresh-store import work once the cwd is canonical (verified 2026-09-23 with `probe-restore-host.ts codex`); the adapter canonicalizes the thread cwd (macOS `/var` → `/private/var`) and string-compares it per 25-thread page, so a symlinked project path needs the host's `realpath` retry in `native_sessions.rs`

- Claude via claude-agent-acp 0.81.0 picks its compaction presentation from `clientCapabilities.session.compaction` (source: `dist/context-compaction.js`, `acp-agent.js` `clientSupportsCompactionUpdates`). Without it, every compaction (manual or Claude Code's own autocompact) arrives as a `tool_call` `kind: "think"` titled "Compact conversation", which rendered as a thought row; with it, standard `compaction_update` in_progress → completed / failed (`error`) / cancelled at the turn boundary, plus `compaction_summary_chunk` (not rendered). `initialize_request` advertises `session.compaction: {}`. "Autocompact is thrashing: the context refilled to the limit within 3 turns …" is Claude Code's own circuit breaker after three back-to-back autocompacts (an oversized file read / tool output), surfaced as the prompt error, not a host fault. The capability switch is source-verified only; not yet confirmed against a live compaction. codex-acp gates the same way (`capabilities?.session?.compaction != null`, source only). pi-acp 0.0.33 reports automatic compaction as two whole prose chunks (`Context nearing limit, running automatic compaction...` / `Automatic compaction finished; context was summarized to continue the session.`) and a manual `/compact` as `Compaction completed.\nTokens before: N\n\n<summary>`; all three map to a compaction row through `compaction_text.rs` (source only). pi's provider auto-retry arrives the same way (pi-acp 0.0.33 `auto_retry_start` / `auto_retry_end`): whole chunks `Retrying (attempt N/M, waiting Ss)...` (bare `Retrying...` when the numbers are missing) and `Retry finished, resuming.` — the latter even when the last attempt failed, since pi-acp drops pi's `success` flag. `retry_text.rs` turns one run into a single warning `notice` row (category `connection`, no actions) rewritten in place per attempt and settled by the resume line; a resume line with no run open is dropped (seen in the UI 2026-09-25, strings source-verified). pi-acp also ends a provider-failed prompt with `end_turn` and forwards no `errorMessage`: a gateway refusal (seen 2026-09-25: asgard → Devin Connect `permission_denied` content policy on every prompt) surfaces as `empty_response`; the reason is only in pi's session `.jsonl`. Claude Code 2.1.224 (native `claude` under claude-agent-acp 0.81.0) sizes the model window before autocompaction: `[1m]` in the model id or a catalog-native 1M model gives 1M, otherwise 200k; `CLAUDE_CODE_MAX_CONTEXT_TOKENS` only applies to model ids that do not start with `claude-`, so a gateway alias like `claude-opus-5.5` stays at 200k (the adapter's `usage_update.size` shows 200000). `CLAUDE_CODE_AUTO_COMPACT_WINDOW` is `min(model window, value)` and `CLAUDE_AUTOCOMPACT_PCT_OVERRIDE` a fraction of that, so `30` with a 1M window setting still compacts at ~54k (observed `compact_boundary.compactMetadata.preTokens` 53–60k on every autocompact, 2026-09-25) and ends in "Autocompact is thrashing". The `[1m]` suffix is stripped before the request (`Ta`), so the gateway still sees the plain id, plus the `context-1m-2025-08-07` beta header. Source: the bundled binary's `Q9` / `zw` / `paf` / `Ta`.
- OpenCode 1.18.15 (`opencode acp`): `loadSession` + `list / resume / fork / close`; one auth method `opencode-login` ("Run `opencode auth login`", the ACP `authenticate` itself is a no-op); `session/new` returns no `modes` but a `mode` config option (`build` / `plan` / the user's custom agents from `opencode.json`) that `applyConfigOptions` turns into modes (switching goes through `set_config_option`), a flat `model` select (`provider/model` values) and `effort` (low / medium / high); `available_commands_update` lands ~5 ms after the response; `usage_update` carries `{ used, size, cost: { amount, currency } }` with `cost` the session's cumulative spend; the prompt response's `usage` is per prompt. Permission options are `once` / `always` / `reject`. `session/load` replays the whole history as `user_message_chunk` / `agent_thought_chunk` (one chunk per thought) / `agent_message_chunk` with `messageId`, no `stop`, no `usage_update`; `session/resume` restores without replay; `session/list { cwd }` is newest first with `title` (auto-generated a little after the first turn) and `updatedAt`; `close` keeps the session listable. Every `session/new` — including the settings page's controls probe — persists a "New session - <iso>" row in OpenCode's own store; the import list therefore never creates one. Model calls through a slow gateway have been seen to take 40 s+ for a one-word reply; that is the provider, not the protocol
- DeepSeek Harness 0.1.5-rc.2 (`dsh --profile acp`): `agentInfo` is `deepseek-harness-acp 0.0.1` (the ACP package's version, not the CLI's), `list / resume / close`, no `loadSession`, `authMethods: []` (credentials live in the DSH config / `dsh web`), no modes, a **grouped** `model` select whose values are JSON tuple strings (`["asgard","composer-2.5-fast"]` — opaque ids, never parsed) and `reasoning_effort` with a `""` "Provider default" option next to off / low / medium / high (renders as a Thinking switch + pills); no commands are advertised; `usage_update` is `{ used, size }`. Restore errors are bare `-32602`s told apart by message (`sessionErrors.ts` `classifyRestoreError`: `unknown session:` gone · `session is already active:` locked · `session is not resumable:` readonly with the peer's reason · `session cwd does not match:` / MCP config errors retryable failure; an unrecognized -32602 still means gone, which is what Grok / Kimi answer for an unknown id). `session/list` items carry only `sessionId` + `cwd`; a created session shows up in the *next* process's list. `session/new` persists a directory under `~/.dsh/sessions/<cwd>/`, so probes use a temp `DSH_HOME`
- Pi via pi-acp 0.0.33 (`pi-acp`, spawns `pi --mode rpc` — `requires: ['pi']`): `loadSession` + `list / delete` (no resume; `delete` removes the pi session file and is deliberately unused), auth method `pi_terminal_login`, `embeddedContext: false`; `modes` are the thinking levels (`Thinking: off…xhigh`) duplicated as `thought_level` → `controls.ignoreModes`; the list is hard-coded in the adapter (`getThinkingState`) instead of pi's per-model `getAvailableThinkingLevels` / `thinkingLevelMap`, so `max` never appears and a model that cannot turn thinking off still offers `off`, and every thought_level pick is echoed as `current_mode_update` (source, pi-acp 0.0.33 / pi 0.86.0); pi itself drops `xhigh` / `max` for a custom `models.json` model without a `thinkingLevelMap` entry and clamps the pick down (`getSupportedThinkingLevels` / `clampThinkingLevel`, source only); commands are `/skill:<name>` per discovered skill plus `/compact /autocompact /export /session /name /steering /follow-up /changelog`; no `usage_update`, no prompt `usage`, and pi's `get_session_stats().contextUsage` never leaves the adapter (`/session` prints only token totals). `acp/pi_usage.rs` therefore reads pi's own session file, polled like Grok (start / load, every 800 ms while a prompt runs, turn end, model switch; a size + mtime stamp skips unchanged files): the file is `~/.pi/pi-acp/session-map.json` → `sessionFile`, else `<agentDir>/sessions/--<cwd, / \ : → ->--/<ts>_<acpSessionId>.jsonl` (`agentDir` = `PI_CODING_AGENT_DIR` or `~/.pi/agent`; pi's session id is the ACP one). - Kimi's `session/new` auth gate (`ensureAuthed`) checks only the provider behind `default_model` in `~/.kimi-code/config.toml` (api_key set, or a cached OAuth token), then falls back to "any OAuth provider logged in". It does not care which model the session will use, so a working custom provider (`asgard`, …) still gets `-32000` when `default_model` points at `managed:kimi-code` and its OAuth cache is empty; fixes are `kimi login` or pointing `default_model` at the custom provider's model. `kimi acp` takes no `-m`, but `KIMI_CODE_HOME=<dir>` swaps the whole config dir (`pnpm probe kimi` with it verifies).
