# Agent quirks

Per-agent facts observed on the wire (Devin, Grok, Kimi, Codex, Claude, OpenCode, DeepSeek Harness, Antigravity, Pi), with the versions they were verified against.

- Devin 3000.10.21 sends 420 flat model options, 210 of them Fusion pairs named `Fusion (<lead> + <sidekick>)` (`fusion-gpt-6-astra-high-fast-sidekick-swe-2-medium`, description "Pairs frontier intelligence with cost-efficient execution"). Dimensions: 4 leads × Low–Max × 6 sidekicks (their own effort baked into the label) × Fast, not a full product (Luna / Sol sidekicks pair with a subset of leads). Fast is one pair-level switch — `-fast-` after the lead, `-priority` on the sidekick — and the name marks it on whichever side supports it, so a Fable lead (no Fast of its own) still reads Fast off its sidekick. `shared/models.ts` `parseFusionName` folds them into one `Fusion` family (`brand: devin`, `ModelVariant.lead` / `sidekick`, `ModelFamily.fusion.leads` / `sidekicks`); the ambiguity detector's tuple includes lead + sidekick or every pair would look duplicate. The picker shows one `Fusion` row, and while it is current the footer is Devin's own four controls (Lead / Sidekick menus, the lead's effort segments with the pair's Fast toggle in their header, `chat/ModelPicker.tsx` `FusionParams` over `ui/Field` `SelectRow`) resolved through `findFusionVariant` (exact → drop Fast → the lead's first sidekick → nearest effort); switching a plain model into Fusion makes it the lead when it is one. The chip reads only `Fusion` (pair in the tooltip); the settings page has one Fusion row whose switch hides all pairs. Verify with `test/models.test.ts` "fusion pairs" and `lab/model-params.preview.html?fusion`
- Devin hides an opt-in for standard ACP select groups: `clientCapabilities._meta['cognition.ai/groupedSessionConfigOptions'] = true` at `initialize` (stderr logs `grouped_options=true`) makes `session/new` return the same 420 ids as `{ group, name, options }` families (62 groups, some empty — `SWE-check`, `Subagent Default`, `Fusion Sidekick (…)` — which `flattenSelect` drops). Fusion stays one flat 210-option group there too, so the name parser is still needed; not advertised yet because `flattenSelect` would turn every option's `description` into the group name and `groupModels` would show it as `source` under an identical family name. The binary also names `cognition.ai/isFusion`, `isFusionCompatible`, `isFastSpeedVariantOf` option meta and a `cognition.ai/windsurfConfigBridge` capability, none of which appear in 3000.10.21's responses
- Grok echoes our prompt back as `user_message_chunk`; ignore it while a turn is in flight, and suppress content updates during load/resume replay
- Grok's first `tool_call` packet carries only `title` (e.g. `"read_file"`); kind/locations arrive in later `tool_call_update`s. A target inferred from the title is a fallback only — never overwrite rawInput/locations
- Grok does not advertise modes in the protocol, but CLI ≥ 0.2.117 accepts `session/set_mode`, so the registry declares synthetic modes (`AgentDef.modes`): default / plan go over the protocol, yolo is host-side auto-approval of permissions while the CLI stays in default; `AcpSession.applyControls` backfills when the protocol gave no modes.
- Grok 1.0.18 advertises standard `reasoning_effort` / `thought_level` selects when the active catalog entry declares `reasoning_efforts`; `session/set_config_option` accepts a string value. The official grok-4.6 catalog has xhigh / high / medium / low. A custom alias without that declaration omits the select and rejects effort changes with -32602 (`unknown reasoning_effort value`). Synthesizing a client control cannot fix the CLI gate, and legacy `session/set_model` can acknowledge an ignored `_meta.reasoningEffort`. Declare supported efforts in the CLI model config; never infer successful application from acknowledgement alone. Verify with `scripts/probe-controls.ts` (a one-off probe, since removed) and `scripts/probe-controls-host.ts` (a one-off probe, since removed).
- Grok 1.0.18 does not emit standard `usage_update`. Its prompt `_meta.usage` is per prompt, not cumulative — a two-prompt probe's second response reported `inputTokens 38140`, `cachedReadTokens 37888`, `outputTokens 20`, `modelCalls 1`, fresh spend for that one prompt — and not current context occupancy. `grokUsage.ts` reads `_x.ai/session/info` → `result.context.used` / `total`, the same snapshot as the CLI context view. Refresh on start/resume, model selection and prompt completion before automatic compaction; prefer standard usage notifications when available. Invalid/unsupported snapshots stay unknown, and stale responses cannot replace newer usage. Kimi 0.41.0 asgard/kimi-k3 already advertises thinking low / high / max and emits `usage_update` asynchronously after the prompt response; keep probe processes alive for that notification. Switching models appends the previous thinking value when the new model does not offer it (K3 grows a leftover `on`, K2.7 a leftover `high`; DeepSeek legitimately mixes `off` with low / medium / high / max). `composerControls.presentReasoning` drops the stranger, renders `off` as a Thinking switch rather than a radio sibling, and `AcpSession.syncThought` writes a native value so the leftover does not stay on the wire.
- Devin credentials are a long-lived API key (`windsurf_api_key` from a PKCE login) stored at `~/.local/share/devin/credentials.toml`. With `ACP_BACKEND` set, `devin acp` only accepts credentials handed over by the host (the registry sets `ACP_BACKEND=windsurf`): `session/new` fails with -32000 until `authenticate({ methodId, _meta: { api_key, api_server_url } })` — any advertised methodId works if `_meta` has the key
- Devin's browser login (`devin-browser`) authenticates only the current process: the response is `{}`, the key is never returned or persisted. Durable accounts come from the toml only: import the local login, or run `devin auth login` in an isolated XDG directory (needs a TTY, so it runs in a VS Code terminal with file polling)
- `devin auth status` reads only the toml (ignores `WINDSURF_API_KEY`); delete `ACP_BACKEND` from the env before running it or it reports "Not logged in"
- Devin quota is not on the ACP wire: `/usage` is TUI-only (`Unknown command` over ACP) and `/session-stats` is per-session. The CLI reads it from the Windsurf seat service, a Connect RPC that also answers JSON: `POST {api_server_url}/exa.seat_management_pb.SeatManagementService/GetUserStatus` with `{ metadata: { apiKey, ideName, ideVersion, extensionVersion } }` (all four required, else 400; a bad key is 401). `userStatus.planStatus` carries `dailyQuotaRemainingPercent` / `weeklyQuotaRemainingPercent` (whole numbers) and `*QuotaResetAtUnix` (int64 as strings); `planInfo.hideDailyQuota` / `hideWeeklyQuota` say which windows the plan has (Max: weekly only, Pro: both). proto3 JSON omits zero fields, so on `billingStrategy === 'BILLING_STRATEGY_QUOTA'` a missing percent is 0%, not a missing window. `DevinAccountProvider.quota` → `AccountManager` cache (30 s max-age, forced after each turn of a bound session) → `AccountInfo.quota` → `ui/QuotaBars` in the account menu / settings rows
- Devin quota exhaustion and the automatic switch (devin 3000.11.3, verified 2026-09-26 with a real account): the default model `swe-2-high` (SWE-2) does not count against the window — two accounts at weekly 0% still answered with it — so a probe must pick a metered model (`claude-sonnet-5-medium` was used). With it, the Max account at weekly 0% failed the prompt with "Your weekly usage quota has been exhausted. Visit https://app.devin.ai/settings/usage to purchase on-demand usage or turn on auto-reload. (trace ID: …)"; the host replaced the error with the switch notice, skipped the Pro account (weekly 0%, daily 17%) under earliestReset, bound the Max account with allowance left, resumed the same native session with the chosen model kept, and the hidden continue prompt got the reply (`end_turn`, no error)
- Devin sweeps empty sessions that never received a message when the creating process exits: `session/resume` then returns `-32016 Session not found`. `AcpSession.openSession` sorts every restore failure into one of three outcomes — the peer has no restore path at all (readonly, `host.cannotResume`), it answered the session is gone (`session_not_found`, `session not found` text, or an invalidParams on resume/load whose message names none of DSH's other causes — see `classifyRestoreError` under the DSH bullet), it knows the session but refuses to continue it (`session is not resumable`: readonly with the peer's reason, `host.notResumable`), or it tried and failed (e.g. -32603: thrown as `host.resumeFailed` → the error Notice, where Retry does a full reconnect + resume). "Gone" transparently falls back to `session/new` only when the transcript is still empty; with turns present the session goes readonly (`host.sessionGone`) instead of silently continuing the visible conversation on an empty native context. A `session/prompt` answered session_not_found likewise leaves `ready` for the error state. Another common errorKind is `session_locked` (-32015, retryable: another process holds the session) — the one case with real evidence of occupation, so it gets its own error text (`host.sessionLocked`) and the same retryable error state. The message names the holder: `Session '<id>' is already open in another process (PID <n>). Close the other instance before opening it here.` (seen on a Linux remote, 2026-09-27, version not recorded); on disk the lock is `~/.local/share/devin/cli/session_locks/<id>.lock` holding that pid as text, left behind after the holder exits (Devin 3000.11.3, macOS). The usual holder is Acpira itself: a dropped Remote-SSH connection leaves the old extension host (kept for the server's reconnection grace period), its sidecar and that sidecar's `devin acp` running, and a reconnect that lands in a fresh extension host starts a second sidecar whose resume meets the lock — Retry can never succeed while the first one lives. `acp/agents/lock_holder.rs` reads the pid out of the error; when that process is a direct child of another `acpira` binary (`ps -o ppid=,comm=`, not this sidecar, unix only) the session records it and the view gets `canTakeOver`, the Notice offers "Take over here" (`takeOverSession`): the holder is checked again, SIGTERM'd (SIGKILL after `KILL_GRACE`), and the session starts over like Retry. The old sidecar only sees its agent exit and marks its own session errored; it does not reconnect by itself. A holder that is not a sidecar's child (a terminal `devin`) keeps the plain error. Verified with `a_lock_held_by_another_sidecars_agent_can_be_taken_over` (fake agent, `holder.pid`), not against a real orphaned extension host
- Devin background shells: an `exec` (kind execute, `rawInput.command` / `timeout`) that outlives its timeout is parked, not finished — a `tool_call_update` keeps `status: in_progress` and adds `_meta['cognition.ai/background'] = true`, `cognition.ai/backgroundShellId`, `cognition.ai/backgroundCommand`; the call stays in_progress until the process exits (`_meta.terminal_exit`), and its output lands on that exec's `content`. Later `get_output` (title `Read shell`, **no kind**, `rawInput { shell_id, timeout }`, `_meta['cognition.ai/inferenceToolName'] = 'get_output'`) blocks for up to its timeout waiting on that process; `kill_shell` is `Kill shell` with the same shape, `write_to_process` arrives as kind execute titled ``Wrote to `cmd` ``. Rendered generically this read as `正在调用工具 shell` for minutes and was mistaken for a hang (one such session was cancelled and told to continue for no reason). `normalize.rs` marks the parked exec `background` (skipped by `activityOf` / `foldActivity`, so a streaming thought wins), and gives `get_output` / `kill_shell` `verb.wait` / `verb.kill` with the parked command as target via `NormalizeState.shells` (shell id → command, in-memory). Verify with `scripts/probe-questions.ts devin "<prompt asking for a backgrounded sleep + get_output>"` (a one-off probe, since removed)
- `promptCapabilities.image` is not authoritative for Grok: it advertises `image: false` yet accepts inline `{ type: 'image', data, mimeType }` blocks in `session/prompt` and the model really sees the pixels (Devin / Kimi / OpenCode / DSH / pi-acp advertise `true`). The registry declares `prompt.imagesRegardless` for Grok; every other agent's flag is honoured (DSH rejects images its route cannot take). `pnpm probe <agent> --image PATH "describe it"` verifies. Grok also echoes the image block back as a `user_message_chunk` with `content.type === 'image'`, so user chunk handling must tolerate non-text content. Grok / Devin / Kimi / OpenCode advertise `embeddedContext: true`; DSH and pi-acp advertise `false`

- Claude authentication and silent 401 retries (2026-10-07; Windows 11, claude-agent-acp 0.84.0, Claude Code 2.1.284): a user-level `ANTHROPIC_API_KEY` made native `auth status --json` report `loggedIn: true`, `authMethod: api_key`, `apiKeySource: ANTHROPIC_API_KEY` while Acpira had no saved subscription account. The reported “你好” session persisted seven `system/api_error` records with HTTP 401 `API key is invalid` before cancellation after about 69 s; a read-only `/v1/models` request also returned 401. The adapter's `api_retry` handler deliberately suppresses authentication warnings, assuming the CLI gives up after one credential refresh. The host now subscribes to raw `system/api_retry` alongside workflow progress; a root retry with `error_status: 401`, `error: authentication_failed` and `attempt >= 2` ends the turn with an auth error, preserves partial output, and detaches/kills the retrying process. A first retry, child session and non-auth error remain under CLI control. `vendors/claude_auth.rs` also runs the same adapter's `--cli auth status --json` with the session cwd, agent env and bound account env before session creation and auth retries: only an explicit missing first-party credential blocks startup; API keys, external providers and unknown/unavailable probes retain the ACP path. A clean config on macOS (adapter 0.83.0 / CLI 2.1.284) reproduced `loggedIn: false` with successful ACP `session/new`; the fixed engine stopped at `auth_required` without a real prompt. Verify `tests/engine/acp_session/auth.rs`.
